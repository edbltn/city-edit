Two features whose product is common knowledge — “we are looking at this together, and we both know it” — so both are engineered for a number nobody has a reason to doubt rather than a number that is large. That inverts the usual analytics instinct: over-counting destroys the effect outright, under-counting costs a little, and every trade resolves in that direction. Neither reads device_id, whose localStorage preimage is currently fragmenting — keyed on it, both counts would RISE exactly as identity degrades. View counts are per-block HyperLogLogs UNIONed at read time, so a route proposal needs no durable id (it has none) and one person who opens two of its blocks counts once. Co-presence is a ZSET, not a sketch, because a room has to be able to empty. Both ride the WebSocket that already exists.

IDENTITY

What one person is, when device_id is falling apart

Symptom

Both features have to answer “how many PEOPLE” while the app’s only per-browser key is actively fragmenting: one iPhone produced six distinct voter_ids in three minutes on prod (2026-08-13), and per-device dedupe is already load-bearing for vote counting and proposal ranking.

Root cause

  • device_id is the sha256 of a localStorage UUID, and localStorage is not stable on this app’s traffic: Private Browsing and “Block All Cookies” mint a fresh id per document load, a sticker scan is TWO document loads, Safari’s ITP deletes script-writable storage after 7 days without a first-party interaction, and the canonical-subdomain hop crosses an origin
  • The dangerous property is not that the key is wrong — it is the DIRECTION it is wrong in. Keyed on device_id, a view count and a presence count both RISE as identity degrades. The metric looks healthier the more broken we get, and nothing outside the system can tell the difference
  • The product here is common knowledge, so a number people suspect is inflated is worth less than no number at all. Under-counting costs a little; over-counting costs everything at once

What changed

  • Both features dedupe on the COUNTING identity votes already use (server/vote_identity.py): the hashed IP. Neither reads device_id
  • Neither reads ANY client-supplied identifier. The key is taken from the WebSocket handshake server-side, so a client is never asked who it is and could not lie if it wanted to
  • Degradation is stated in both directions rather than assumed away: shared egress (household, office, carrier NAT) UNDER-counts permanently; one person across genuinely different networks over months over-counts by a few. The residual inflation needs a NETWORK change, not a page load — reload a hundred times and neither number moves
  • If VOTE_COUNT_IDENTITY=device is ever set, both inherit it along with votes and inflate together. That coupling is deliberate: there should not be two answers on one map to “how many people is this”

VIEW COUNTS

Counting per block, without double counting a corridor

Symptom

A view count on a proposal modal must not report one person twice because they opened two different blocks of the same route proposal — and a route proposal has no durable id to hang a counter on.

Root cause

  • RouteProposal.id is an FNV-1a hash of the corridor’s sorted PATH EDGES. It rotates whenever a vote lengthens, shortens or reroutes the corridor — the client already uses an id change as its signal that a corridor MOVED. A counter keyed on it would silently reset every proposal’s audience to zero on the next vote
  • legendIdx is worse: it is assigned by first-encounter order while the server builds each graph-votes snapshot, so one vote reordering one edge can shift every index for everybody
  • Summing per-block counts is the obvious implementation and is exactly the double count the brief rules out

What changed

  • Storage is one Redis HyperLogLog per (map, vote type, block): pv:<slug>:<type>:<block_id>. The key is a BLOCK id — a baked artifact, already the unit the vote system counts in
  • The proposal is named only at READ time, as a set of blocks. PFCOUNT k1 k2 … kn returns the cardinality of the UNION, so a person present in two of a corridor’s sketches contributes exactly 1. The dedupe is a property of the data structure, not bookkeeping anyone has to keep correct
  • Because nothing durable names the proposal, reshaping the corridor tomorrow reshapes the number with it — no migration, no backfill, no id to keep alive
  • The TYPE is in the key. Without it the 200 people who read a Protected-bike-lane corridor would appear as the audience for a Fix-signal-timing pin on the same corner. The key uses the LABEL, the one part of a proposal’s identity stable across recomputes and across clients
  • A view writes EVERY block the proposal spans, not just the clicked one. Anchoring on the clicked block was the first design and was wrong: a 40-block corridor read by 100 people would put all 100 in one sketch, so a sub-corridor would read 100 or 0 for the same street and the same readers depending on whether it happened to contain that block

CO-PRESENCE

A room that can empty

Symptom

“You’re looking at this with N other people”, shown only when there is more than one other viewer — and correct across the app’s 1–6 Cloud Run instances.

Root cause

  • HyperLogLog is right for cumulative views and WRONG here, for one reason: presence has to go DOWN. A HLL cannot forget a member, so a map 40 people visited over an afternoon would read “40 people are here now” forever — monotonic inflation, the exact failure this feature cannot survive
  • delta_hub.subscriber_count() already existed but is PER-PROCESS, so it would have under-reported by a factor of the instance count
  • This app throttles background tabs hard enough that a buried viewer is doing nothing at all, so a socket being open is not evidence anyone is looking

What changed

  • A Redis ZSET pres:<slug>, member = counting identity, score = last heartbeat. Entries older than 35s are pruned at read; heartbeats every 10s come from the server’s own socket loop, so client throttling cannot silently expire a live viewer
  • Departure is EXPLICIT (ZREM), not left to expiry — a count that stays high for 35 seconds after everyone leaves is over-reporting. A per-process refcount keeps closing one of a person’s two tabs from evicting them
  • Only VISIBLE tabs are counted: the client reports visibilitychange over the same socket and a hidden tab leaves the room immediately. A hidden tab is also not PUSHED the count — it is not in the set, so n would exclude it while the UI renders “n − 1 others” on the assumption that it is counted
  • Each process memoizes the count for 2s so a crowded map costs one Redis read per tick rather than one per socket; arrive/depart drop that memo, since the two changes a process makes itself are stale by construction

TRANSPORT

Four JSON messages on the socket that already exists

Symptom

Presence and view counts both need a client↔server round trip, and neither may open a second channel.

Root cause

  • A second connection per map for a viewer count would double the connection count, and — worse for a feature whose entire product is trustworthiness — would let presence and votes disagree about whether a client is still there
  • The binary wire codec’s KIND_DELTA/KIND_SYNC group layout does not fit a scalar, and client→server binary is rejected outright in frame version 1

What changed

  • {"type":"here","visible":B} and {"type":"view","k","t","b"} up; {"type":"presence","n"} and {"type":"views","k","n","exact"} down. No codec bump, no new endpoint
  • Presence pushes are EDGE-TRIGGERED — sent only when the number actually changes — so a steady room sends nothing at all
  • Presence maintenance sits BEFORE the queue drain in the socket loop: the continue on a successful drain skips the rest of the loop, so anything below it silently stops running on a busy map — exactly when people are most likely to be here together
  • k echoes the client’s own request token, so a reply that lands after the reader moved to another card is discarded rather than painted onto the wrong proposal
  • Views are rate-limited by a TOKEN BUCKET, not a flat interval. The flat version was the first cut and silently dropped a legitimate second view when a point card closed and a route card opened inside one second. PFADD is idempotent, so this is a work bound and never an integrity control

UI

Subtle, and countable

Symptom

Both numbers have to be legible and believable without becoming the loudest thing on the screen.

Root cause

  • A number nobody can check is a number people quietly discount, which is the whole failure mode for a rational-ritual feature
  • The proposal card’s de-emphasis convention is color-mix(in srgb, var(--ink) N%, transparent) plus a smaller size — never a hardcoded grey, so it tracks the light/dark basemap

What changed

  • The view count rides the card’s existing meta line — inside the 106px right-padding that clears the tool icons, in the same breath as the block count, at 45% ink against the meta’s 70%. It fades in, because it arrives seconds after the card and an unannounced layout shift at that distance reads as a glitch
  • Nothing renders below 2 people or while the count is unknown: no skeleton, no zero, no dash. “1 person has looked at this” printed to the one person looking at it reads as a bug or a boast
  • Copy is “N people have opened this”, not “N views” — views are cheap and get discounted on sight, and people is the literal truth of what the sketch holds. Above 1000 it says “about 1.2k” rather than a confident 1,247 the HLL cannot stand behind
  • Co-presence draws ONE MARK PER PERSON with yours filled, in the bare 1.5px stroked box the mobile wordmark builds its letters from. You can count the marks against the sentence, and the filled mark shows without a footnote that the total includes the reader — a count that had quietly excluded you, or padded itself, could not survive being drawn
  • The honest small print is one hover away rather than absent: counted once per network connection, foreground tabs only, people sharing a connection count as one

Verification

What was run

  • The load-bearing dedupe, measured on a REAL 22-block corridor in the running app: naive per-block sum 25, union 4. Three synthetic people seeded into three DIFFERENT blocks of one corridor plus the browser’s own view, unioned back to four.
  • Fragmentation immunity, end to end: three concurrent WebSocket clients from one IP report a presence count of 1, not 3, and six repeat views from one identity leave the sketch bit-identical.
  • Hidden tabs leave the room and come back: zcard went 4 → 3 when the browser tab was backgrounded and 3 → 4 when it returned, with no reconnect. Hiding ONE of a person’s tabs does not evict them; hiding the last one does.
  • Rendered in the running app and screenshotted: the proposal card reads “1 proposal · 5 people have opened this”, and the bottom-left strip reads ■□□□ “You’re looking at this with 3 other people”.
  • Cards that are not proposals stay silent, verified by the [audience] debug channel: a plain block logs idle enabled=true label=- blocks=1 and reports nothing. Hover cards never report at all.
  • A hidden tab refuses to report a view client-side AND the server refuses to record one — the two checks are independent, and the client-side refusal was observed in the debug log as <- no answer.
  • Two real bugs were found by testing rather than reasoning, and both were in the over-reporting direction: the 2s count memo served a pre-arrival value (joining a map you were alone on showed “0 others”, and a departure lingered), and the server kept pushing presence to hidden tabs (stale strip, and n silently excluding the reader so “others” was off by one).
  • 11 new tests against a real Redis, plus the full existing suite green (259 unit tests) and npx tsc -b clean — Vite dev never type-checks, so that pre-flight is the only thing that catches a broken client build.
For you

Manual checklist

  • Open the same map in two browsers on DIFFERENT networks (phone on cellular + laptop on wifi) and confirm the bottom-left strip appears with the right mark count. Two tabs on ONE network will correctly show nothing — that is the dedupe working, not a bug.
  • Background one of those tabs and watch the other’s count drop within a couple of seconds; foreground it and watch it come back.
  • Open a proposal card and leave it open for two seconds, then reopen it — the count must not increase. Reload the page a few times and reopen: still must not increase.
  • Open the SAME route proposal from two different blocks of its corridor and confirm the number is identical and unchanged — this is the double-count the design exists to prevent.
  • Confirm a proposal with only you having viewed it shows NO count at all, rather than “1 person”.
  • Hover (don’t click) across a dense cluster of pins and confirm no counts move — hover cards must never register a view.
  • After deploy, check redis-cli --scan --pattern 'pv:*' | wc -l grows slowly and zcard pres:<slug> tracks real traffic; both keys carry TTLs, so neither should grow without bound.

+tell the difference from the outside, which is why it has to be structurally

+"""How many people have opened a proposal.
+
+Same honesty bar as presence.py, a different time horizon: this number is
+cumulative, so it has to survive being wrong for months rather than for 35
+seconds.
+
+WHAT IS STORED — one sketch per (map, vote type, block), nothing per view
+------------------------------------------------------------------------
+`pv:<slug>:<type>:<block_id>` is a Redis HyperLogLog holding one member per
+person who has opened a proposal of that type covering that block. There is no
+row per view, no timestamp, no IP, no device_id, and nothing enumerable — a HLL
+is a lossy register array, so the stored bytes cannot be turned back into a list
+of who was here. The honest minimum for "show a count" is a structure that can
+only ever produce a count, and this is that structure. It is also ~200 bytes for
+a block a few dozen people have seen (Redis keeps small sketches sparse) against
+~40 bytes per row for the obvious alternative, so the private choice is the
+cheap one too.
+
+WHY THE ROUTE LEVEL DOES NOT DOUBLE COUNT
+-----------------------------------------
+A route proposal is a corridor of many blocks, and the same person will open it
+from two different blocks on two different days. Summing per-block counts would
+report them twice.
+
+We never sum. `PFCOUNT k1 k2 … kn` returns the cardinality of the UNION of the
+sketches, so someone present in both block A's and block B's sketch contributes
+exactly 1 to a proposal spanning {A, B}. The dedupe is a property of the data
+structure, not bookkeeping anyone has to keep correct.
+
+That is also what makes the feature implementable at all, because *route
+proposals have no durable id*. `RouteProposal.id` is an FNV-1a hash of the
+proposal's sorted path edges (routeProposals.ts), so it rotates every time a
+vote lengthens, shortens or reroutes the corridor — the client uses an id change
+as the SIGNAL that a corridor moved. `legendIdx` is worse: it is assigned by
+first-encounter order while the server builds each graph-votes snapshot, so it
+can shift for everyone when one vote reorders one edge. Hanging a counter on
+either would have quietly reset every proposal's audience to zero on the next
+vote. Here the storage key is a BLOCK id — server-owned, baked, already the unit
+of the vote system — plus the vote type's LABEL, which is the one part of a
+proposal's identity that is stable across recomputes and across clients. The
+corridor itself is supplied at READ time as a set of blocks. Reshape it tomorrow
+and the number reshapes with it, still deduped, with no migration and no
+backfill.
+
+WHY THE TYPE IS IN THE KEY
+--------------------------
+Without it, every proposal on a block shares one audience: the 200 people who
+read the Protected-bike-lane corridor would appear as the audience for a
+Fix-signal-timing pin on the same corner, which is a different proposal by a
+different author about a different thing. Keying by type confines any bleed to
+proposals of the SAME type overlapping the same ground — which the proposal
+layer already limits (one point winner per block per type; route proposals of a
+type are diversity-capped at Jaccard 0.5).
+
+WHAT A "VIEW" IS, AND WHY WE WRITE EVERY BLOCK
+----------------------------------------------
+A view is: an interactive proposal card, open and on screen, for VIEW_DWELL_MS.
+Hover cards never count — they are `pointer-events:none` transients the mouse
+crosses on the way somewhere else, and counting them would make the number
+mostly mouse trajectory. A hidden tab never counts.
+
+One view PFADDs the viewer into every block the opened proposal spans, not just
+the one they clicked. Anchoring on the clicked block alone was the first design
+and it is wrong: a 40-block corridor read by 100 people would put all 100 in one
+sketch, so a sub-corridor's count would depend on whether it happened to contain
+that one block — 100 if it did, 0 if it didn't, for the same street and the same
+readers. Writing every block makes each sketch a true statement on its own
+terms, and makes the count precisely sayable:
+
+    a proposal's count = the number of people who have opened a proposal of
+    this type covering any part of this one.
+
+The UI copy is written to that sentence and does not claim more.
+
+IDENTITY, AND WHAT THIS DEGRADES TO
+-----------------------------------
+The member is the COUNTING identity votes already use (vote_identity.py): the
+hashed IP, taken from the WebSocket handshake. Explicitly NOT `device_id`, whose
+localStorage preimage is currently fragmenting — one iPhone, six voter_ids,
+three minutes (prod 2026-08-13).
+
+Keyed on device_id, that person reads as six viewers, and the count rises every
+time identity degrades further: a metric that looks healthier the more broken it
+gets, with no way to notice from outside. Keyed on an IP hash, those same six
+page loads are one member added six times to one sketch, and PFADD is
+idempotent, so the number does not move at all. Reload the tab a hundred times
+and nothing happens.
+
+What it degrades to instead:
+  · Shared egress — household, office, school, carrier NAT → many people, one
+    member, permanently UNDER-counted. Accepted: a modest true number is worth
+    more here than a large uncertain one.
+  · One person on genuinely different networks over months (home, work, phone)
+    → a few members. This is the residual inflation. It is real, but it is
+    bounded by how many networks a person uses, not by how often their storage
+    clears — a few, not dozens, and it needs a network change rather than a
+    page load.
+  · Redis unreachable → 0, which reads as "say nothing" at the display floor.
+    A broken cache must not be able to invent an audience.
+
+Finally, HLL is approximate (~0.81% relative error) at large cardinality and
+effectively exact while the sketch stays sparse, which covers every number these
+maps actually produce. `count_views` returns that distinction next to the number
+so the UI can stop claiming precision it does not have.
+"""
+
+import hashlib
+import logging
+
+logger = logging.getLogger(__name__)
+
+# Sketches for a block nobody has opened in half a year are not worth keeping.
+# Refreshed on every write, so a proposal people still read never expires.
+KEY_TTL = 180 * 86400
+
+# Ceiling on how many blocks one message may write or union. Corridors run to a
+# few dozen blocks; this bounds the work one client can ask for per view.
+MAX_PROPOSAL_BLOCKS = 256
+
+# Above this, stop printing an exact figure — HLL's error stops being smaller
+# than the last digit we would be showing.
+EXACT_BELOW = 1000
+
+# Returned when Redis fails or the request is empty.
+COUNT_ERROR = (0, True)
+
+
+def type_token(label: str) -> str:
+    """Short stable token for a vote type.
+
+    The LABEL, not `legendIdx` (per-snapshot, shifts under everyone) and not the
+    DB `vote_type_id` (which would mean a lookup that can create rows on a path
+    driven by client messages). Hashed only to bound the key length and keep
+    arbitrary user text out of Redis key names.
+    """
+    return hashlib.sha1((label or "").strip().encode("utf-8")).hexdigest()[:10]
+
+
+def block_key(slug: str, token: str, block_id: int) -> str:
+    return f"pv:{slug}:{token}:{int(block_id)}"
+
+
+def normalize_blocks(block_ids) -> list[int]:
+    """De-duplicated, integer, length-capped. Block ids may legitimately be
+    NEGATIVE — `blockKeyOf` returns `-(edgeId + 2)` for an edge that belongs to
+    no baked block — so the guard is on type and count, never on sign."""
+    out: list[int] = []
+    seen = set()
+    for b in block_ids or ():
+        try:
+            bid = int(b)
+        except (TypeError, ValueError):
+            continue
+        if bid in seen:
+            continue
+        seen.add(bid)
+        out.append(bid)
+        if len(out) >= MAX_PROPOSAL_BLOCKS:
+            break
+    return out
+
+
+def record_view(redis_client, slug: str, label: str, blocks: list[int],
+                identity: str) -> None:
+    """Count `identity` as having opened a proposal of type `label` spanning
+    `blocks`.
+
+    Idempotent by construction: a hundred reopens from the same identity leave
+    every sketch bit-identical, which is why no rate limit is needed to keep the
+    number honest (only to keep the work bounded).
+    """
+    if not blocks:
+        return
+    try:
+        token = type_token(label)
+        pipe = redis_client.pipeline()
+        for bid in blocks:
+            key = block_key(slug, token, bid)
+            pipe.pfadd(key, identity)
+            pipe.expire(key, KEY_TTL)
+        pipe.execute()
+    except Exception as e:
+        logger.debug(f"[VIEWS] pfadd failed for {slug}/{label}: {e}")
+
+
+def count_views(redis_client, slug: str, label: str,
+                blocks: list[int]) -> tuple[int, bool]:
+    """People who have opened a proposal of this type covering any part of this
+    one. Returns `(count, exact)`.
+
+    The UNION — not the sum — is what makes one person who opened two different
+    blocks of the same corridor count once.
+    """
+    if not blocks:
+        return COUNT_ERROR
+    token = type_token(label)
+    try:
+        n = int(redis_client.pfcount(*[block_key(slug, token, b) for b in blocks]))
+    except Exception as e:
+        logger.debug(f"[VIEWS] pfcount failed for {slug}: {e}")
+        return COUNT_ERROR
+    return n, n < EXACT_BELOW
