Dropping a waypoint onto a route-based top proposal (a diamond) now threads the route through the proposal's whole corridor with an explicit forced-corridor flag in the canonical Selection — replacing the old implicit “the pair's coords happen to equal a live proposal's anchors” matching. Selection model · forcedCorridor

1 · Forcing is now a first-class flag, not a coordinate coincidence

Symptom

“Forcibly routed through the top proposal” was implicit: any consecutive waypoint pair whose coords happened to float-equal a live RBTP's anchors routed through its corridor. That broke silently under proposal churn (live vote deltas recompute the proposal set), couldn't distinguish “user threaded this” from coincidence, and left no room for the endpoint-drop scenarios.

Root cause

  • The corridor resolver matched (a, b) against every live proposal's anchorCoords within 5 m — no stored state anywhere.

What changed

  • SelWaypoint.forcedCorridor: {proposalId, edgeIds?} — the segment LEAVING a waypoint is flagged as forced. edgeIds is a snapshot of the corridor's ordered path edges taken at threading time, so the forced geometry survives proposal churn; proposalId (the deterministic FNV id) is what the URL carries.
  • Break rules live in the reducer, exhaustively unit-tested: moving either end of a flagged pair clears it (updateAt/setStart/setEnd), inserting a mid between the anchors clears it (insertMid), removing an anchor clears it (removeAt, and the multi-remove in removeWaypointsNear). An in-place replace (same coords, e.g. re-pinning a vote edge) keeps it.
  • URL: ?w=lat,lng,f<proposalId>;… — one compact marker per forced segment. History entries compare flags too, so back/forward restores forcing exactly.
  • insertWaypointAtSegment skips the instant local geometry split when the split segment was forced — splitting the corridor polyline in place would silently KEEP the shape the user just asked to break; it does a full recalc instead.

MapView · endpoint drops

2 · Dropping START or END on a diamond threads the corridor (scenarios 1 & 3)

Symptom

Dragging an endpoint onto a route-based top proposal did nothing corridor-ish: the sticky snap glued the point to the diamond's midpoint, the kite hid behind the indicator (“the endpoint seemingly disappears”), and the route just re-ran OSRM to that spot.

Root cause

  • The start/end kites ended their drags with bare setStartPoint/setEndPoint (MapView) — no diamond hit-test; only mid/path drops were corridor-aware.

What changed

  • Drop E on a diamond → replaceEndWithPair: route becomes S…A→Z with the near anchor joining as the last mid, the far anchor becoming the END proper, and the pair flagged. chooseAnchorOrder with a head-only chain picks SAZ vs SZA — the corridor's own length cancels, so it reduces to “is the last fixed point closer to A or Z” on the straight-line proxy every drop decision shares.
  • Drop S on a diamond → replaceStartWithPair: AZ…E or ZA…E, one anchor becomes the START proper (kite + geocode), ordered by the new chooseAnchorOrderBefore (the head-side complement).
  • Both ops are atomic: one selection change, one history entry, one recalc — mirroring removePoint's choreography (handlingRemovalRef suppresses the main effect's duplicate recalc). Re-dropping an already-threaded corridor in the same orientation is a no-op.
  • The exploded-proposal drop path (onProposalDrop) routes its start/end branches through the same handlers, and the mid/path pair ops now stamp the flag too. Clicking a diamond funnels through the new atomic selectCorridor (replacing the clearPoints+setStart+setEnd dance).

GraphLayer · corridor resolver

3 · Flag-driven resolution: live proposal → snapshot → OSRM

Symptom

A deep link or history restore of a corridor selection rendered the OSRM path between the anchors — the coordinate match only worked while the proposal set happened to contain the same anchors, and nothing re-routed when proposals finished computing.

Root cause

  • Resolution keyed on live anchor coords only; proposals compute AFTER the first route calc on load, and nothing re-triggered the calc when they arrived.

What changed

  • The resolver takes the flag: live proposal by id first (keeps the corridor current while it exists — deep links carry only the id), then corridorFromEdgeIds rebuilds the chain from the snapshot (start node inferred from the first two edges, polyline oriented a→b geometrically), else null → graceful OSRM fallback.
  • notifyCorridorsChanged: RouteContext remembers when a FLAGGED segment failed to resolve; GraphLayer pokes it whenever the live proposal set changes, so a restored link recalcs exactly once and the corridor snaps in — verified live: a cold reload with only f1c98f342 in the URL rendered the segment as the corridor's verbatim 70-point chain.
