Two block-pipeline playground maps (“Test: Midtown”, “Test: Central Park”) were showing on the public cityedit.org landing grid — the boot-time preset seeder recreated them in every environment, so row deletion alone could never stick. They are now opt-in via SEED_TEST_MAPS=1 and their prod rows and Redis stamps are gone. In the same session the staging environment was decommissioned entirely (not enough users to justify the parity copy): all 14 staging terraform resources destroyed with targeted applies, the staging files removed from the repo, and the deploy runbook rewritten to the direct-to-prod flow — backup → digest → verify.

SERVER / DATA

Test: Midtown & Test: Central Park kept resurfacing on prod

Symptom

The two block-pipeline playground maps showed as public cards on the cityedit.org landing grid. Deleting their DB rows would not have stuck: they reappear on the next boot.

Root cause

  • seed_presets() upserts every PRESET_MAPS entry unconditionally at startup, in every environment — the playground entries added for the block-pipeline experiments therefore self-heal into any DB, prod included
  • /api/maps has no hidden/archived filter: every row in maps renders on the landing grid

What changed

  • The two playground presets are now opt-in: appended to PRESET_MAPS only when SEED_TEST_MAPS=1 (never set on prod), so the seeder can no longer recreate them there
  • Deleted their maps rows on prod (both had 0 votes, no redirects); purged the two orphaned bver:* Redis keys — the only test-map keys in prod Redis
  • Existing local DBs keep their playground rows untouched (the seeder only upserts); a fresh local DB wants SEED_TEST_MAPS=1
  • Shipped as overlay digest d64843f6… (base: the serving f0bf4262…) → prod rev 00121-2h6, after the mandatory DB backup (~/city-edit-prod-backups/20260801-224221/)
