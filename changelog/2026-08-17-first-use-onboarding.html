A newcomer arrives holding a complaint ("I nearly got hit crossing here") and the app asks them for a vote type ("Add curb extension"). So the first screen is now a wall of half-finished sentences drawn from the map’s OWN vote types, and the map is where you finish one. Picking a sentence writes its vote type into the canonical Selection; every step after that is DERIVED from that Selection rather than tracked beside it. Two things decided the shape more than taste did: "have you been here before?" is answered on the IP hash the vote system already counts by, because the browser id demonstrably fragments; and a route-kind sentence is not allowed to reach the cast button until it has two ends, because a route vote on one point silently retargets.

THE FIRST SCREEN

A wall of sentences, built from the map’s real vote types

Symptom

Nothing greeted a first-time visitor. The map loaded, the heat painted, and the app waited for a click it had never explained — and the vocabulary it wanted ("Add curb extension", "Daylight this corner") is written in the voice of a work order, not of a person standing on a corner.

Root cause

  • The gap is a VOICE gap, not an instructions gap. Nobody thinks "improve sidewalk"; they think "two people can’t pass each other here". A tour that pointed at the existing controls would have taught the controls without closing that gap
  • Vote types are per-map (maps.custom_vote_types + the global vote_types table) and get edited: nyc-tactical went 24 → 18 on 2026-08-14. Any hardcoded list of openers rots on the next edit

What changed

  • The wall — a full-screen grid of half-finished sentences over the live map, one per vote type the map actually authors, read from /api/maps/<slug>. Every slip names the vote type it commits to and whether it wants a spot or a stretch, so the wall is a friendlier way IN to the vote types, never a way of hiding which one you picked
  • The phrasebook (onboarding/phrasebook.ts) owns exactly one direction: label → the sentence a person would say. 120 hand-written lines cover every label the shipped maps use; verb rules derive a grammatical sentence for types authored later; generic sentences that name no vote type at all carry a map whose set is entirely custom (nyc-ebike-charging authors none)
  • It is the wordmark, exploded. CITY EDIT is drawn as letters in 1px boxes; the wall is that construction at paragraph size, ruled into one continuous grid, with the map showing through a 96% paper scrim. No new tokens, no new type family — the point of the screen is that the app has already started
  • Route and point types are INTERLEAVED rather than grouped: a map’s authored list arrives clustered by family, and a wall that reads as two solid blocks invites you to pick from the top block only — which is exactly the choice that decides whether the flow asks for one point or two

STATE

The step is a projection of the Selection, not a copy of it

Symptom

The obvious way to build a first-run flow is a little state machine of its own — step 1, step 2, step 3 — and the moment it exists it can disagree with the map.

Root cause

  • This app has selection history (real back/forward), deep links, a legend that can move either endpoint, and a topbar Cast control. Any of them can move the user’s position in the flow without telling the flow
  • The canonical Selection already knows everything the flow needs: how many waypoints exist, which vote type was requested, whether the current target is already cast

What changed

  • onboardingStep(facts) is a pure function of the live Selection — the same kind of projection as selectionPhase and pointType. Wall → start → end → cast → done, recomputed every render, never stored
  • Picking a sentence calls setVoteType(label), so the choice lands in the Selection AND in the URL (?vt=Add+crosswalk). A reload resumes at the same sentence; the flow’s memory IS the address bar
  • Only two flags belong to the flow, and neither holds a fact the Selection also holds: a generic sentence was chosen (it names no vote type, so there is nothing canonical to hold), and the optional end was declined ("stop asking", not "there is no end")
  • Where the flow acts, it DRIVES the model: reaching the end step calls setActiveTool("end") — the same call the legend’s End button makes — because sticky-start means a bare tap would otherwise wipe the route and drop a new start

THE FIRST TRAP

"Have you been here before?" is answered on the IP hash, not on the browser

Symptom

A first run keyed on a fragmenting identity greets the same real person again, and again, and again — which is strictly worse than never onboarding anybody.

Root cause

  • voter_id is a UUID in localStorage, and prod recorded ONE iPhone minting six of them in three minutes on 2026-08-13 (the day server/vote_identity.py was written). Private Browsing, "Block All Cookies", Safari’s 7-day ITP eviction, and the canonical-subdomain hop (which crosses an ORIGIN) each mint a fresh one
  • A flag written beside it fragments identically. The QR flow is the worst case and the most important one: a scan is TWO document loads, /s/<code> then the map

What changed

  • The question is behavioural, and the key is the one the vote system already counts by. New endpoint GET /api/visitor answers "has anybody at this COUNTING identity ever cast a vote?" via vote_identity.counting_identity() — the IP hash, falling back to the device — out of Postgres, which survives Redis flushes and deploys
  • localStorage appears in exactly one role: a SUPPRESSANT. It can stop the flow, never start it. Losing it costs one round-trip, never a repeat performance
  • Fails closed. An unreachable or erroring API answers "returning visitor". A blip must not put a wall in front of everybody on the site; the cost of the opposite mistake is that one newcomer sees the map without its introduction, and the map is what they came for
  • What happens when the key changes, stated rather than implied. Storage cleared, same network → server suppresses. New network, storage intact → local mark suppresses. Both at once → they see it again, which is why the wall is one tap to dismiss and never claims "welcome back". Shared NAT → a genuinely new colleague of a voter is NOT onboarded — a false negative preferred deliberately to a false positive, and recoverable: "Start a sentence" in How it Works reopens the wall on demand
  • Two single-column indexes (idx_edge_votes_device, idx_edge_votes_ip) back the two EXISTS probes: 0.07–0.09 ms index-only scans against 1.19 M dev rows. The existing composite index cannot serve them — it leads with map_slug, and the question is deliberately map-agnostic

CORRECTNESS

A route-kind sentence cannot reach the cast button on one point

Symptom

"I cross here every day, and there’s no crosswalk…" with a single pin down would have offered a cast — and cast the wrong thing.

Root cause

  • With one waypoint the Selection’s pointType is "point", so resolveEffectiveVoteType finds "Add crosswalk" invalid for the current family and falls back to the map’s DEFAULT POINT TYPE. The cast would have recorded something the user never picked
  • And a route vote on an isolated point can never become a route proposal — it is not a small corridor, it is a dead vote

What changed

  • requiresEnd() holds the cast step back until both ends exist, keyed on the chosen label’s point_type read from the map’s own vote types (pointTypeForLabel), never from a list in the flow
  • A generic sentence asks for an end but takes no for an answer (endIsOptional) — and its cast step quotes what the map’s default resolved to, plus "— or pick another above": the only place the app tells a newcomer that the Proposal picker is theirs to move
  • Station networks (ebikes) never ask for an end, whatever kind their types were authored as — the same rule mapVoteTypesForPointType already applies
  • The label is QUOTED in the question (“Add crosswalk”, all along this stretch?) rather than folded into it: vote types are work orders, and no wording makes every one of them read as a verb phrase mid-sentence

THE SECOND TRAP

What the downvote policy actually is — measured, not assumed

Symptom

The brief asked whether inviting a brand-new user to cast a negative vote is a bad first impression. It is a fair question, and the answer was not in any doc.

Root cause

  • The code says downvotes are first-class. direction = -1 is live end to end: the topbar’s − button, /api/vote, plan_block_vote’s one-direction-per-block invariant, and block heat’s signed differential with its own negative arm (NEG_FULL_SCALE = 10, per-theme cold arms). Nothing is disabled and no map can disable it
  • The operational record says otherwise. Counted directly out of the prod snapshots in ~/city-edit-prod-backups/: of 873,176 rows on 2026-08-14, 298 are negative — 0.034%, and they are FOUR cast events in the app’s whole history (2026-06-07, 06-08, 06-09, and one 295-edge corridor on 08-13)
  • And a batch was deleted four days ago. Diffing 20260814-181936-before-queens-negatives against the next snapshot: 98 rows removed, all one device, one IP, one timestamp, one vote type ("Add traffic calming") on nyc-proposals — i.e. one person’s single downvote fanned across a 98-edge Queens corridor, deleted by hand. The documented 308 k deletion before it was different in kind: IMPORT-generated -1 rows, after which flips were banned on prod imports (counter_lyft cancels with direction 0)

What changed

  • Both buttons ship, in this order: − Not here, then + Yes, here. Hiding − would teach a newcomer that the map only takes agreement, which is false to the data model and to the intent of a map about contested street space
  • The affirmative completes the sentence. Every opener is a complaint or a wish, and the vote it produces is the REMEDY — a + for the fix, not a − for the street. That is the whole reason a complaint-shaped opener can drive a support-shaped data model, and it means the natural path through this flow produces the row the system is happiest with
  • − is styled as the equal-weight second option (--color-end outline) rather than a de-emphasised one — present and honest, never the default
  • Flagged for you, not decided by me: if the Queens deletion means downvotes are unwanted in practice, the honest fix is a per-map switch on the whole app’s − control, not a first-run screen that quietly withholds it. Say the word and I will build that instead

THE QR PATH

The scan trigger needed nothing from the sticker flow

Symptom

Onboarding also has to fire for a scan of an unlinked QR code — a flow another agent owns and that must not be rewritten.

Root cause

  • That flow already does the two things this one needs. stickerFallbackUrl / stickerMapUrl put the sticker’s vote type into the URL as ?vt=, which IS the canonical Selection’s memory; and ?stk= rides along only while the code is still unbound

What changed

  • What I needed from it, and took without touching it: hasPendingSticker() (true exactly when this visit came from an UNRESOLVED code) and the vt= it already writes. Zero lines changed in sticker/ or StickerGate
  • An unlinked scan onboards even for a VETERAN voter, overruling both the server answer and the local suppressant. That visit’s first vote is what pins the sticker for everyone who scans it afterwards — and the veteran is the person most likely to pin it right
  • The wall is skipped entirely on that path: the object in their hand already chose the sentence, so the coach opens at "tap the map on the spot you mean". Same derivation, no special case — a vt= in the URL means "picked", whoever put it there
  • A link that arrives WITH a selection (a shared proposal, a located sticker) also skips the wall: that choice is already made, and a wall over somebody’s shared link is a bad answer to a good link

THE UI SLOT

One place the app speaks from, and one thing standing aside

Symptom

The bottom-centre of the map is a contested slot: the error toast, the event banner and the co-presence strip all live there.

Root cause

  • MapNotice is the single base for that slot, and it enforces two rules a new component would have had to re-earn: the strip is transparent to the pointer, and it sits UNDER the map’s cards, so a notice can never be why a proposal underneath it won’t take a tap

What changed

  • The coach IS a MapNotice — it inherits the slot, the palette, the safe-area insets, the wrapping and the stacking, and the error toast rides above it automatically. Not one raw z-index was written; the wall takes the existing --z-modal rung
  • While the coach is up, the event banner stands aside (onboarding/active.ts, a two-value store read with useSyncExternalStore). It is durably dismissible and the event is a week out; a first-timer being asked to do one thing should not also be invited to a walk next Saturday. It takes the slot back the moment the coach retires
  • The coach carries its own address search, which matters most on a phone: .topbar-legend is display: none under 600px, so the search field the desktop legend offers does not exist there at all. Its autocomplete opens UPWARD, because the strip is at the bottom of the screen

  • Pick a stretch slip, place only the start, and confirm the coach refuses to offer a cast until the second end is down — while the topbar’s Cast pair is live. That asymmetry is deliberate.
  • Pick a your own words slip and check that the cast line quotes what it resolved to before you press anything.
  • Decide the downvote question: the − button ships in the first run. If the Queens deletion means you want downvotes gone, say so and I will put a switch on the app’s − control rather than hide it here.

+// Where a first-timer is in the flow — derived, never stored
+// ==========================================================================
+// The canonical Selection already knows everything about where somebody is: how
+// many waypoints they have placed, which vote type they asked for, whether the
+// current target is already voted. So the onboarding step is a PROJECTION of
+// that, exactly like `selectionPhase` and `pointType` are. Nothing here is
+// state; every input is read from RouteContext on the render it is used.
+//
+// This matters more than it looks. The obvious way to build a first-run flow is
+// a little state machine of its own — step 1, step 2, step 3 — and the moment it
+// exists it can disagree with the map: the user drops a second pin from the
+// legend, or hits the browser back button (this app has real selection history),
+// or opens a shared link, and the coach is still saying "tap the map to start"
+// over a finished route. Deriving costs one function and cannot drift.
+//
+// Two flags are genuinely the flow's own, and neither carries any truth the
+// selection also holds:
+//   · `picked`     — a wall tile was chosen. When it names a vote type this is
+//                    itself derived (the label is in the Selection, and in the
+//                    URL). Only a GENERIC tile, which names no type, needs the
+//                    local bit, and losing it just reopens the wall.
+//   · `endSkipped` — the user declined the optional end on a generic sentence.
+//                    "Stop asking", not "there is no end": place one anyway and
+//                    the route appears, because the selection is still the truth.
+// ==========================================================================
+
+/** The step the coach is on. `wall` is the tiled opener screen. */
+export type OnboardingStep = "wall" | "start" | "end" | "cast" | "done";

+  /** A sentence has been chosen (typed tile ⇒ the selection carries its label). */
+  picked: boolean;
+  /** The chosen type's kind, or null for a generic sentence. */
+  pointType: "route" | "point" | null;
+  /** The map votes on fixed stations (ebikes): one point, never a route. */
+  isStationNetwork: boolean;
+  hasStart: boolean;
+  hasEnd: boolean;
+  /** The optional end was declined (generic sentences only). */
+  endSkipped: boolean;
+  /** This selection is already cast in the direction the control would apply. */
+  hasVoted: boolean;
+}

+/**
+ * Whether this flow must collect an end point before it may offer a cast.
+ *
+ * Route-kind vote types are the reason this exists. A route vote on a single
+ * point is not a small version of a corridor — it is a vote that can never
+ * become a route proposal, and worse, casting one silently retargets: with a
+ * lone waypoint the selection's point type is "point", so the effective vote
+ * type resolves AWAY from the route label the user chose and lands on the map's
+ * default point type instead. Offering the cast button early would record a vote
+ * for something the user never picked.
+ */
+export function requiresEnd(facts: OnboardingFacts): boolean {
+  if (facts.isStationNetwork) return false;
+  return facts.pointType === "route";
+}
+
+/** Whether an end point is worth asking for but fine to skip — a generic
+ *  sentence, whose vote type isn't decided until the cast. */
+export function endIsOptional(facts: OnboardingFacts): boolean {
+  return !facts.isStationNetwork && facts.pointType === null;
+}
+
+export function onboardingStep(facts: OnboardingFacts): OnboardingStep {
+  if (facts.hasVoted) return "done";
+  if (!facts.picked) return "wall";
+  if (!facts.hasStart) return "start";
+  if (!facts.hasEnd && (requiresEnd(facts) || (endIsOptional(facts) && !facts.endSkipped))) {
+    return "end";
+  }
+  return "cast";
+}

+  /** This visit arrived from a scan of a sticker that nobody has voted from yet
+   *  (`?stk=` — sticker/pending.ts). */
+  pendingSticker: boolean;
+  /** The visitor dismissed the flow during this visit. */
+  dismissed: boolean;

+ *               with the sentence already chosen, so the coach is two steps.
+ *               It runs even for a veteran voter, which is the point: the
+ *               veteran is the person most likely to bind it correctly.

+  if (facts.pendingSticker) return true;

+/** Alternate the two families, longest-first, so neither can own the top of the

+function interleave(a: MapVoteType[], b: MapVoteType[]): MapVoteType[] {
+  const [long, short] = a.length >= b.length ? [a, b] : [b, a];
+  const out: MapVoteType[] = [];
+  for (let i = 0; i < long.length; i++) {
+    out.push(long[i]);
+    if (i < short.length) out.push(short[i]);
+  }
+  return out;

+    // ordering and therefore the map author's preference.

+    .slice(0, genericCount)

+      text,
+      voteType: null,
