Fund per row — and three things that were not what they looked like

2026-08-09 · branch main
Fund moves onto the row The nav tooltips were not losing a z-index fight The source markers were there the whole time What Donorbox will and will not prefill VerificationChecklistFull diff

Four follow-ups. The fund affordance moves off the card and onto the row: a [$] chip beside that row's [a][b][c] source markers, which also lets the "which proposal did you mean" rule be deleted rather than refined — a row IS a proposal. The other three were misdiagnosed by their symptoms. The nav tooltip was not losing a z-index fight; it already painted on top, in the same paper-and-hairline as the buttons it landed on, so it dissolved into them. The mobile source markers were not missing; they were sitting at the half-strength resting state that only a hover can lift, at 10px, which on a phone is the same as gone. And the donation links populate nothing because the redirect still eats the query string in prod — a deploy, not a bug. The one thing that really cannot be done is the comment field: probed one parameter at a time, Donorbox ignores every spelling of it.

THE CHANGE

Fund moves onto the row

Symptom

The fund affordance shipped as a text row at the foot of the card — [$] Fund this proposal — which is a whole extra band of card for one link, and it had to answer a question first: WHICH proposal, when the card lists several?

Root cause

  • A card is a place; a ROW is a proposal. Putting the action on the card forced a rule (fundableProposalName: the top proposal, else a lone vote type, else nothing) whose entire job was to disambiguate something the rows already disambiguate by existing
  • That rule also meant the commonest interesting case — a corner where three different things have been proposed — got NO fund affordance at all, because guessing would have been wrong

What changed

  • The row carries a [$] chip beside its own [a][b][c] source markers: same bracket-token vocabulary, same size, in the accent because it is an ACTION and they are citations
  • Each chip's link names its own vote type, and its deep link re-selects this point under that type — so two rows on one corner produce two distinguishable donations
  • The chip LEADS the marker run instead of trailing it: citation counts vary row to row, so a chip after them would land at a different x on every line, and this is a thing you aim at
  • The card-level donate prop becomes donateUrlFor(label), and fundableProposalName is deleted outright — the question it answered no longer exists

NOT WHAT IT LOOKED LIKE

The nav tooltips were not losing a z-index fight

Symptom

Hovering Donate (and How it Works) showed a label that seemed to disappear underneath the "Clear" button on the row below.

Root cause

  • It reads exactly like a stacking bug, but it is not one. The tooltip is position: absolute at --z-dropdown (200); nothing between it and the topbar creates a stacking context, and a positive-z positioned element paints above every non-positioned sibling in the same context. Painting a probe copy in magenta showed it sitting cleanly on top of Clear
  • The real cause is camouflage. The tooltip was background: var(--paper) with a 1px solid var(--ink) border — which is exactly what the Cast/Clear buttons it lands on are. Same fill, same hairline, so the box read as part of the control beneath it and its text tangled with the word "Clear"
  • Donate makes it worse by having nothing to say: it renders its label INLINE above 1080px, so its tooltip was a second "Donate", one row lower, on top of something else

What changed

  • The tooltip inverts — background: var(--ink), color: var(--paper) — so it can never be mistaken for the UI it covers. Inversion is theme-safe by construction: both tokens flip together on the light basemap
  • Donate's tooltip is suppressed above 1080px (content: none), exactly where its inline label speaks for it; below that width the label is hidden and the tooltip comes back
  • z-index is untouched, because it was never the problem

MOBILE

The source markers were there the whole time

Symptom

Reported as "the [a][b][c] links do not appear on mobile".

Root cause

  • They do appear. Driven headless at 390×844 with touch emulation and a real tap on a proposal pin: the interactive card opens, /api/vote-sources answers with the 21st Street study, and the anchor is in the DOM — display: flex, visibility: visible, inside the card's bounds
  • What is missing on touch is the HOVER. The markers rest at opacity: 0.5 and only reach full strength on :hover, which a finger never delivers. So on a phone they sit permanently at half strength, at 10px
  • 10px at 50% opacity on a phone is not a subtle affordance, it is an invisible one — which is indistinguishable from absent

What changed

  • Under @media (hover: none) the markers rest at 0.85 instead of 0.5 — the state they can never otherwise reach
  • The whole run (fund chip included) goes to 11px with 4px of vertical padding, which takes the tap target from 13px to 22px tall without widening the row or moving anything on desktop

INVESTIGATION

What Donorbox will and will not prefill

Symptom

The donation links looked like they populated nothing at all.

Root cause

  • The live redirect is still eating the query string. curl -sI 'https://donate.cityedit.org/?utm_source=cityedit' returns a Location with no query today — the $is_args$args fix is committed but ships with the app image, and prod has not been deployed since. Nothing reaches Donorbox to prefill
  • The comment field genuinely cannot be prefilled. Probed against the live embed one parameter at a time: comment, donation[comment], message, note and designation all come back with the field untouched
  • What DOES prefill, verified the same way: first_name, email, amount — and the five UTM parameters, which land server-side in donation[utm_params_attributes][…] and ride onto the donation record

What changed

  • No code change: the design already uses the only channel Donorbox honours. The message rides utm_content and the deep link rides utm_term, and both are stamped into the record
  • The blocker is a deploy, not a bug — after the image ships, the same curl should return a Location that carries the query
  • Designations are not a way around it: they are a fixed list configured in the Donorbox dashboard, so they cannot name one of thousands of proposals

    Verification

    What was run

    • The z-index theory was disproved before anything was changed: a probe copy of the tooltip painted in magenta sits fully on top of the Clear button. The fix is a colour change, not a stacking change.
    • Mobile was measured rather than assumed, twice over — once by deep link and once by a real touchscreen.tap on a pin at 390×844 with hasTouch. Both open the interactive card, both resolve sources, both render the anchor.

    • Full client suite green — 409 passed, 1 skipped — and npx tsc -b clean.
    • Seen in the app: the row reads ◆ Add bus lane [$] [a] 72/72 [−0│1│+1], and the inverted Feedback tooltip is legible sitting directly over Cast/Clear.

    • Open http://localhost:3000/m/nyc-proposals, click a proposal — expect a small accent [$] right after the vote-type name, before any [a] markers, and no row at the foot of the card.

    • Hover a nav-rail icon (Blog / About / Feedback) and confirm the label is now a dark inverted chip that reads clearly over Cast/Clear.
    • Hover Donate at a wide window and confirm NO tooltip appears (its label is already showing); narrow the window under 1080px and confirm the label hides and the tooltip returns.
    • On a phone (or a touch-emulated window), open a proposal on nyc-proposals and confirm the [a] markers are legible now rather than ghost-faint.
