Groundwork for launching in Washington, D.C. and Philadelphia. Backend · config

1 · Register Philadelphia as a city

Context

We want to launch in D.C. and Philadelphia. D.C. was already wired into the city registry; Philadelphia was entirely absent, so it couldn’t be selected when proposing a map, OSRM didn’t route it, and no graph existed for it.

How it works

  • A city in City Edit is data-driven from server/cities.py (bbox + center + zooms + the source PBF + the OSRM service). The client city dropdown auto-populates from /api/cities, so adding a city is purely a backend/data step — no client changes.
  • Two collaborating definitions must agree on the bbox: cities.py (south,west,north,east) drives the votable walk-graph build and the map view, while osrm/build-merged.sh (west,south,east,north for osmium) clips the city into the single merged OSRM extract that serves every city from one instance.

What changed

  • Added Philadelphia to CITIES in server/cities.py — bbox (39.867, -75.280, 40.138, -74.956) enclosing the elongated NE–SW city limits (Navy Yard up to Somerton), center on the bbox midpoint so the map opens centered, zooms matching the other mid-size cities, the bbbike Philadelphia PBF, and osrm_service="osrm-philly".
  • Added the matching philly line to osrm/build-merged.sh (osmium west,south,east,north order) with the bbbike primary + geofabrik pennsylvania-latest fallback URL, so the next merged-OSRM build routes Philadelphia.
  • Built the Philadelphia walk graph locally with refresh_osm.py --city philly --force → osm_data/philly/walk_graph.pkl (504,998 nodes / 1,177,436 edges, 107 MB — between SF and Chicago in size).
  • Derived GraphRegistry(max_loaded=…) from len(CITIES) instead of the hard-coded 4, so the resident-graph budget tracks the registry automatically and never silently under-provisions when the next city is added.

Files touched

  • server/cities.py — add the philly City to CITIES
  • osrm/build-merged.sh — add the philly clip line (+ refresh the stale city-list comment)
  • server/app.py — max_loaded = len(CITIES) + len(STATION_NETWORKS) (was 4 + …)
Backend · seed data

2 · Make D.C. and Philly reachable out-of-the-box

Context

Registering a city only makes it selectable in Propose-a-Map. A city has no actual maps until a maps row exists, so D.C. and Philly had nowhere to land — you couldn’t open /m/<slug> for either.

How it works

  • Maps are DB rows. seed_presets() runs at startup (idempotent upsert) and seeds the canonical preset vote-type lists plus the preset maps from server/presets.py PRESET_MAPS — which until now held only the three NYC maps (Bikes / Trees / Walkways).

What changed

  • Added six preset maps to PRESET_MAPS — dc-bikes / dc-trees / dc-walkways and philly-bikes / philly-trees / philly-walkways — reusing the existing bikes / trees / walkways vote-type lists, for parity with NYC.
  • Launched subdomain-less (subdomain: None): the NYC presets keep their vanity bikepaths./trees./walkways. hosts, but the new cities are reached at /m/<slug> until DNS/TLS is added — the subdomain column is nullable and the seed upsert handles None cleanly.
  • Refreshed the stale “Preset NYC maps” comment to describe the general case.

Files touched

  • server/presets.py — six dc-*/philly-* PRESET_MAPS entries (+ comment)
Verification

What was run

  • python -c 'import cities, presets' — both import; CITIES is ['nyc','sf','chicago','dc','philly']; every PRESET_MAPS entry’s city_id and list_key resolves.
  • bash -n osrm/build-merged.sh — syntax clean.
  • refresh_osm.py --city philly --force — built osm_data/philly/walk_graph.pkl (504,998 nodes / 1,177,436 edges).
  • Booted host Flask and hit GET /api/cities — returns all five cities including dc and philly with correct bounds/center/tilesPath.
For you

Manual checklist

  • Bring up local Postgres (Docker daemon was down this session: docker compose up -d postgres), restart Flask, and confirm the boot log shows seed_presets succeed (no “Failed to seed presets”).
  • Open http://localhost:3000/m/philly-walkways and /m/dc-walkways — the map should center on the right city and the votable street network should render.
  • Curl localhost:5001/api/graph-votes?map=philly-walkways&mode=walkways and confirm it returns vote arrays sized to the Philly topology (no length mismatch).
  • Cast a vote on a Philly street and confirm it persists + paints (exercises OSRM node-id → edge mapping for the new city).
  • For prod: run gcloud builds submit so the merged OSRM image picks up Philadelphia, then let the boot warmup build the philly graph on-demand (see the resnap-on-deploy runbook).
  • Decide whether D.C./Philly want vanity subdomains; if so, add DNS/TLS and set the subdomain via the admin endpoint.
