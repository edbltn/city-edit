Top-proposal rework — route/point kinds end-to-end, one pin per block, corridors earn their length

2026-07-08 · branch fix/unify-voting
1 2 3 VerificationChecklistFull diff

Top proposals now respect what a vote type IS. Every vote type carries a route/point kind end-to-end — declared where it's authored, recorded by the cast that creates a free-text suggestion, stored in vote_types.point_type, served in the map config, and repaired on startup for legacy rows — so route-flavored types (“Add bike greenway”) can no longer masquerade as square point pins. Point pins additionally obey the block grain (one pin per street block, across all types) and same-type pins spread to 600 m. Route corridors get a support-scaled length budget (600 + 150·√score, ≤ 2.5 km): a peeled path is trimmed to its hottest contiguous stretch, so a chain of stray net-1 edges can't stretch a corridor across the borough.

Data model · vote-type kinds

1 · Every vote type now carries a route/point kind — recorded, served, repaired

Symptom

On NYC Bikes, ROUTE-flavored vote types (“Add bike greenway”, “Add bike lane”) showed up as square POINT top-proposal pins. Presets always declared a pointType, but the flag died at the config boundary: the global vote_types registry (which backs free-text suggestions and the searched custom types) never stored it, the cast that creates a suggestion never sent it, and the proposal selectors never looked at it.

Root cause

  • Four half-unified code paths: preset lists carried pointType in JSONB; the vote_types table had only (id, label); /api/vote dropped the kind on the floor; searchVoteTypes served bare label strings.

What changed

  • vote_types.point_type column ('route' | 'point' | NULL). get_or_create_vote_type_id(label, point_type) stamps NEW rows and fills NULLs (COALESCE — an existing kind is never overwritten by a later cast).
  • seed_presets() force-stamps preset labels (presets are authoritative — this is the startup repair for mis-flagged/legacy preset rows like “Add bike greenway”).
  • NEW backfill_vote_type_kinds() (runs on every startup): fills NULL rows by label match against every authored set — preset lists, promoted community lists, and each map's inline custom_vote_types. Local run: 50 rows stamped, 4 true free-text legacy suggestions remain NULL (unknown kind ⇒ eligible for both families, never hidden).
  • /api/vote accepts point_type; the client sends the selection's kind (castVotes({pointType}) from RouteContext) — the creating cast is the only witness of what a free-text suggestion was suggested as.
  • searchVoteTypes upgraded from string[] to {label, pointType}[]; map creation 400s on custom vote types without a valid pointType and registers the authored kinds immediately.
  • NEW client resolver pointTypeForLabel(label, voteTypes, searchVoteTypes) — mirrors iconForLabel's precedence (map's own list → searched customs → preset themes → null). The selector's searched suggestions are now kind-filtered too (a route-kind custom type no longer offers itself for a point selection).

PBTP · selection

2 · Point pins: point-kind only, one per block, same-type pins 600 m apart

Symptom

Two (or more) square pins could stack on a single street block when their vote types differed, same-type pins could sit one avenue block apart (300 m), and route-kind types competed for point pins at all.

Root cause

  • selectTopProposals had no notion of kind, no block awareness (only exact-edge dedupe), and a single 300 m same-type radius.

What changed

  • Step 1 filter: computeVoteTypeWinners(…, kindOf) skips ROUTE-kind labels — their support surfaces as RBTP diamonds instead. Unknown-kind labels stay eligible. Station networks pass no resolver (every vote there is a point).
  • NEW step 3 dedupeWinnersByBlock: at most ONE pin per street block ACROSS all vote types (strongest wins, salted tiebreak). Uses blockKeyOf, so maps without block artifacts degrade to per-edge singleton keys — no behavior change there.
  • Same-type spacing raised 300 → 600 m (TOP_PROPOSAL_MIN_SPACING_M): identical pins carry zero information nearby, while different-type pins only collapse when they share a block — the cross-type grain is deliberately finer than the same-type radius.

RBTP · corridor length

3 · Route corridors earn their length — support-scaled meter budget

Symptom

Route-based top proposals could snake for miles: greedy path extension keeps going while ANY net-positive arc exists, so one seed vote plus a chain of stray net-1 edges produced an absurdly long “corridor”.

Root cause

  • No length limit anywhere in the peel pipeline — the only gates were score and edge COUNT minimums, which long paths pass trivially.

What changed

  • Each peeled path gets a meter budget that grows with support: min(2500, 600 + 150·√score) (routeLengthBudgetM). One block of votes ⇒ a short corridor; 4× the votes ⇒ 2× the earned reach.
  • NEW capPathToLengthBudget: sliding window over the path's edges keeping total length ≤ budget, returning the max-weight window — the hottest contiguous stretch survives, straggly tails drop. Deterministic ties (shorter, then earliest); a single over-budget edge (a bridge) is kept rather than trimming to nothing. Activity gates run on the TRIMMED path.
  • Point-kind vote types are skipped by the corridor extraction (opts.kindOf) — the mirror of the PBTP filter.
  • NEW edgeLengthMeters in graphTopology (equirectangular, shared helper).
  • Fixed a latent bug the window slicing exposed: greedyHeaviestPath's splice duplicated the seed node in nodes, misaligning nodes[i] ↔ edges[i]. Harmless before (only the endpoints were read), wrong anchors after trimming.
