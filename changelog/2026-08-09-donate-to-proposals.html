Donate to a proposal

2026-08-09 · branch main

A proposal can now be donated to. Its card carries one row at the foot — [$] Fund this proposal — in the same bracket-token voice as the [a][b][c] source markers and the [−│net│+] control, so a dense modal gains an action rather than a section. The link carries WHAT is being funded: Donorbox will not prefill its comment box from a URL, but it does stamp UTM parameters onto the donation record, so the message rides utm_content and a deep link back to the exact proposal rides utm_term. All of which nginx was silently dropping — a literal return 301 does not forward the query string.

THE FEATURE

One row at the foot of the card

Symptom

Donating was a single site-wide button in the topbar. You could support City Edit, but you could not support the bike lane you had just clicked on — and the proposal modal is exactly where someone has decided they care about a specific block.

Root cause

  • The proposal card is already dense: header, place, meta line, an optional column header, then one row per vote type carrying a top-proposal badge, a coverage fraction, source footnotes and a three-part vote control — plus four tool icons in the corner. A donate button competing with any of that would fight the vote controls, which are what the card is FOR
  • The card's existing language is bracket tokens: [a][b][c] for sources, [−│net│+] for votes, [×] for remove

What changed

  • A single row at the foot, under a hairline: [$] Fund this proposal — the same bracket-token voice, so it reads as part of the card rather than a pasted-in donate button
  • Quiet at rest (opacity 0.82, hairline border, the accent living on the [$] alone); the accent border and a 12% accent wash arrive on hover, at which point it is the thing being pointed at
  • It is the card's only outbound money action and the only element that ASKS for something rather than reporting it — so it gets exactly one row, and nothing else moves

ATTRIBUTION

Making the donation say what it is for

Symptom

A donate link that just opens the campaign page tells you nothing: the money arrives with no idea which proposal prompted it.

Root cause

  • donate.cityedit.org redirects to a Donorbox campaign. Donorbox does have a “leave a comment” field — donation[comment] — but it does NOT prefill it from the URL: passing ?comment=… is ignored, and that field stays donor-authored
  • It DOES prefill its UTM fields server-side. Fetching the embed with ?utm_content=X comes back with <input value="X" … name="donation[utm_params_attributes][utm_content]"> already populated, and those values are stamped onto the donation record

What changed

  • The proposal's identity rides the UTM parameters, which is the channel that actually reaches the record: utm_content is the message (“Fund: Add bus lane — Grand St & Bowery — NYC Proposals”) and utm_term is the deep link that re-selects that exact proposal on the map
  • utm_medium=proposal is what separates a proposal-funding donation from a plain topbar one, which carries no UTM at all; utm_campaign is the map slug
  • Each value is clipped at 160 chars with an ellipsis — ended legibly here rather than cut mid-word by something downstream
  • The client links to donate.cityedit.org, never to Donorbox directly, so the campaign can move without a client deploy

INFRA · WOULD HAVE SILENTLY FAILED

The redirect was dropping the whole query string

Symptom

Every parameter above would have vanished in transit. curl -sI 'https://donate.cityedit.org/?utm_source=cityedit' returns a Location with no query at all.

Root cause

  • nginx does not append the query string to a return 301 whose target is a literal URL — only to rewrites and to targets containing variables. The redirect inventory in docs/url-routing.md even recorded this, in a column reading dropped
  • Nothing would have errored. The donation page would have opened normally and every donation would simply have arrived anonymous — the failure mode is silence, which is why it is worth calling out

What changed

  • return 301 https://donorbox.org/support-spherical-harmonics$is_args$args;, with a comment at the line saying what depends on it
  • The redirect inventory row flipped from dropped to preserved — it is the stated source of truth for every redirect the system performs, so a stale row there is a trap for the next person
  • This ships with the image: until the nginx config is deployed, the fund links work but arrive stripped of their attribution

CORRECTNESS

Refusing to guess which proposal

Symptom

“Fund this proposal” has to name ONE proposal. A busy intersection card lists several vote types, and a card on an unvoted segment lists none.

Root cause

  • The card is headed by a proposal only when it has a winner — a top proposal (PBTP) for a point card, a covered corridor (RBTP) for the route-summary card. Otherwise it is a place with N proposals on it, and the header shows no label
  • Station-network maps (e-bikes) suppress the top-proposal header entirely — their pins ARE the stations — so the winner the fund row may offer has to be the same gated value the header uses, not the raw one

What changed

  • fundableProposalName: the winner if there is one; else a lone vote type; else the empty string and NO fund row — wrong is worse than absent
  • The station gate is now computed once as pinnedCardWinner and used for the header, the eyebrow and the fund row together, so they cannot disagree. The share link's ?vt deliberately keeps naming the raw winner, which is pre-existing behavior
  • Hover cards never get the row: they are pointer-events: none, so the link would render and not be clickable

BUG FOUND EN ROUTE

The source footnotes were Leaflet blue

Symptom

The new row rendered in browser-link blue instead of the card's ink. Measuring it showed the same was already true of the [a][b][c] source markers shipped on 08-01 — described in their own comment as “deliberately small and quiet”, and rendering as bright blue links.

Root cause

  • Leaflet's stylesheet carries .leaflet-container a { color: #0078A8 } — specificity 0-2-0. These cards are portaled INTO the map container, so every anchor inside them matches it
  • .graph-proposal-row-link { color: inherit } is 0-1-0 and simply loses. Nobody noticed because the card's other “link” (Street View) draws an SVG with a hardcoded fill

What changed

  • One reset above Leaflet's reach: .leaflet-container .graph-proposal-card a { color: inherit }
  • That fixes the source markers and is also what lets the fund row take the card's own ink — it expresses its rest/hover difference with opacity rather than a second color declaration that would need to win the same fight

Verification

What was run

  • Donorbox's prefill behavior was measured, not assumed: fetching the embed with ?utm_content=TESTMSG123 returns that value already set on donation[utm_params_attributes][utm_content], while ?comment=HELLOMSG appears nowhere in the response.
  • The dropped query string was confirmed against the live host, not read off the config: curl -sI 'https://donate.cityedit.org/?utm_source=cityedit&utm_content=TEST' returns a Location with no query.
  • Driven in the running app on nyc-proposals: clicking a top-proposal pin opens a TOP PROPOSAL card whose fund row's href resolves to donate.cityedit.org with utm_content=“Fund: Fix dangerous intersection — 40.75732, -73.98965 — NYC Proposals”, utm_medium=proposal, utm_campaign=nyc-proposals and a utm_term deep link carrying the vote type.
  • The route side verified the same way: selecting the 30th Avenue corridor opens TOP ROUTE PROPOSAL — Add bus lane (72 blocks) and the fund row is present there too.
  • Both negative cases seen in the app: a segment with no votes renders “No votes yet” and no fund row (checked by DOM query, rows=0 fund=false).
  • The remaining branch — several proposals on one place — is covered by unit test rather than by screenshot, which is the more durable place for it. 10 tests pass across the URL builder and the fundable-name rule.
  • The Leaflet-blue bug was measured, not eyeballed: a probe anchor with class graph-proposal-row-link inserted into a live card computes to rgb(0, 120, 168). After the fix, the [a] marker on the bus-lane row reads as grey.
  • npx tsc -b clean — Vite dev never type-checks, so this is the only thing standing between an edit and a broken client build.
  • Committed as a partial stage: another session is mid-flight in the same two files (a legend vote-type filter and a nav rail), so only this workstream's hunks were applied to the index and git diff --cached was read back line by line before committing.
For you

Manual checklist

  • Open http://localhost:3000/m/nyc-proposals and click a proposal pin — expect a [$] Fund this proposal row at the foot of the card, and an accent border when you hover it.
  • Click that row and check the Donorbox page opens in a NEW tab with your map selection still behind it.
  • On the opened donation URL, confirm the query string survives the redirect — this is the part that needs the nginx change deployed before it works in prod.
  • Click a plain street segment with no votes and confirm there is no fund row; then click a busy intersection listing several vote types and confirm there is none there either.
  • Look at a row with source footnotes ([a]) and confirm they now read as quiet grey rather than link blue.
  • Run cd client-react && npx vitest run src/utils/donateLink.test.ts — 10 tests.
  • Before trusting attribution in prod: deploy the image (the nginx conf ships with it), then re-run the curl above against donate.cityedit.org and confirm the Location now carries the query.

+// ==========================================================================
+// Per-proposal donation links
+// ==========================================================================
+// donate.cityedit.org is our donation page (an nginx 301 onto the Donorbox
+// campaign, forwarding the query string). Donorbox does NOT prefill its
+// "leave a comment" box from the URL — that field is donor-authored — but it
+// DOES stamp UTM parameters onto the donation record server-side. So that is
+// where a proposal's identity rides:
+//
+//   utm_content  the message: what is being funded, in words
+//   utm_term     the deep link back to that exact proposal on the map
+//   utm_campaign the map slug it lives on
+//
+// Every donation started from a proposal card therefore arrives naming the
+// proposal it was meant for, with a link that re-selects it.
+
+import { getCurrentMap, getMapSlug } from "../map/runtime";
+
+/** Our donation page. Keep the client pointed at the cityedit host (not the
+ *  Donorbox URL directly) so the campaign can move without a client deploy. */
+const DONATE_URL = "https://donate.cityedit.org/";
+
+/** Ceiling on each UTM value. These ride in a URL and land in a reporting
+ *  column of unspecified width, so clip long vote-type/street names here —
+ *  where we can end them legibly — rather than letting something downstream
+ *  cut them mid-word. */
+const MAX_UTM_CHARS = 160;
+
+function clip(text: string): string {
+  const trimmed = text.trim();
+  if (trimmed.length <= MAX_UTM_CHARS) return trimmed;
+  return `${trimmed.slice(0, MAX_UTM_CHARS - 1).trimEnd()}…`;
+}
+
+/**
+ * The one proposal a card may offer to fund, or "" when it names none.
+ *
+ * A card headed by a top proposal funds that proposal; a card listing exactly
+ * one vote type funds that one. Anything else is a place with several
+ * proposals on it — "fund this proposal" there would have to guess which, so
+ * the row is simply absent rather than wrong.
+ */
+export function fundableProposalName(
+  winnerLabel: string | null | undefined,
+  rows: readonly { label: string }[],
+): string {
+  if (winnerLabel) return winnerLabel;
+  return rows.length === 1 ? rows[0].label : "";
+}
+
+export interface ProposalDonationTarget {
+  /** The proposal's vote-type label — "Protected bike lane". */
+  name: string;
+  /** Where it is, in words: the card's street or intersection name. Route
+   *  cards span many blocks and have no single place, so they omit it. */
+  place?: string | null;
+  /** Deep link that re-selects this proposal on the map (see buildSelectionUrl
+   *  for points; the live URL already is one for a route selection). */
+  url: string;
+}
+
+/**
+ * Donation-page URL carrying the identity of the proposal being funded.
+ *
+ * The message is written to be read cold in the donation record — "Fund:
+ * Protected bike lane — Grand St & Bowery — NYC Proposals" — because that
+ * record is the only place it is ever read.
+ */
+export function buildProposalDonateUrl(target: ProposalDonationTarget): string {
+  const mapName = getCurrentMap()?.name ?? "";
+  const place = target.place?.trim();
+  const message = [
+    `Fund: ${target.name}`,
+    place || null,
+    mapName || null,
+  ].filter(Boolean).join(" — ");
+
+  const params = new URLSearchParams({
+    utm_source: "cityedit",
+    // Distinguishes a proposal-funding donation from a plain topbar/landing
+    // donation, which carries no UTM at all.
+    utm_medium: "proposal",
+    utm_campaign: getMapSlug() || "cityedit",
+    utm_content: clip(message),
+    utm_term: clip(target.url),
+  });
+  return `${DONATE_URL}?${params.toString()}`;
+}
