Voters and Blocks: a crooked header and counts that never landed

2026-08-09 · branch main
The captions never shared a baseline The votes cancelled their own count The coalescing rules, without a DOM VerificationChecklistFull diff

Two bugs reported off one screenshot of a prod proposal card. The header was crooked on the axis nobody had measured — VOTERS sat 3.5px above BLOCKS, because one caption is bottom-aligned to the row and the other was centred inside a 19px control mirror. And the vote columns read “‒” and stayed there: the distinct-voter request was cancelled by the very votes it was counting, so its answer was thrown away before it could reach the cache — and because nothing was cached, every retry took the cold, undebounced path for the next vote to kill in turn.

BUG 1 · HEADER

The captions never shared a baseline

Symptom

The BLOCKS and VOTERS captions still looked misaligned, months after a fix that was supposed to line them up.

Root cause

  • The earlier fix (95d81c6) was real and is already live on prod — the shipped bundle contains its minWidth: ${String(total).length}ch padding, and measured on the running card both captions sit 0.0px off their columns' centres. Horizontally there was nothing left to fix, which is why re-shipping it would have changed nothing
  • The remaining error is vertical. Measured on prod: VOTERS ink top/bottom sat 3.5px above BLOCKS. Two labels side by side in one header row that don't share a baseline read exactly like horizontal raggedness — hence "still slightly misaligned"
  • The two captions were placed by unrelated rules. BLOCKS is an ordinary flex item, so the head's align-items: flex-end bottom-aligns it to the row. VOTERS is an absolute overlay on the vote-control mirror, centred inside it — and that mirror is 19px tall because it faithfully copies the real control's metrics (11px text + 3px padding + hairline borders). Centring a 10px caption in 19px lands nowhere near where a 10px caption bottom-aligned in the row sits

What changed

  • Give the caption the same bottom edge instead of the same centre: align-items: flex-end, and a line-height that matches BLOCKS so the two line boxes are identical rather than merely adjacent
  • inset: 0 resolves against the mirror's padding box — one hairline short of the row's own bottom — so the caption anchors to bottom: calc(-1 * var(--vote-border)), reaching back out through the border
  • That border width is now a token on .graph-vote rather than a literal 1px, so the compensation can't drift away from the border it compensates
  • Phones sized the two captions differently (BLOCKS inherited the 10px data-cell rule while VOTERS was 9px). Two captions sharing a bottom edge must share a size or their baselines part again, so the head's BLOCKS rule is 9px there too

BUG 2 · COUNTS

The votes cancelled their own count

Symptom

Every vote column on the card rendered the pending figure-dash and stayed there; casting a vote didn't move it.

Root cause

  • Not the server. /api/route-votes on prod answers a full 4000-edge union in ~150ms, and it was never returning an error — a 141-, 384- and 440-block corridor all resolved correctly when asked directly
  • Not the etag/304 desync either: prod's graph-votes reports x-vote-rev equal to x-vote-rev-current, so nothing was being served rev-stale and the bounded stale-refetch never engaged
  • useRouteVoteRows refetches on refetchToken = votesVersion + graphVoteVersion. That bumps on every vote mutation and every heatmap refresh — a WS delta from any user anywhere on the map, an optimistic cast, a snapshot reconcile. So the effect re-runs constantly on a busy map
  • Its cleanup set cancelled = true, and the response handler tested that flag before writing the cache. A vote landing while the first request for a selection was open therefore discarded a reply that was still perfectly correct for the selection on screen
  • Because nothing reached the cache, the next run took the cold path again — delay = firstDelayMs, which is 0 for the route card, not the 350ms debounce — and fired immediately, for the next vote to discard in turn. A request storm that never resolves, on a card whose only fallback state is "pending"

What changed

  • The cancel flag was guarding a real invariant — one selection's rows must never land on another's card — but that invariant is about the key, not about which effect run happened to ask. So it now compares the live key and lets the answer through
  • Rows resolve through a new routeVotesCache.ts that owns the contract: an answer is keyed by the edge set, so it is cached unconditionally once it arrives, whoever asked and whether or not they re-asked
  • One request per key at a time. A caller arriving mid-flight joins the open request instead of opening a second
  • A caller that arrives mid-flight still wants FRESH rows (it only re-asked because a vote landed), so the flight is marked stale and re-issues exactly once on settle. A burst of bumps costs "this request plus one more" rather than one request per bump
  • It never rejects — a network blip resolves to whatever is cached, so it cannot strand a card either
  • The ref sync moved into an effect. It was assigned during render (a pre-existing react-hooks/refs error) and the fix now leans on that ref being current when the response lands, so it shouldn't stay a lint violation

Root cause

What changed

+function remember(key: string, rows: VoteTypeRow[]): void {
+  // Re-insert so the key counts as most recently resolved.
+  cache.delete(key);
+  cache.set(key, rows);
+  while (cache.size > ROUTE_VOTES_CACHE_MAX) {

+  }

+/**
+ * Resolve rows for `key`, fetching at most once at a time.
+ *
+ * A caller arriving while a request for the same key is open joins that
+ * request rather than opening a second one. It still wants FRESH rows though
+ * (it only re-asked because a vote landed), so the open flight is marked stale
+ * and re-issues exactly once when it settles. That collapses a storm of vote
+ * bumps into "the request now, plus one more after it" instead of one request
+ * per bump.
+ *
+ * Never rejects: a failed request resolves to whatever is cached (or null), so
+ * callers can't hang on a network blip.
+ */
+export function loadRouteVoteRows(
+  key: string,
+  fetchRows: () => Promise<VoteTypeRow[] | null>,
+): Promise<VoteTypeRow[] | null> {
+  const open = inflight.get(key);
+  if (open) {
+    open.stale = true;
+    return open.promise;
+  }
+
+  const flight: Flight = { stale: false, promise: Promise.resolve(null) };
+  // Start the request now rather than a microtask from now, so a second caller
+  // in the same tick sees an open flight and joins it instead of opening its
+  // own. The try/catch covers a fetcher that throws synchronously.
+  let started: Promise<VoteTypeRow[] | null>;
+  try {
+    started = Promise.resolve(fetchRows());
+  } catch {
+    started = Promise.resolve(null);
+  }
+  flight.promise = started
+    .catch(() => null)
+    .then((rows) => {
+      if (rows) remember(key, rows);
+      if (flight.stale) {
+        // Clear ourselves out first so the re-issue opens a fresh flight
+        // rather than joining the one that is settling.
+        if (inflight.get(key) === flight) inflight.delete(key);
+        return loadRouteVoteRows(key, fetchRows);
+      }
+      return rows ?? cache.get(key) ?? null;
+    })
+    .finally(() => {
+      // Only if we're still the current flight — the stale branch above may
+      // have already replaced us.
+      if (inflight.get(key) === flight) inflight.delete(key);
+    });
+
+  inflight.set(key, flight);
+  return flight.promise;
+}
