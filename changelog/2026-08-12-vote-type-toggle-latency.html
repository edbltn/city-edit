The vote-type toggle, measured: one second down to one frame

Toggling a vote type off in the legend took about a second to show anything, for a change that alters no votes at all. Measuring it first found two separate stalls and neither was where the code’s own comments predicted: the heat repaint was rewriting all 42,524 lit blocks’ feature-state because a filter had nudged one normalization ceiling from 93 to 80, and the pins and corridors were being reclustered from scratch through an idle callback — ~800ms of work whose result, per vote type, was identical to what was already on screen. Both are now caches keyed on a vote epoch, and the whole toggle runs synchronously in the click: heat 273ms → 29ms, proposals 1,023ms → 12ms.

MEASUREMENT

Where the second actually went

Symptom

Clicking the eye on a vote type in the legend left the map unchanged for roughly a second before its pins, corridors and heat responded.

Root cause

  • Instrumented the live app (perf/vtoggle.mjs, Playwright): the click handler itself is instant — the filter subscriber runs 0.2–1.1ms after mousedown. Everything after it is the problem.
  • Stall 1, the heat (~273ms). The synchronous work is cheap (10–14ms), but it issued 42,524 setFeatureState calls, and the MapLibre render that followed took 244–268ms before the first GL draw. The paint layer diffs by a denomKey identity; hiding a type moved the negative arm’s observed ceiling from 93 to 80, which changes every lit block’s normalized heat, which forces a removeFeatureState + full rewrite.
  • Stall 2, the proposals (~700ms more). The subscriber queued requestProposalsRecompute(true); the idle callback landed ~340ms after the click (behind stall 1’s render) and then reclustered every visible vote type: “20 corridors in 729.4ms (12 types over 12 slices)”. Total: pins and corridors settled at 1,023ms.
  • The controlled case is the one that gives it away: hiding Add bike signal phase changes 15 blocks — and repainted 42,524 of them, then spent 729ms reclustering, to do it.

What changed

  • Two of the three leads held. Feature-state was being over-written, though not by the per-sourcedata storm of the old bug — that fix is intact; this was the full-vs-diff branch. Route recomputation was on the toggle path, and did account for most of the second.
  • The third lead — that a visibility toggle should be paint-only, not a data rebuild — is exactly right, and is what the fix implements.

THE BIG ONE

A hidden type does not change the other types’ answers

Symptom

Hiding one of thirteen vote types reclustered all twelve survivors, ~800ms, to produce corridors byte-identical to the ones already on screen.

Root cause

  • createRouteProposalJob took isVisible and used it to decide which types to step. Since a filter change meant a fresh job, every visible type was reclustered from zero — even though job.step(type) reads only that type’s nets and the topology. There is no cross-type state in it.
  • selectTopProposals did the same: its O(edges) candidate scan (3.3M edges on the NYC bike map) applied isVisible inside the per-type loop, so a toggle rescanned the whole edge table to re-pick from a few dozen candidates.
  • The filter is applied BEFORE selection on purpose — hiding a type must free its slot for another type’s runner-up, not just delete a row from the finished list. That requirement is what made it look like it had to live inside the expensive part.

What changed

  • Split the scan from the selection. computeWinnerCandidates (O(edges), filter-independent) and selectTopProposalsFrom (steps 2–5, a few dozen items) with the visibility filter between them — still before selection, so the promotion semantics are unchanged.
  • Exported rankRouteProposals, the job’s assembly tail, so a caller holding cached per-type corridor arrays can re-rank a different SUBSET of them.
  • GraphLayer caches both, keyed on a vote epoch. A toggle re-ranks what it already has: “recompute: 20 corridors from cache in 0.1ms”.
  • Lazily, per type. Hidden types are never clustered, so a filtered map still recomputes faster, not slower; showing a type that was hidden at page load clusters that one type and nothing else.
  • Both equivalences are pinned by tests, in both directions: re-ranking a cached subset equals recomputing with the type hidden, and the full cached set equals the unfiltered recompute.

CORRECTNESS

Why the cache key is not the revision

Symptom

—

Root cause

  • The obvious key is lastRevRef, the server vote revision. It is wrong: the optimistic cast path (applyMyVoteChange) edits edge_vote_types in place and does NOT advance the revision — the server’s delta corrects it later. A cache keyed on the revision would serve a derivation of vote data that has already changed under it.

What changed

  • Added voteEpochRef, bumped at every mutation of the in-memory vote state: full fetch, cached load, applied WS delta, and the local optimistic cast. Both proposal caches key on it, so a cast invalidates them the moment it lands.
  • An in-flight sliced job cannot poison a newer epoch: a recompute cancels the previous job’s token before touching the cache, and a slice checks its token first.
  • publishVoteTypeSupport is dropped from the toggle path entirely — the legend’s net counts are unmasked by design, so a visibility toggle cannot move them.

THE PAINT

A filter does not get to move the scale

Symptom

Hiding a vote type rewrote every lit block’s feature-state — 42,524 writes, ~250ms of render — to change as few as fifteen blocks.

Root cause

  • makeHeatNormalization derives one log denominator per arm from the observed ceilings, and the paint layer treats that denomKey as the identity it diffs against. Correctly so: if the scale moves, every lit block’s heat moves.
  • But the ceilings are computed from the MASKED differentials, so a pure display filter perturbs them. Hiding the type that happened to hold the strongest opposition took the negative ceiling from 93 to 80 — a ~3% change in normalized heat, bought with a full citywide repaint.

What changed

  • A source === "filter" broadcast now reuses the normalization already applied instead of building a new one, so the toggle stays on the diff path.
  • It also reads better than the rescale did: the surviving proposals are measured against the same ruler as before, so what you are comparing is their support rather than a moving scale.
  • Real vote changes still renormalize exactly as before — this is scoped to the filter broadcast, which the payload already labelled.
  • Result on the heaviest toggle: full/42,524 writes → diff/6,416 writes, first GL draw 287ms → 111ms. On a typical one, 15 writes and 29ms.

THE LAST 300ms

Nothing left to defer

Symptom

Even after the caches, routing the toggle through requestIdleCallback(…, {timeout: 150}) added ~300ms of waiting to ~1ms of work.

Root cause

  • The idle deferral exists because the recompute used to be an ~800ms scan that must not land mid-gesture. Once it is a re-rank of cached arrays, the queue is pure latency — and it queued behind the heat render, which is why the first idle callback measured at t=340ms.

What changed

  • The filter subscriber now runs heat, pins and corridors synchronously, in the same tick as the click.
  • The one genuinely expensive case — showing a type never clustered this page load — still slices through idle time inside recomputeRouteProposals, so the sync call stays cheap there too.

For you

Manual checklist

  • Open http://localhost:3000/m/nyc-bikes, open the Proposal dropdown, and click the eye next to Improve bike lane — the corridors and pins for that type should go in the same beat as the click, not after a pause.
  • Toggle it back on and confirm the same corridors return in the same order — the cached re-rank has to be identical to the recompute, not merely similar.
  • Toggle a type with no votes (Add bike counter): nothing at all should visibly change, and it should cost nothing.
  • Watch the heat while toggling the busiest type: the rest of the map should keep its brightness rather than re-shading — that is the scale-pinning change, and it is the one visible behaviour difference.
  • Cast a vote, then immediately toggle a type — the corridors should reflect the new vote, not a pre-cast cache. (This is what the vote epoch is for; the optimistic cast does not advance the server revision.)
  • Reload with a type hidden, then show it: that one type is clustered on demand, so expect a short pause there specifically. Everything else stays instant.
  • In a debug tab (?tab=vt), watch the console for [proposals] recompute: N corridors from cache in 0.1ms on each toggle and [blocks] heat apply (diff): … — a line reading (full) after a toggle means the scale pinning is not holding.
