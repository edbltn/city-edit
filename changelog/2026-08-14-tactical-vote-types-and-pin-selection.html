Three ways a map lied about itself

2026-08-14 · branch main
The vote types that never left Five slots, one neighbourhood What a route analog actually costs Seeing the candidates, not just the winners VerificationChecklistFull diff

Three complaints about nyc-tactical, and in all three the map was telling the truth about state that was itself wrong. Vote types "came back" that had never been removed from prod at all — row xmin proves the row was untouched, so the earlier edit went to another database and said "✓" anyway. Two tied proposals 12 km apart drew one pin, not because the spacing radius suppressed one, but because all five of the type's candidate slots had already been spent inside a 228 m stretch of the other — the cap is applied before the spacing pass and breaks ties by edge index, which is graph build order. And giving those votes a route analog turned out to cost five changes rather than one, the binding one being a corridor support floor that would have silently discarded the smaller of the two casts.

ISSUE 1 · THE REGISTRY

The vote types that never left

Symptom

Seven vote types were removed from nyc-tactical's picker earlier in the day. They were still there afterwards, and the obvious reading was that something had put them back.

Root cause

  • Nothing put them back. Prod's row was never written. track_commit_timestamp is off, but row xmin still orders writes: the map row's last write is 3,417,135, while the oldest vote cast on that map is 3,562,860 and the current txid is 3,578,411. The row's last write predates the map's own oldest vote by ~146,000 transactions
  • Both suspects clear on inspection, not by elimination. Only two writers of custom_vote_types exist — this CLI and create_map, a plain INSERT behind slug_available() (a repeat POST returns 409). The weekly DOT import targets MAP_SLUG=nyc-proposals and writes only the vote_sources registry
  • seed_presets() does rewrite rows wholesale on every Flask startup — visible in the same xmin data as one contiguous block (vote_type_lists 3567783-85, the nine preset maps 3567786-94). But it touches only PRESET_MAPS slugs and never writes custom_vote_types. nyc-tactical is not a preset
  • So the edit landed somewhere that was not prod — and every path there ends in the same cheerful checkmark. load_dotenv() at import silently supplies server/.env's LOCAL url whenever the caller forgets an inline prod one; both databases hold maps with the same slugs; an UPDATE matching zero rows is not a SQL error

What changed

  • The CLI names its database. · database: host:port/name prints before every command, so a wrong-target edit is visible in the transcript instead of indistinguishable from a right one
  • And proves the write landed. It fails when the UPDATE matches anything but one row, then reads the row back and refuses to claim a write it cannot see. It cannot know which database is the right one — that is the operator's call — but it can stop lying about which one it used
  • A second, real return path is now named. The dropdown IS the legend (buildVoteTypeLegend): it lists a label the map authored or one that carries votes. Removing a voted label takes it out of custom_vote_types and it returns immediately, sourced from the votes instead. remove now warns with the vote count when that will happen
  • The seven removals then ran against prod, each read back: 24 → 17 types, and none of the seven had a single vote, so nothing re-admits them

ISSUE 3 · PIN SELECTION

Five slots, one neighbourhood

Symptom

Two litter casts on nyc-tactical, 12 km apart and tied at one supporter each, drew a single pin between them — well past the 1 km spacing radius that was supposed to be the only thing separating them.

Root cause

  • The spacing pass was not the culprit. It never saw the second cast.
  • TOP_PROPOSALS_PER_TYPE truncates a type's candidate blocks BEFORE the spacing pass, and the truncation is a plain slice() over a list whose tiebreak is the edge index — which is graph BUILD order, so on any map where blocks tie it is effectively a geographic sort
  • Ties are the normal state of a young map: every proposal has exactly one supporter. Here, 39 blocks all at net 1
  • Run against live prod, all five slots landed inside a 228 m stretch of one cast (edges 585714–585767). Step 4 then correctly collapsed those five near-identical pins to one. The other neighbourhood's twelve blocks were never candidates, so they had nothing to lose with
  • Which cast won was decided by nothing more meaningful than 66 of its edges being numbered below the other's lowest — the same data replayed on a locally-built graph, where the numbering interleaves, produced two pins and hid the bug entirely

What changed

  • takeSpacedBlocks fills a type's slots strongest-first while skipping any block within TOP_PROPOSAL_MIN_SPACING_M of one already taken, so perTypeLimit counts distinct places rather than distinct rows
  • It uses the SAME radius as step 4, so it can only pre-empt suppressions that pass would have made anyway — it cannot admit a pin the finished list would reject. Cost is O(blocks × slots), not O(blocks²): the scan stops at five kept
  • Suppression radius halved, 1000 → 500 m. At a walkable grain a kilometre suppressed neighbouring streets with nothing to do with each other; 500 m is ~6 avenue blocks or ~2 crosstown ones
  • Same prod data, after the fix: 4 candidates 12.4 km apart, 4 winners, both neighbourhoods represented
  • The fixture whose edges all join one node pair now asks for spacing 0 — with a single midpoint between them, spacing would collapse the block-grain cases those tests are actually about. Three new cases cover the spacing itself, one of which reproduces the old loss by turning step-1 spacing back off

ISSUE 2 · THE CONVERSION

What a route analog actually costs

Symptom

"Run a litter pickup here" is point-only and needed a route analog, with the existing votes moved onto it so they could become corridors. The stated trap was that route-kind labels must sit on corridors, not on isolated points.

Root cause

  • The geometry was never the problem. Both casts are already corridor-shaped: 130 edges over 1,077 m spanning 15 blocks, and 59 edges over 874 m spanning 23 blocks. Both clear MIN_ROUTE_EDGES=2 and MIN_ROUTE_BLOCKS=5 comfortably
  • The binding constraint is the corridor support floor. A path's score is the sum of its edge nets, and every edge here has net 1, so a cast's score is capped at its edge count. With no map override, minRouteScore = ROUTE_PROPOSAL_MIN_NET + 1 = 101: the 128-edge cast squeaks through and the 59-edge one cannot
  • Measured rather than assumed. All 189 prod votes were replayed onto the local NYC graph (resnapped by lat/lon, 0 unsnapped — and it reproduced prod's 39 voted blocks exactly), then run through both real pipelines. At floor 101: 1 corridor, and the second cast vanishes entirely. At floor 1: 2 corridors
  • A vote also lives in three Redis layers, and rebuild_redis_for_map rebuilt only one of them while deleting the revision key — sending it backwards, below what connected clients already hold

What changed

  • The conversion needed five things, not one: the authored route entry, a registry row with point_type='route' (the CLI does not mint one), the 189 re-pointed rows, top_proposal_min_net = 0 on the map, and all three Redis layers rebuilt
  • rebuild_redis_for_map now rebuilds every layer a vote lives in. bd:/bagg: are keyed by vote type as well as by block, so re-pointing votes left their old slots standing and stale pins kept rendering from state nothing would ever correct
  • They are keyed by edge→block, which lives on the graph and is not available there, so they are CLEARED rather than replayed — /api/graph-votes rebuilds them from Postgres on the next request against the graph that instance actually has
  • The revision is INCR'd, never SET. Atomic, collision-free against a concurrent caster, and always above whatever was there. This also fixes the graph_reload path, where _resnap_city_maps reset the revision on every graph rebuild

THE INSTRUMENT

Seeing the candidates, not just the winners

Symptom

Every surface the app offers shows the FINISHED proposal list. A candidate that was never in the running looks exactly like one that lost.

Root cause

  • The pin bug is invisible from the outside: one pin where two were expected is equally consistent with "spacing suppressed it", "its net was lower" and "it was never a candidate" — three very different faults
  • It is also environment-dependent. Replaying the same votes on a locally-built graph produced the correct two pins, because local edge numbering interleaves the two casts. Only prod's numbering triggers it

What changed

  • scripts/tacticalDiag.ts runs BOTH families for one map through the real pipelines — candidatesForGraph / selectTopProposalsFrom and createRouteProposalJob / rankRouteProposals — with exactly the options GraphLayer passes them
  • It prints the per-type candidate set BEFORE the spacing pass alongside the finished winners, plus the max separation within each type. That one line ("5 candidates, max separation 228 m") is the whole diagnosis
  • API_BASE points it at a local Flask or at prod, so a bug that only prod's graph numbering triggers can be reproduced without shipping anything
  • MIN_NET=<n> previews what a map-level topProposalMinNet override would do to both families — which is how the corridor floor was measured before touching prod, rather than after

Verification

What was run

  • The registry claim was proved, not inferred. Row xmin on the maps row (3,417,135) sits ~146,000 transactions before the oldest vote on that map (3,562,860), so the row demonstrably was not written that day — which is what rules out a rewrite and leaves a mis-targeted edit as the only explanation.
  • The pin bug was reproduced against live prod before any change: 5 candidates, max separation 228 m, 1 winner. After the fix, same prod data: 4 candidates, max separation 12,434 m, 4 winners.
  • The conversion was measured on a full replay, not predicted. All 189 prod votes resnapped onto the local NYC graph (0 unsnapped) reproduced prod's 39 voted blocks exactly; at corridor floor 101 the replay yields 1 corridor, at floor 1 it yields 2.
  • The Redis rebuild was verified end to end: rev 200 → 201 (forward, not reset), bagg 39 → 0, and then the next /api/graph-votes served the stale body once (SWR) and rebuilt 39 blocks from Postgres under the new vote type.
  • 567 client tests and 203 server tests pass, npx tsc -b is clean, and scripts/check_algorithm_docs.py reports OK 7 dossiers, 20 bound source files.
  • Prod, after the change: /api/maps/nyc-tactical returns 18 vote types with topProposalMinNet: 0; /api/graph-votes returns rev 3, 189 voted edges, 39 voted blocks, legend ['Pick up trash along here']; and the diagnostic returns 0 point proposals and 2 corridors (scores 128 and 59) — exactly the replay's prediction.
  • Rendered in the browser on prod: the Morningside Park cast draws as a corridor labelled PICK UP TRASH ALONG HERE +128, the Wyckoff Avenue cast as +59, and the picker shows 18/18 — 11 point, 7 route — with no chalk entries and the new type filed under ROUTE PROPOSALS at net 39.
  • Backup taken before any write (~/city-edit-prod-backups/20260814T200100Z/): 27 MB pg_dump plus targeted snapshots of the 189 vote rows, the 24-entry vote-type JSON, and the ev:/bagg:/vote_rev Redis state, so this is reversible without a full restore.
  • One transient worth knowing: the legend briefly rendered #44128. Prod's serving revision was built 2026-08-13, a day before resolve_vote_type gained DB read-through, so an instance whose startup cache predates an out-of-band vote type cannot resolve it.
