The heatmap blocks that vanished when you zoomed out

2026-08-09 · branch main
The heat is complete at z14, and mostly gone at z12 Stop paying for attributes nobody reads, then stop dropping The bake now checks itself VerificationChecklistFull diff

Three fixes to Top Proposals: a pin now takes real support (>100 net votes, both point and route families); every modal badges the vote types that are CURRENT top proposals for what it shows (square = point, diamond = route fully inside the selection); and route corridors are now grown ROUTING-CONSISTENTLY — an extension either keeps the segment a shortest path or pins a ghost waypoint (max 3), and the whole waypoint chain lands in the URL, so a shared top-proposal link keeps routing into its corridor long after the proposal itself has churned away.

THE BUG

The heat is complete at z14, and mostly gone at z12

Symptom

Zooming out past the default view drops most of the heatmap blocks — and it drops them worst over the densest part of the city, so Manhattan empties out while Brooklyn and Queens stay lit.

Root cause

  • blocks.pmtiles is not a decorative basemap layer: it is the heatmap's geometry, addressed by feature id. --use-attribute-for-id=block_id makes block_id the native id, and the client paints purely from setFeatureState on that id — it reads no tile property at all. A block that is not in the tile therefore cannot be lit, no matter how many votes it has
  • tippecanoe fits each tile into a byte budget (500KB by default) by dropping features in proportion to density (--drop-densest-as-needed). That is the right instinct for labels and POIs and exactly the wrong one here: density is a proxy for where the votes are
  • The archive is complete from z13 up, so the default landing view (leaflet 14 = MapLibre z13) is perfect and the defect is invisible. It appears only when you zoom OUT: leaflet 13 → 61% of NYC's blocks, leaflet 12 → 24%, leaflet 11 → 17%
  • It is also non-monotonic, which is what makes it read as "some zoom levels": dropping is decided per TILE, so whether a given zoom looks fine depends on how the city falls across that zoom's tile grid. On SF the run went 56% at z9, 46% at z10, 39% at z11, then back to 70% at z12
  • Nothing ever counted. The bake reported blocks built, not blocks that survived into tiles, so a 15-point drop or an 80-point drop looked identical from the terminal

What changed

  • Measured, not inferred: for one 1.1km box in Midtown the app renders 586 blocks / 95 of them lit at leaflet 17, and 135 blocks / 8 lit at leaflet 12 — 92% of the heat gone, on a fresh load at that zoom
  • The "fresh load" part matters: MapLibre keeps already-loaded tiles when you zoom out, so zooming out inside a session looks fine and hides the bug. Reproducing it needs the map to OPEN at the wide zoom (a scratch ?dbgzoom= hook), not to arrive there by zooming
  • Ruled out at the top end: at leaflet 19/20/21 the source overzooms its z16 tiles and every block is still there, so nothing is wrong above the default view

THE FIX

Stop paying for attributes nobody reads, then stop dropping

Symptom

—

Root cause

  • The tiles carried seven display attributes per block — seg_id, road_class, road_name, area_m2, n_edges, n_nodes, node_id. A grep of the client for any of them finds only unrelated vote-payload fields: nothing reads a block tile property. At 15,000 features in a wide tile they were most of its bytes
  • --no-tiny-polygon-reduction is the second half: below ~z11 tippecanoe accumulates sub-pixel polygons into one shared "tiny polygon" square, which silently merges their ids away. That is a density-preserving trick for cartography and an id-destroying one for a layer keyed by id
  • --coalesce-densest-as-needed was in the command and had never fired. With the attributes stripped every feature looks identical to it, and coalescing merges same-attribute features while keeping ONE id — it would have gone from dormant to devastating

What changed

  • --include=block_id — the only attribute that survives, and --use-attribute-for-id then moves it onto the native id and out of properties (verified: sample feature comes back as id 18871, props {})
  • --no-tiny-polygon-reduction — sub-pixel blocks stay themselves
  • --maximum-tile-bytes=1500000 — up from the 500KB default. Only the handful of city-wide z9–z11 tiles come near it; z12 and up stay under 450KB, so this changes nothing at any zoom people work at
  • Dropped --coalesce-densest-as-needed; kept --drop-densest-as-needed as the last-resort backstop so a pathological tile still cannot blow up unboundedly
  • -Z8 — the client never asks below it (leaflet zoom = MapLibre zoom + 1, and the lowest min_zoom in cities.py is 10, so ml z9 is the widest tile ever fetched). That drops ~3MB of world-view tiles per city that nothing has ever requested
  • Geometry at working zooms is untouched: comparing a z13 and a z14 tile before/after, the mean area delta per block is 0.00 tile units and the vertex count moves by +0.12 — the new archive only ADDS features

REGRESSION GATE

The bake now checks itself

Symptom

This shipped for months because a thinned low zoom looks exactly like a healthy one from the build log.

Root cause

  • The failure is quiet by construction: tippecanoe reports what it wrote, the server serves whatever is in the archive, and the client happily paints the subset it is given
  • The one number that would have caught it — distinct feature ids per zoom vs blocks built — was never computed anywhere

What changed

  • verify_blocks_tiles.py scans the fresh archive and prints distinct blocks per zoom against the count the builder just wrote, labelling every row with BOTH the MapLibre zoom and the Leaflet zoom you would reproduce it at
  • It fails the bake if any zoom from z10 up carries under 95% of the blocks. The widest zoom (below z10) is reported but tolerated — a whole metro at 1px genuinely cannot fit inside one tile budget, and thinning there is cosmetic
  • It runs on the TEMP archive, before the atomic rename, so a bad bake can never replace a good one
  • Only z8–z13 are decoded: the high zooms are never in doubt (their tiles are a fraction of the budget) and reading NYC's 4,600 maxzoom tiles would add minutes for no information
  • Pointed at the CURRENT shipped NYC archive it exits 1 and names z10, z11, z12 — i.e. it reproduces the bug report from the artifact alone

Verification

What was run

  • Reproduced in the running app, not just in the archive: a fixed 1.1km box in Midtown holds 95 lit blocks at leaflet 17 and 8 at leaflet 12 on a fresh load — with the same feature-state applied in both cases (6,296 lit blocks map-wide either way).
  • The reproduction needed care: MapLibre retains loaded tiles across a zoom-out, so the naive test (zoom in, then out, then count) reports the healthy high-zoom set at every zoom and shows nothing wrong. The map has to OPEN at the wide zoom.
  • Two dev servers ran side by side — a concurrent session was hot-reloading GraphLayer.tsx into a crash loop, so the measurements were taken against an isolated Vite on :3100 from a clean HEAD worktree (with its own hardlinked node_modules, so its dep-optimize cache could not thrash the other session's).
  • Re-baked NYC for real and measured the same box again on a fresh load at leaflet 12: 585 blocks / 95 lit, i.e. identical to the leaflet-17 reference (586 / 95). Before the change it was 135 / 8.
  • Archive-level before/after on the shipped NYC block set (287,352 blocks): z10 17.3% → 99.9%, z11 23.7% → 100.0%, z12 60.9% → 100.0%, z13+ 100% throughout.
  • The re-bake is provably the SAME block set, not a new one: the builder was re-run into scratch directories and reproduced the shipped mapping exactly — same topology_etag, same n_blocks (287,352), same blocks_sha256, and an edge→block array that compares equal element for element. So only the tiles changed; no vote, no edge id and no mapping moved.
  • Independently confirmed on a second city (SF, where the shipped archive is baked from the geojson on disk): z10 45.6% → 99.9%, z11 38.6% → 100%, z12 69.8% → 100%.
  • The archive got smaller, not bigger: NYC 23.9MB → 18.8MB of tile bytes despite carrying every block at every served zoom. The dead attributes cost more than the recovered geometry.
  • Largest single tile is now 1,389KB (z10) and 450KB at z12 — the raised ceiling binds only on the city-wide tiles it was raised for.
  • Ruled out the top of the range explicitly: at leaflet 19/20/21 the source cache holds z16 tiles overzoomed and every block renders, so the defect is entirely below the default view.
  • The high-zoom geometry is bit-for-bit comparable: mean per-block area delta 0.00 tile units at z13 and −0.03 at z14 (extent 4096), i.e. the shapes users click did not move.
For you

Manual checklist

  • Open http://localhost:3000/m/nyc-walkways and zoom OUT to leaflet 12–13 (two or three steps below the default). Manhattan should stay as densely lit as Brooklyn — before this change it went nearly black while the outer boroughs kept their heat.
  • Reload AT the wide zoom rather than zooming out to it, or MapLibre's retained tiles will show you the healthy high-zoom set and hide any regression.
  • Re-run a bake and read its last block: ./server/streetscape_blocks/build_city_blocks.sh <city> now ends with a per-zoom table and [verify] OK; it should refuse to install an archive that drops blocks at z10+.
  • Point the verifier at an old archive to see the failure mode it guards: server/env/bin/python server/streetscape_blocks/verify_blocks_tiles.py <old>.pmtiles --expect <n_blocks> exits 1 and names z10/z11/z12.
  • Click a block at leaflet 17–18 and confirm selection and the proposal card still work — the feature ids are unchanged, so this should be indistinguishable, and it is the thing that would break if they were not.
  • Before shipping to prod, remember the artifacts route: blocks ride the cloudbuild.blocks-overlay.yaml path and must be baked against the SERVING image's graphs, not local ones, or the edge ids shift.

+#!/usr/bin/env python3
+"""Post-bake gate: did every block survive into the low-zoom tiles?
+
+blocks.pmtiles is not a decorative basemap layer — it is the heatmap's
+geometry, addressed by feature id. A block tippecanoe thins out of a tile
+cannot be lit by `setFeatureState`, and tippecanoe thins in proportion to
+DENSITY, so the blocks it drops are the downtown ones, i.e. exactly where the
+votes are. That failure is invisible at the default view (the tiles are
+complete from z13 up) and only shows when you zoom out to the city, which is
+how it survived unnoticed: Manhattan was losing 45% of its blocks at z12 and
+83% at z11.
+
+So the bake now checks itself. Distinct feature ids per zoom, compared with
+the block count the builder just wrote, over the zooms the client actually
+requests (leaflet zoom = MapLibre zoom + 1, and the lowest min_zoom in
+cities.py is 10, so ml z9 is the widest tile ever fetched). The widest zoom
+gets a warning rather than a failure — a whole metro at 1px cannot hold every
+block inside one tile budget, and there the thinning is cosmetic.
+
+    python verify_blocks_tiles.py <archive.pmtiles> --expect <n_blocks>
+"""
+
+import argparse
+import collections
+import gzip
+import math
+import sys
+
+import mapbox_vector_tile as mvt
+from pmtiles.reader import MmapSource, Reader, all_tiles
+
+# Zooms at or above this must be essentially complete; below it (the widest
+# view the client can reach) a shortfall is reported but tolerated.
+DEFAULT_MIN_COMPLETE_ZOOM = 10
+DEFAULT_THRESHOLD = 0.95
+
+# Scanning every zoom would decode the whole archive (minutes for NYC's 4,600
+# maxzoom tiles) to confirm what is never in doubt: the high zooms hold
+# everything, because their tiles are a fraction of the size budget. Only the
+# wide zooms can drop, so only they are read.
+MAX_SCANNED_ZOOM = 13
+
+
+def scan(path: str) -> tuple[dict[int, set], dict[int, int], dict[int, int]]:
+    """(ids, tile count, max tile bytes) per zoom, for the low zooms only."""
+    src = MmapSource(open(path, "rb"))
+    ids: dict[int, set] = collections.defaultdict(set)
+    tiles: collections.Counter = collections.Counter()
+    biggest: collections.Counter = collections.Counter()
+    for (z, x, y), data in all_tiles(src):
+        if z > MAX_SCANNED_ZOOM or not data:
+            continue
+        tiles[z] += 1
+        biggest[z] = max(biggest[z], len(data))
+        raw = gzip.decompress(data) if data[:2] == b"\x1f\x8b" else data
+        for layer in mvt.decode(raw).values():
+            for feature in layer["features"]:
+                ids[z].add(feature.get("id"))
+    return ids, tiles, biggest
+
+
+def main() -> int:
+    ap = argparse.ArgumentParser()
+    ap.add_argument("archive")
+    ap.add_argument("--expect", type=int, required=True,
+                    help="block count from the builder (edge_blocks_<net>.json n_blocks)")
+    ap.add_argument("--min-complete-zoom", type=int, default=DEFAULT_MIN_COMPLETE_ZOOM)
+    ap.add_argument("--threshold", type=float, default=DEFAULT_THRESHOLD)
+    args = ap.parse_args()
+
+    header = Reader(MmapSource(open(args.archive, "rb"))).header()
+    ids, tiles, biggest = scan(args.archive)
+
+    print(f"[verify] {args.archive} zooms {header['min_zoom']}-{header['max_zoom']}, "
+          f"{args.expect} blocks expected")
+    failures = []
+    for z in sorted(ids):
+        share = len(ids[z]) / args.expect if args.expect else 0.0
+        # Leaflet is one zoom ahead of MapLibre (256 vs 512px tiles), and every
+        # zoom in the UI, the URL and cities.py is a Leaflet zoom — print both
+        # so a shortfall here names the zoom you would reproduce it at.
+        line = (f"[verify]   z{z:<2d} (leaflet {z + 1:<2d}): {len(ids[z]):7d} blocks "
+                f"({share * 100:5.1f}%)  {tiles[z]:5d} tiles, largest "
+                f"{math.ceil(biggest[z] / 1024)}KB")
+        if share >= args.threshold:
+            print(line)
+        elif z < args.min_complete_zoom:
+            print(f"{line}  — thinned (widest view, tolerated)")
+        else:
+            print(f"{line}  — TOO FEW")
+            failures.append(z)
+
+    if failures:
+        sys.stdout.flush()  # or the stderr verdict lands above its own table
+        zooms = ", ".join(f"z{z}" for z in failures)
+        print(f"[verify] FAILED: {zooms} dropped more than "
+              f"{(1 - args.threshold) * 100:.0f}% of the blocks. The heatmap will "
+              f"have holes there — see the tippecanoe flags in build_city_blocks.sh "
+              f"(--include=block_id, --no-tiny-polygon-reduction, "
+              f"--maximum-tile-bytes).", file=sys.stderr)
+        return 1
+    print("[verify] OK — every served zoom carries the block set")
+    return 0
+
+
+if __name__ == "__main__":
+    sys.exit(main())
