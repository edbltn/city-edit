Quiet the console: bursts cost two lines, not two hundred

2026-08-19 · branch main

The debug console had grown past the point where anyone reads it: a named ?tab= turns on all eleven channels, and four of the lines behind them fire per hover, per delta or per apply — a mouse sweep across a few blocks printed 33 [blocks] select lines. Rather than delete the evidence, those streams now go through one coalescing logger: first line, then “+39 more in 1950ms” when the burst goes quiet. A normal visitor's console is now completely silent, three lines that were reporting real trouble at debug level were promoted to warnings, and ?debug=<channels> arrived for when all-on is still too much.

THE FIX

One logger for anything that can fire in a flurry

Symptom

A hover sweep across a downtown block face printed 33 [blocks] select: [id] lines; every no-op heat diff announced 0 writes; every incoming vote delta and every proposal-label re-broadcast took a line of its own.

Root cause

  • These are not badly-written log lines — each one is the right thing to know once. The problem is their rate: block selection is dispatched on every hover target change, heat applies on every delta and every legend toggle, label broadcasts again each time a corridor's voter count lands
  • Deleting them was the obvious move and the wrong one: selection and heat are exactly what you are reading the console for when selection or heat is broken

What changed

  • dburst(channel, key, message) prints the first event of a burst, counts the rest, and emits ONE summary when the stream goes quiet (400–800ms of silence): [blocks] +14 more in 5081ms — last: select: [259586]
  • A stream that never goes quiet still reports every 5s — a runaway loop has to be visible, not hidden behind its own first line
  • key keeps independent streams in one channel apart, so blocks/select and blocks/heat summarise separately rather than interleaving into nonsense
  • Applied to the four flurry-prone streams: block selection (per hover), heat applies (per delta / filter toggle), vote deltas (per incoming vote), proposal-label broadcasts (per voter count landing)

NORMAL SESSIONS

A visitor with no debug flag now sees nothing at all

Symptom

A plain load of /m/nyc-walkways — no tab, no flag — printed [ws] disconnected — reconnecting in 1000ms as a warning, and then reconnected.

Root cause

  • The provider's unmount cleanup closes the socket. That close runs through the same onclose as a network drop, so our own teardown warned about itself and then scheduled a reconnect for a connection nobody wanted
  • In dev, StrictMode's throwaway first mount makes this fire on every single page load
  • The obvious fixes both fail: a ref is racy (a remount's own socket gets mistaken for the dead one) and a module-level WeakSet is worse — the dev server can hand out more than one instance of a module, which is exactly what the probe found (two module ids, marks written into one set and read from the other)

What changed

  • The mark lives on the socket object itself, so it cannot be separated from the socket it describes
  • An intentional close logs [ws] closed by teardown at debug level and returns — no warning, no reconnect
  • Result: zero app-originated console lines on a plain load. What remains is Vite's own HMR client, Chrome's React-DevTools notice, and (headless only) two WebGL driver notices

ERRORS SURVIVE

Three real problems were whispering on a channel nobody had on

Symptom

Noise reduction can quietly become silence. These went the other way — up.

Root cause

  • A route that fails to calculate clears the path and shows the user NO_ROUTE_MESSAGE; it was reporting that at dlog level, invisible unless you happened to have proposals on
  • A failed /api/visitor probe fails closed (everyone is treated as a returning visitor) and said so at debug level
  • Worst of the three: scheduleStaleVotesRefetch gave up after its last retry with a bare return. The server is still serving a snapshot behind its own revision, the heatmap is knowingly stale, and nothing anywhere said so

What changed

  • All three now go through dwarn, which prints regardless of which channels are enabled
  • The stale-snapshot give-up is new text, not a promotion — it warns exactly once (the retry counter is stepped past the ceiling) rather than on every subsequent attempt
  • dwarn/derror are pinned by test: a failure is not chatter, and no channel setting can turn one off

DEBUG TABS

?tab= keeps all eleven channels — and ?debug= arrives for when that is wrong

Symptom

Eleven channels at once was the complaint. The choice was: default a named tab to a useful subset, or make every channel quiet enough that all-on is readable.

Root cause

  • A subset default has a failure mode that is hard to recover from: you open a debug tab to find out why blocks are not lighting, see no [blocks] lines, and conclude the subsystem is dead when in fact it was never switched on
  • The whole point of a named tab is that you do not yet know which subsystem is lying to you

What changed

  • Chosen: keep all-on, and make it readable — which the burst collapsing does. A named tab's load is now 17 app lines, and the interactive streams cost two lines per burst instead of one per event
  • ?debug=<spec> overrides it per page load, and wins over both the tab default and localStorage.cityedit_debug: ?debug=cast,blocks, ?debug=*, ?debug=off (a named tab you want silent for one reload)
  • The banner line now states what is actually on, so a tab is never silently narrower than you think
  • Two removed redundancies while here: MapLibre re-logged the label count GraphLayer had just logged, and every proposals recompute dumped all twenty corridors (now the top 5 and “…+15”)

Verification

What was run

  • Measured, not asserted — /m/nyc-walkways in headless Chromium, fresh browser context each run (no localStorage carry-over), 20s settle, every console event captured: plain 7 → 6 lines and ?tab=check 30 → 23. Both after-numbers reproduced exactly across two consecutive runs.
  • Of the 6 remaining plain-load lines, 0 are ours: 2 Vite HMR client, 1 React DevTools notice, 2 Chrome WebGL driver notices (headless only), 1 Chrome notice about the StrictMode socket we close while it is still connecting — browser-generated, not suppressible from the page.
  • Under interaction (hover sweep of 40 moves, a drag-pan, two clicks, zoom in/out) a named tab went 72 → 41 lines, with the blocks channel alone falling 37 → 11. 6 of the remaining 41 are another session's in-flight [audience] lines.
  • The teardown fix was found by probe, not by reasoning: sockets and module instances were stamped with ids, which showed the mark being written into one module instance's set and read from another's (mod hlpo vs mod vp5r). That is why the flag ended up on the socket object.
  • New unit test debugLog.test.ts (7 cases) pins the contract: a disabled channel prints nothing, a 40-event burst is one line plus one summary, a never-quiet stream still reports, separate keys stay separate, and dwarn/derror survive every channel being off. Fake timers include performance, without which the max-window flush cannot be tested at all.
  • Full suite green: 661 passed, 1 skipped. npx tsc -b clean for these files.
  • Committed hunk-by-hunk. GraphLayer.tsx and MapLibreBackground.tsx are being rewritten by another session right now, so only the hunks matching this work were staged (5/8 and 4/13); the rest of both files is still uncommitted in the working tree, untouched.
For you

Manual checklist

  • Open http://localhost:3000/m/nyc-walkways with devtools open and no debug params — expect nothing from the app: Vite's HMR lines and Chrome's own notices only.
  • Open http://localhost:3000/m/nyc-walkways?tab=check and read the first line: it names the tab and lists exactly which channels are on.
  • In that tab, sweep the mouse across a dozen blocks — expect one [blocks] select line and then a +N more in Mms summary when you stop, not one line per block.
  • Try ?tab=check&debug=cast,blocks and confirm the other nine channels stay quiet; try ?debug=off on the same named tab and confirm it goes silent without losing the [dbg:check] title tag.
  • Cast a vote in the debug tab and confirm [cast] press, [cast] server: and the block heat lines still tell the whole story of the press — the press path was deliberately left one-line-per-action.
  • Run npx vitest run src/utils/debugLog.test.ts (7 tests) if you want the burst behaviour checked without a browser.
