THE MOVE

A strip at the bottom of the screen cannot point

Symptom

Every step of the first run was one strip at the bottom of the map: "Tap the map where that stretch starts." Two of the three controls those sentences were about live in a bar at the TOP of the screen, which a first-timer has not looked at yet.

Root cause

  • The strip was a deliberate choice and the reasoning was sound as far as it went: the app has exactly ONE place it speaks from (MapNotice) and a first-run coach is not special enough to earn a second. That was right about the strip and wrong about the coach
  • Having no way to indicate a control, each step had to DESCRIBE one — and a description is the weakest possible pointer, because the reader has to find the thing before they can act on it. The instruction and its subject were as far apart as the screen allows
  • It also forced the strip to carry COPIES of the app's controls (its own address search, its own +/− pair), since a thing that cannot point has to bring the controls to the reader instead

What changed

  • Each step is a CALLOUT WITH AN ARROW TIP, hung off the real control, and the rest of the chrome greys out behind it so exactly one thing on the screen is lit
  • start → the Start field, end → the End field, cast → the −/+ pair. done keeps the strip and is unchanged: the closing line is a report rather than an instruction, and it has no control to point at
  • The coach's own control copies are gone. Pointing at the real ones means what somebody learns in the first run is the app they will actually use
  • One decision the chrome cannot make survives in the box — "It's one spot", declining an end point the flow was only GUESSING might exist because the label's kind is unknown

FOCUS

Greying everything else — and what the map counts as

Symptom

"One lit thing" is easy to say and has two traps in it: the obvious CSS for it does not work, and the map is not always part of "everything else".

Root cause

  • OPACITY ON A CONTAINER MAKES A GROUP. Fading .topbar and un-fading the Start field inside it is not expressible — nothing inside a faded group can be brought back to full. So the greying cannot be one rule on one ancestor
  • The floating chrome gives every plate a backdrop-filter, which makes each its own stacking context. Nothing rendered inside the Start plate can be drawn over anything outside it, whatever z-index it is given
  • The ladder has no rung between --z-map-card-hover (500) and --z-chrome (600), and zScale.test.ts requires 100 between named rungs, so a scrim that covers the map but not the bar cannot have a name of its own

What changed

  • The bar's controls are faded INDIVIDUALLY, each excluded from its own step by :not([data-coach=…]). One body attribute (data-coach-focus) is the entire coupling; the rules live in this flow's own stylesheet
  • The map is greyed at the cast step and NOT before it. Placing a point is a map gesture, so greying the map during start or end would grey out the very thing being asked for. By cast the points are placed and the only move left is in the bar
  • The scrim is calc(var(--z-chrome) - 1) — a VARIANT of the rung it hangs off, which is the convention globals.css documents for exactly this. It covers the map, its furniture, the bottom strips and any open proposal card; the bar stays above it and is greyed by the rules instead, which is what leaves the −/+ the single lit thing
  • Nothing is disabled. Somebody moving a point they already placed, or changing the vote type before casting, is doing something reasonable — a first run that traps them teaches that the app is a wizard. Only the MAP is actually taken away, and only once there is nothing left to do on it
  • The callout is portalled to <body> at --z-transient, the ladder's own name for a tooltip anchored to a control

GEOMETRY

Measured, never guessed — and "absent" is an answer

Symptom

There is no width at which a hard-coded position for the Start field would be right, and there are several at which the field does not exist at all.

Root cause

  • The chrome has TWO MODES. data-chrome="float" (the default) is a 6-column grid of floating plates; banner is a stacked bar in normal flow. Start and End are in completely different places in each, and the mode is chosen per device rather than per breakpoint
  • Inside float there are three grids — >1080px, 580–1080px and <580px — and the Start/End plate changes grid area in each
  • THE ANCHOR CAN BE ABSENT, three different ways: .topbar-legend is display:none in short landscape, the legend is never rendered at all on a point-only map, and the cast plate is display:none before a selection exists and visibility:hidden (hidden-reserve) while a cast is impossible

What changed

  • coachAnchor.ts asks the DOM and watches it: window resize, a ResizeObserver on the element, a MutationObserver over the whole bar (attributes included — that is how the fields switch into their typing state) and document.fonts.ready. The same observer set useLogoAnchor settled on, for the same reasons
  • Both renderings of a field carry data-coach: the resting <button> and the typing <div> are different ELEMENTS in one slot, so the anchor is replaced rather than moved every time somebody opens a search
  • "Absent" is a first-class answer and falls back to the bottom strip. An arrow tip pointing at nothing is worse than the strip it replaced
  • TopBar gains five data-coach attributes and nothing else — no refs, no state, no imports. Moving a control is free; the callout is measured wherever it lands

PLACEMENT

The box is clamped; the tip is not

Symptom

Two rules pull against each other, and the second is the one a naive anchored callout gets wrong.

Root cause

  • THE BOX MUST STAY ON SCREEN — a callout running off the right edge has lost half its sentence, which is worse than being off-centre
  • THE TIP MUST STAY ON THE CONTROL. Centre the arrow on the BOX and the moment a clamp moves the box the arrow points confidently at whatever happens to be beside the control. At 450px, where the cast pair sits 8px from the right edge, that is every time

What changed

  • The box is clamped into the viewport with an 8px margin; the arrow then SLIDES along the box's edge to stay over the anchor's centre, keeping a 16px inset from the box's own corners so a tip never grows out of one
  • Vertically it is a flip: below by default — every anchor is in the top bar, so below is where the map is — above when there is no room below AND there is room above; below when neither fits, because a box above a control that does not fit covers the control
  • The clamp guards its own inverted range: at a viewport narrower than the box, an unguarded Math.min(Math.max(…)) throws the box off the LEFT edge, where no scrollbar will ever reveal it
  • The entrance animation is a FADE with no transform. A transform is included in the rect the next measurement reads, so a sliding entrance feeds its own offset back into the placement — and a stalled animation parks the box at the offset for good. Caught in the act: the tip measured 3px high of its control until the transform came out
  • Split from the component and unit-tested, because the failure mode is never "does it render", it is "does it still point at the right thing at 380px"

RESTRAINT

Standing down while somebody types an address

Symptom

Clicking the Start field opens an address search INSIDE that same plate — and the callout is hanging off that plate, over where the suggestion list opens.

Root cause

  • Setting a start point by address is one intention with four steps in it: click the field, type a street, wait for the geocoder, arrow down and press Enter. Nothing should interrupt it, and least of all the thing that asked for it
  • The suggestion list is --z-autocomplete; a callout hanging off the same plate is in its way whatever the rung

What changed

  • The coach shows NOTHING for the whole of it — not the callout, not the strip, and the greying comes off too, so the bar the visitor is now using is fully lit. It comes back on the other side, by which time the point has landed and the step has already moved on
  • Detected from the DOM (.legend-tool.typing) rather than from TopBar's own state: it rides the observer already watching the bar, needs no prop drilled through a component another workstream is editing, and keys on the class the float chrome's own stacking rules key on — so it cannot quietly stop meaning this

FOUND WHILE VERIFYING

Two bugs, both about something not running

Symptom

The coach sat over the suggestion list it was supposed to stand aside for; and abandoning an address search silently took the whole coach with it.

Root cause

  • The anchor tracker coalesced its measurements on requestAnimationFrame. rAF DOES NOT RUN in a hidden or fully occluded window — Chrome stops the frame clock — so the mutation that says "the field just became a search box" fired, scheduled a callback, and the callback never ran
  • The callout listened for Escape on the window. So does the address search it points at. One Escape did both

What changed

  • Coalesce on a timeout. There is nothing to align to a frame here — this reads layout and sets state, and the render that follows is React's to schedule
  • The callout does not close on Escape at all. The × is its dismissal; Escape belongs to the WALL, which is a modal dialog and owes the reader an escape hatch. A label on a control does not
  • Worth naming as a pair: both are things that silently did not happen, in the two seconds when the visitor was doing exactly what they had been asked to do

+// ==========================================================================
+// Putting the callout somewhere it can actually point from
+// ==========================================================================
+// Pure geometry, separated from the component for one reason: the thing that
+// goes wrong with an anchored callout is never "does it render", it is "does it
+// still point at the right control at 380px" — and that is a question about
+// four numbers, which a test can ask far more thoroughly than a person dragging
+// a window edge can.
+//
+// Two rules do all the work, and they pull against each other:
+//
+//   THE BOX STAYS ON SCREEN. It is clamped into the viewport with a margin. A
+//   callout that runs off the right edge is worse than one that is not centred,
+//   because half its sentence is gone.
+//
+//   THE TIP STAYS ON THE CONTROL. So when the clamp moves the box, the arrow
+//   does NOT move with it — it slides along the box's edge to stay over the
+//   anchor's centre. This is the part a naive implementation gets wrong: it
+//   centres the arrow on the BOX, and then at narrow widths the arrow points
+//   confidently at whatever happens to be next to the control.
+//
+// The arrow keeps a minimum inset from the box's corners, because a tip growing
+// out of a corner reads as a rendering fault rather than as a pointer. When the
+// anchor is so far into a corner that even the inset cannot reach it, the arrow
+// stops at the inset and the box is as close as it can get — the honest failure,
+// and the only one available once the box is against the viewport edge.
+//
+// Vertically it is a simple flip: below the anchor by default, above it when
+// there is no room below AND there is room above. Below is the default because
+// every anchor the coach uses is in the top bar, so below is where the map is.
+// ==========================================================================
+
+import type { AnchorBox } from "./coachAnchor";
+
+export interface Viewport {
+  width: number;
+  height: number;
+}
+
+export interface CalloutSize {
+  width: number;
+  height: number;
+}
+
+export interface CalloutPlacement {
+  /** Viewport coordinates for `position: fixed`. */
+  top: number;
+  left: number;
+  /** Which side of the box the tip grows out of. */
+  side: "above" | "below";
+  /** The tip's centre, in pixels from the box's own left edge. */
+  arrowLeft: number;
+  /** What the box is allowed to be, before it is measured. */
+  maxWidth: number;
+}
+
+/** Clear of the viewport edge. */
+const MARGIN = 8;
+/** Between the anchor's edge and the box — the tip lives in here. */
+const GAP = 10;
+/** How close the tip's centre may get to a corner of the box. */
+const ARROW_INSET = 16;
+/** Wide enough for two lines of the ask at desktop type; narrower is fine. */
+const PREFERRED_WIDTH = 300;
+
+function clamp(value: number, low: number, high: number): number {
+  // Guard the inverted range: at a viewport narrower than the box, `high` lands
+  // below `low` and an unguarded clamp returns the larger of the two, throwing
+  // the box off the LEFT edge — the one place there is never a scrollbar to
+  // reveal it.
+  if (high < low) return low;
+  return Math.min(Math.max(value, low), high);
+}
+
+/** The widest the box may be here. Read before the box exists, so it can be
+ *  applied as a CSS max-width and measured afterwards. */
+export function calloutMaxWidth(viewportWidth: number): number {
+  return Math.min(PREFERRED_WIDTH, Math.max(160, viewportWidth - MARGIN * 2));
+}
+
+export function placeCallout(
+  anchor: AnchorBox,
+  size: CalloutSize,
+  viewport: Viewport
+): CalloutPlacement {
+  const maxWidth = calloutMaxWidth(viewport.width);
+
+  const below = anchor.top + anchor.height + GAP;
+  const above = anchor.top - GAP - size.height;
+  const fitsBelow = below + size.height <= viewport.height - MARGIN;
+  const fitsAbove = above >= MARGIN;
+  // Below unless it does not fit and above does. When NEITHER fits — a control
+  // taller than the viewport minus the box, which short landscape can produce —
+  // stay below and let the clamp deal with it, because below is where the map
+  // is and an overlapping callout above the bar covers the control itself.
+  const side: "above" | "below" = !fitsBelow && fitsAbove ? "above" : "below";
+
+  const top = clamp(
+    side === "below" ? below : above,
+    MARGIN,
+    Math.max(MARGIN, viewport.height - size.height - MARGIN)
+  );
+
+  const anchorCentre = anchor.left + anchor.width / 2;
+  const left = clamp(
+    anchorCentre - size.width / 2,
+    MARGIN,
+    viewport.width - size.width - MARGIN
+  );
+
+  const arrowLeft = clamp(
+    anchorCentre - left,
+    ARROW_INSET,
+    Math.max(ARROW_INSET, size.width - ARROW_INSET)
+  );
+
+  return { top, left, side, arrowLeft, maxWidth };

+// Where the coach points — measured, never guessed
+// ==========================================================================
+// The first-run coach used to be one strip at the bottom of the map saying
+// "Tap the map where that stretch starts." A strip at the bottom of the screen
+// cannot point, so the sentence had to describe the control instead of
+// indicating it, and the control it described is at the TOP of the screen in a
+// bar the reader had not looked at yet. Now the coach is a callout hung off the
+// real element, with an arrow tip on it.
+//
+// That turns the whole problem into one question — WHERE IS THAT ELEMENT RIGHT
+// NOW — and this module is the answer. Nothing here is a constant, because
+// every constant would be wrong at some width:
+//
+//   · The chrome has TWO MODES. `data-chrome="float"` (the default) lays the
+//     bar out as a 6-column grid of floating plates; `banner` is a stacked bar
+//     in normal flow. Start and End are in completely different places in the
+//     two, and the mode is chosen per device, not per breakpoint.
+//   · Inside float there are three grids — >1080px, 580–1080px, and <580px —
+//     and the Start/End plate moves grid area in each.
+//   · THE ANCHOR CAN BE ABSENT. `.topbar-legend` is `display: none` in short
+//     landscape, and the whole legend is never rendered at all on a point-only
+//     map (a station map, or a theme whose inputMode is "point"). The cast
+//     plate is `display: none` in float mode until a selection exists, and
+//     `visibility: hidden` (`hidden-reserve`) when a cast is not yet possible.
+//     A callout with an arrow tip pointing at nothing is worse than the strip
+//     it replaced, so "absent" is a first-class answer here and the caller
+//     falls back to the bottom strip when it comes back.
+//
+// So: ask the DOM, watch it, and re-ask on anything that could have moved it.
+// The observers are the same set `useLogoAnchor` settled on for the same reason
+// — resize, a ResizeObserver on the element, a MutationObserver over the whole
+// bar (class and attribute changes included, because that is how the fields
+// switch into their typing state), and `document.fonts.ready`, since the bar's
+// own height changes when the mono face lands.
+//
+// One extra fact this reports that the logo hook did not need: whether an
+// ADDRESS SEARCH IS OPEN in the legend. The flow has to stand down while
+// somebody is typing an address — see the note on `typing` below.
+// ==========================================================================

+   * and presses Enter. That is one intention with four steps in it, and a
+   * callout with an arrow tip parked over the suggestion list — which opens

+  // whole pixels keeps a resize from re-rendering the callout every frame.

+    Math.round(a.left) === Math.round(b.left) &&
+    Math.round(a.width) === Math.round(b.width) &&
+    Math.round(a.height) === Math.round(b.height)
