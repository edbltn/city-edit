Removing ferry edges from routing and the display graph

2026-06-17 · branch fix/unify-voting
1 2 VerificationChecklistFull diff

Ferry ways tagged foot=yes were slipping past the "ferries disabled" profile via an access-fallback that both OSRM and its Python mirror share — so routes jumped open water and ferry lines haunted the hover graph. One explicit route=ferry cutoff on each side removes them everywhere, and a new reverse-coverage check keeps the two graphs honest.

OSRM + Backend

1 · The ferry leak — water-crossing edges in both graphs

Symptom

Ferry routes still showed up as long straight lines over open water in the hover/topology graph (most visibly the Staten Island Ferry across New York Harbor), and OSRM would happily route a pedestrian across the water along them.

Root cause

  • Both osrm/foot.lua and its Python mirror server/foot_profile.py already had empty ferry tables (route_speeds = {} / _ROUTABLE_ROUTE = frozenset()) and claimed ferries were disabled.
  • But an empty ferry table only stops the dedicated ferry handler from assigning a ferry speed. A route=ferry way that is also tagged foot=yes (the Staten Island Ferry, Governors Island, every NYC Ferry line…) then falls through to the generic speed step, whose access fallback gives any access-whitelisted way default_speed. So OSRM routed it as a normal walkway, and the Python mirror admitted it via the identical return access in _ACCESS_WHITELIST fallback.
  • Measured against the real NYC extract: 134 of 145 route=ferry ways were being accepted into the topology graph; OSRM routed Whitehall→St George (open water) as 8848 m at 1.39 m/s — normal walking speed straight across the harbor.

What changed

  • Explicit ferry cutoff in OSRM. process_way now aborts on data.route == 'ferry' before the handler sequence runs, so the access fallback never gets a chance to assign a speed. This drops all ferries regardless of their access tags — not just the ones the empty route_speeds already covered.
  • Matching cutoff in the Python mirror. way_is_foot_routable rejects route=ferry (new _ROUTE_BLACKLIST) before the access whitelist fallback, so the votable topology graph — and the PMTiles background and hover graph built from it — carry exactly what OSRM routes.
  • Rebuilt artifacts: the per-city walk graphs (walk_graph.pkl), the merged OSRM dataset (re-extracted with the new profile), and the per-city graph.pmtiles. NYC dropped from 3,309,478 → 3,307,316 directed edges; longest surviving edge is 1439 m (no over-water hops).

Files touched

  • osrm/foot.lua — route=ferry abort in process_way (+ corrected route_speeds note)
  • server/foot_profile.py — _ROUTE_BLACKLIST + route=ferry reject in way_is_foot_routable
Backend · tests

2 · Keeping OSRM and the display graph consistent

Symptom

The deeper question: is the hover graph guaranteed to be a consistent copy of the graph OSRM routes on? The ferry bug was precisely a case where the two independent implementations of the routability rule (Lua + Python) drifted — they were consistently wrong together.

Root cause

  • By design the topology graph is built by a Python mirror of foot.lua and is a deliberate superset of OSRM's foot network (extra topology edges are harmless; every OSRM node must resolve to a topology edge so votes map). validate_osrm_topology.py verified that forward direction (topology ⊇ OSRM) — but nothing checked the other direction, so a topology edge that OSRM refuses to route (a ferry) went unnoticed.

What changed

  • New reverse-coverage check in validate_osrm_topology.py (--reverse-edges N): sample N topology edges and confirm OSRM will actually traverse each at roughly its own length. An edge OSRM refuses or only reaches via a huge detour is flagged as an orphan — exactly the ferry class of bug. On the rebuilt NYC graph: 0 / 382 orphans.
  • Unit regression test tests/unit/test_foot_profile.py locks the Python predicate: ferries with foot=yes/access=yes/designated are all rejected, while ordinary footways and the access-fallback path (e.g. a cycleway tagged foot=designated) still route.
  • Both files keep the KEEP IN SYNC contract explicit: the Lua abort and the Python reject reference each other so the next profile edit updates both.

Files touched

  • server/tests/validate_osrm_topology.py — run_reverse_check + --reverse-edges flag
  • server/tests/unit/test_foot_profile.py — NEW predicate regression tests
Verification

What was run

  • Predicate scan over the real NYC PBF: of 145 route=ferry ways, the old rule accepted 134, the new rule accepts 0.
  • OSRM (rebuilt dataset): Staten Island Ferry crossing Whitehall→St George now returns NoRoute (was Ok, 8848 m); on-land NYC + SF walks still route.
  • Rebuilt NYC topology: 0 edges longer than 1500 m (longest 1439 m) — no over-water hops survive.
  • validate_osrm_topology.py --city nyc -n 300 --reverse-edges 400 against the rebuilt OSRM: forward node coverage 99.95% / edge 99.997%; reverse 0/382 orphan edges.
  • pytest tests/unit — 24 passed (9 new in test_foot_profile.py).
  • All five city walk graphs and their graph.pmtiles rebuilt from the same source PBFs.
For you

Manual checklist

  • Open http://localhost:3000/m/nyc-walkways and look at New York Harbor / the East River — the long straight ferry lines (Staten Island Ferry, Governors Island, NYC Ferry routes) should be gone from both the background network and the hover graph.
  • Try routing on foot from Manhattan to Staten Island — it should fail to cross the water rather than drawing a straight line over the harbor.
  • Spot-check other cities (SF Bay, DC/Potomac) for stray over-water lines.
  • Re-run OSRM_URL=http://localhost:5005 python tests/validate_osrm_topology.py --city sf -n 300 --reverse-edges 400 for a non-NYC city; reverse orphans should be ~0.
  • Confirm server/.env points OSRM_URL at the rebuilt dataset (local: http://localhost:5005, the osrm-local container).
  • On the next prod build, the OSRM image re-extracts from osrm/foot.lua automatically; the per-city graph + PMTiles rebuild picks up the new foot_profile.py.

+def _edge_len_m(a, b):
+    """Great-circle length of a topology edge between [lat, lon] endpoints."""
+    import math
+    (lat1, lon1), (lat2, lon2) = a, b
+    p1, p2 = math.radians(lat1), math.radians(lat2)
+    dphi, dlmb = math.radians(lat2 - lat1), math.radians(lon2 - lon1)
+    h = math.sin(dphi / 2) ** 2 + math.cos(p1) * math.cos(p2) * math.sin(dlmb / 2) ** 2
+    return 6371008.8 * 2 * math.asin(math.sqrt(h))
