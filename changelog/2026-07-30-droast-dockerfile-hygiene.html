React client · build

1 · A missing type import silently broke every Docker client build

Symptom

Building the client image (and therefore ANY overlay deploy) failed at tsc -b with TS2304: Cannot find name 'ForcedCorridor' ×2 in MapView.tsx. Localhost looked perfectly healthy the whole time — Vite's dev server transpiles without type-checking, so the error only existed at image-build time. Surfaced by the droast validation builds, not by any dev workflow.

Root cause

  • 536fb76 (ghost-waypoint corridors) added ForcedCorridor type annotations to MapView's corridorChainOf/corridorChainFor without importing the type — every other user (RouteContext, reducer) already imported it from selection/types.
  • Nothing in the dev loop runs tsc; the first consumer to notice would have been the next overlay deploy's Cloud Build, mid-deploy.

What changed

  • One line: import type {{ ForcedCorridor }} from "../../selection/types"; — same style as RouteContext's import.
  • Verified by host tsc -b (clean) and a full docker build of client-react/Dockerfile (image builds through vite build).

Docker · all images

2 · droast lint pass: 1 error / 12 warnings / 27 infos → clean

Symptom

Ran droast 1.4.11 over all 10 Dockerfiles: 1 error (osrm CMD referenced an undeclared $PORT), 12 warnings (no USER, no CMD in overlays, COPY-everything, single-stage), 27 infos (no .dockerignore anywhere, unpinned apt, missing Python env vars, missing healthchecks). No build context in the repo had a .dockerignore, so local docker builds could sweep secrets (server/.env), server/osm_data graphs, and node_modules into context uploads.

Root cause

  • The Dockerfiles accreted per-workstream (main bake, 5 surgical overlays, 3 service images, 1 batch job) without a shared hygiene pass; screenshots/Dockerfile even used bare pip against the project's own uv mandate.

What changed

  • .dockerignore per build context (root + server + client-react + osrm + screenshots). The root one feeds the app image AND all 5 overlays, so it excludes secrets/graphs/node_modules while preserving every COPY'd path (client-react/, server/*.py + data/, deploy/, .arrays-staging/, .blocks-staging/).
  • osrm: the one ERROR — ENV PORT=5000 declares the var the CMD interpolates (Cloud Run still overrides with 8080); plus EXPOSE 5000 and an explicit HEALTHCHECK NONE (the runtime image ships no curl/wget — same rationale already documented on the compose service).
  • Main image: --no-install-recommends; a status-only HEALTHCHECK probing /health with a 900s start period + 15 retries, mirroring deploy/healthcheck.sh's graph-warmup tolerance (Cloud Run ignores Docker HEALTHCHECK — this is for compose runs).
  • server: PYTHONUNBUFFERED/PYTHONDONTWRITEBYTECODE, --no-install-recommends, explicit HEALTHCHECK NONE — the image is shared with the osm-refresh sidecar (whose command runs no server), so compose owns the flask probe.
  • client-react: explicit COPY of the six build inputs instead of COPY . . (unrelated files no longer bust the npm build cache) + a busybox-wget healthcheck on the nginx stage.
  • screenshots: bare pip → uv pip install --system (CLAUDE.md mandate), Python env vars, HEALTHCHECK NONE (one-shot batch job).
  • droast.toml records the four deliberate global skips with rationale — DF005 apt pinning (Debian point-release churn breaks rebuilds; we pin base images instead), DF020 USER (each image has a concrete root requirement), DF011 single-stage (slim images carry no toolchain), DF036 no-CMD (overlays inherit CMD from the digest-pinned ${{BASE_IMAGE}}). Future runs lint clean: droast exits 0.
