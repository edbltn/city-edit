City Edit · Change log

Sparse vote bodies (the bikepaths OOM), brotli topology, and a first-load P99 dashboard

2026-07-22 · branch fix/unify-voting
1 2 3 VerificationChecklistFull diff

The bikepaths mobile crash traced to the one payload the typed-array migration missed: the dense 26MB /api/graph-votes JSON, whose parse materializes ~9M boxed JS values. Votes now travel sparse and decode into typed arrays, the 50MB topology blob ships as brotli (−17%), and a first-map-load beacon feeds a new P99 row on the System Health dashboard.

Backend + Frontend

1 · The bikepaths mobile crash — the vote body was the last boxed giant

Symptom

Opening bikepaths.cityedit.org (map nyc-bikes, the full NYC streets graph, 906K votes) on mobile Safari showed the loading indicator twice and died with “a problem repeatedly occurred” — WebKit's message after the tab OOM-crashes, auto-reloads once, and crashes again. The walkways map on the SAME graph survived.

Root cause

  • The topology was migrated to typed arrays after the last mobile OOM — but /api/graph-votes never was. Its dense JSON body carries arrays sized to the graph: 3.3M edge_votes + 3.3M edge_vote_types + 1.35M×2 node arrays + 290K×2 block arrays ≈ 9.3M JSON values (26MB decompressed). JSON.parse materializes every empty [] as a DISTINCT boxed JS array — ~3.3M of them for edges alone, roughly 250–400MB of transient+resident heap on a phone whose tab jetsams around 1–1.5GB.
  • Why bikes and not walkways: nyc-bikes has 4.5–8× the vote density (37K voted edges, 48K voted nodes, 29K lit blocks vs 8K/8.6K/3.4K) — so everything DOWNSTREAM of the parse (per-type breakdown sub-arrays, the ~29K-block first setFeatureState sweep, route-proposal nets, pins) is also several times heavier, on top of the same fixed 9.3M-slot parse. The peak lands just past jetsam on bikes and just under it on walkways.
  • The loading indicator showing twice is two stacked things: a benign two-phase loader (config-resolve splash → map+heatmap splash) on every cold load, and Safari's own crash-and-auto-reload. The React ErrorBoundary can't help — a jetsam kill terminates the process; there is no exception to catch.

What changed

  • format=sparse wire format. The server now builds a sparse twin of every vote snapshot: nonzero (idx, val) pairs for edge/node/block totals (numpy flatnonzero — no O(graph) Python loop on the request path) and voted-only dicts for the per-type breakdowns, sourced from the sparse dicts build_arrays/build_block_arrays already hold. Breakdown keys come from the vote dicts, NOT from nonzero totals — counter-votes can cancel an edge's net to 0 while its breakdown must survive (the nyc-bikes Broadway case).
  • Typed + holey decode client-side. decodeSparseVotes() rebuilds edge_votes/node_votes/block_votes as Int32Array and the breakdowns as HOLEY arrays (entries only at voted indices). Every consumer already guards with ?? [] / if (!pairs), and the mutation paths materialize a fresh array before writing — holes are safe where a shared [] sentinel would be catastrophic (voteApply pushes in place). ~600K materialized values instead of 9.3M boxed slots.
  • Both formats served side by side. The dense body stays the default for old cached clients; sparse rides the same snapshot cache entry with its own -sp ETag token. IndexedDB now caches the raw sparse payload (~50× smaller structured-clone) and re-decodes on read; old dense cache entries still decode as-is.
  • Compat fix en route: broadcastBlockVotes gated on Array.isArray, which an Int32Array fails — it now checks length, so block heat survives the typed migration.

Backend

2 · First loads: brotli for the 50MB topology blob

Symptom

A first-time visitor to any NYC map downloads the GTB2 binary topology: 50MB raw, 18.8MB gzipped — the dominant network cost of a cold load (5–15s on mobile LTE).

Root cause

  • The blob was pre-gzipped once per graph load (level 6) and served with Content-Encoding: gzip; brotli was never wired in even though every current browser advertises br.

What changed

  • Pre-brotli'd twin (quality 5). Measured on the real NYC blob: 15.5MB vs 18.8MB (−17%) and 0.6s vs 1.4s to build — strictly better than the gzip it shadows. Served when the client's Accept-Encoding tokens include br; gzip stays the fallback, identity last. Guarded import — no brotli package, no br variant, no error.
  • Prewarm now pre-compresses both twins, and unload() drops the br blob with the rest.

Files touched

  • server/graph_registry.py — topology_binary_br(), unload() clears it
  • server/app.py — token-parsed Accept-Encoding negotiation in graph_topology, prewarm
  • server/requirements.in / requirements.txt — brotli (uv pip compile)

3 · First-map-load P99 on the System Health dashboard

Symptom

No visibility into what users actually experience on first load — Cloud Run's request_latencies only see individual API calls, not the navigation-to-map-visible journey.

Root cause

  • The client had no telemetry at all; the existing P99 tiles chart server-side per-request latency.

What changed

  • One beacon per page load. When the full-screen loader first dismisses (base map ready AND heatmap painted), the client sendBeacons {map, ms, cachedTopo, nav} — ms measured from navigation start via performance.now(), cachedTopo separating true cold first loads from IndexedDB repeat visits. Sent as a plain string: a Blob typed application/json needs a CORS preflight sendBeacon can't perform, and Chrome silently drops it (found live in dev).
  • /api/client-timing → [MAPLOAD] log line. Validates and sanitizes, always 204s (never an error-noise source), logs one line for the log-based metric.
  • cityedit_map_load_ms distribution metric + dashboard row. Log-based DISTRIBUTION (ms, 50ms–10min buckets) labeled by map / cached / nav, plus two new System Health tiles: a First-map-load P99 scorecard and a cold-vs-warm P50/P99 chart. Terraform, targeted-apply safe per monitoring.tf's header.

Files touched

  • client-react/src/utils/loadTelemetry.ts — NEW: reportTopologySource / reportMapLoaded
  • client-react/src/App.tsx — beacon on first loader dismissal
  • server/app.py — /api/client-timing
  • terraform/monitoring.tf — google_logging_metric.map_load_ms + dashboard row

+function denseInt32(n: number, idx?: number[], val?: number[]): Int32Array {
+  const a = new Int32Array(n);
