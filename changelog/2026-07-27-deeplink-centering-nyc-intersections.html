Production data

1 · nyc-intersections — the poster campaign's landing map

Context

The poster QR codes needed a production map dedicated to fixing dangerous intersections: a curated set of point- and route-based improvement vote types, in a look that reads as a safety campaign.

Root cause / how it was done

  • Created via the app's own POST /api/maps (the Propose-a-Map path — no DB surgery, all cache invalidation for free): slug nyc-intersections, name “NYC Dangerous Intersections”, NYC streets network, terracotta style (the light basemap with the brick-red heat ramp), symbol safety.
  • 14 custom vote types — 9 point-kind (Fix dangerous intersection, Add pedestrian signal, Fix signal timing, Daylight this corner, Add curb extension, Add raised crosswalk, Add pedestrian refuge island, Ban turn on red, Add intersection lighting) and 5 route-kind (Add protected bike lane, Add traffic calming, Add crosswalk, Widen sidewalk, Lower speed limit). Labels shared with presets reuse their registry ids/kinds; new labels were stamped at creation so a later cast can't mis-kind them.
  • Dry-run: the identical payload was created and exercised on local dev first (picker filtering, icons, a smoke vote, legend) before the prod POST.

What changed

  • Live at https://cityedit.org/m/nyc-intersections (201 on create; config round-trip verified: style/subtitle/network/14 vote types).
  • generate_posters.py now QR-links every poster to this map with vt=Fix+dangerous+intersection preselected — a scan lands with the pin set and one tap left to cast. All 94 posters + manifest regenerated.

Files touched

  • scripts/generate_posters.py — BASE_URL → nyc-intersections, vt param on QR deep links
  • data/posters/out/ — 94 posters regenerated (gitignored; manifest.csv has final URLs)

2 · Deep links now center the camera on what they select

Context

Visiting a shared link like walkways.cityedit.org/?w=40.869434,-73.826116&vt=Improve+sidewalk restored the selection but opened at the citywide default view — the pin was set, invisible, five zoom levels away. Every poster QR would have landed users on a borough-scale map.

Root cause / how it was done

  • getInitialMapView() only ever read the explicit camera params (z/lat/lng). Selection restore (?w=) seeds the waypoints synchronously in RouteContext, but nothing ever moved the camera to them — links shared from the app happen to carry camera params, so only hand-built deep links (exactly what the QR generator makes) hit the gap.

What changed

  • When no explicit camera params are present, the initial view now derives from the URL selection (w= or legacy slat/slng): a single waypoint centers at street zoom 17; a multi-waypoint route fits its bounding box (cos-corrected span → zoom 11–16). Explicit camera params still always win; vt-only links keep the default view. Pure core extracted as computeInitialMapView() with 8 unit tests (305 client tests green).
  • Deployed staging-first per runbook: prod DB snapshot (~/city-edit-prod-backups/20260727-204128/, full dump + CSVs + checksums) → overlay image on the serving digest base (no graph rebake, no resnap) → staging service verified live (camera centered on Co-op City Blvd & Bartow Ave at street zoom) → same digest d443e966… promoted to prod (revision 00110, 100% traffic, asset hash matches staging). Prod verified on the original repro URL and on a poster QR link.
  • Build hygiene: repo-root /data/ (114 MB of analysis + posters) excluded from Cloud Build uploads — anchored so server/data/ (baked into images) keeps uploading.
