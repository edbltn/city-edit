City Edit · Change log

Counter-votes go cancel-only — negative blocks eliminated

2026-07-23 · branch fix/unify-voting
1 2 3 4 VerificationChecklist

Imported Citibike trips are routed through the foot profile on purpose — the divergence between how a pedestrian moves and where a bike is allowed to go IS the vote. But the ingest upvoted the whole pedestrianized path, so corridors that already carry bikes (and especially streets that already have bike lanes, densest near Citibike stations) got the same +1 as the genuinely un-bikeable stretches. The correction: a second, bike-legality OSRM dataset (stock v5.25.0 bicycle profile flattened to shortest-legal-path, pushing-the-bike disabled) re-routes every ingested ride pinned to its own voted corridor via via-points; every upvoted edge lying bodily inside the resulting route's 20 m corridor gets a direction=-1 cast from the ride's own voter identity. What survives upvoted is exactly what can't be ridden: park and plaza paths, stairs, and one-way streets taken against the flow.

Diagnosis · block layer

1 · The tally floor fixed edges — but blocks count devices

Symptom

A week after the 2026-07-21 tally floor (every net-negative (edge, vote_type) tally clipped to zero), prod block pins still showed net-negative vote breakdowns. Probing the served /api/graph-votes payloads: nyc-bikes had 1,171 (block, vote_type) entries with more downs than ups (sf 61, chicago 22) — while only ONE edge in the entire map was net-negative. The floor demonstrably held at edge level and demonstrably didn't at block level.

Root cause

  • Block counts are not sums of edge tallies. block_votes.py dedupes per device: a block's count for (vote_type, direction) is the number of distinct devices holding at least one row of that direction inside the block. A flipped import device with any surviving −1 row therefore counted as one “against” on that block — no matter how the per-edge sums balanced out.
  • The floor deleted only the excess down-rows (enough to lift each (edge,vt) sum to zero). 308,597 counter-cast −1 rows legitimately survived it (302,916 nyc / 3,754 sf / 1,927 chicago) — each one still marking its device “against” at block level, and each one silently eating one spared upvote on shared corridors (a flip is a −2 swing: the device's own +1 was already removed by clear-then-cast, so the −1 subtracts from someone else's surviving signal).

What changed

  • Recognize the correct end-state: the correction should cancel imported signal, not manufacture opposition. A flipped device's own upvote is already gone — its −1 row carries no information except “subtract one from whoever else voted here”. Delete them all (§2) and stop casting them (§3).

2 · Sweep: delete every counter-cast −1 row in prod

Symptom

308,597 counter-cast down-rows across the three bike maps, identified by the import marker (ip_hash = device_id — every counter cast used ip_from_voter) and direction = -1.

Root cause

  • Safe-to-delete precondition verified first: zero devices hold both directions on any (edge, vote_type) in all three maps — block-scoped clear-then-cast removed each flipped device's +1 when its −1 landed, so deleting the −1 leaves that device's contribution at exactly zero. Human downvotes (ip_hash ≠ device_id) are untouched by the predicate.

What changed

  • Fresh prod snapshot first (~/city-edit-prod-backups/20260723T051700Z/prod-full-pre-downsweep.dump, 32 MB).
  • One DELETE per map over the 5433 tunnel (302,916 nyc / 3,754 sf / 1,927 chicago), then per map: Redis aggregate rebuilt (rebuild_redis_for_map), block state purged (bd:/bagg:/bver — prod lazily rebuilds from the corrected rows), vote_rev bumped +1000 so every cached client invalidates.
  • Verified on the live API: negative (block, vote_type) entries nyc 1171 → 0, sf 61 → 1, chicago 22 → 0. The sf survivor is a single organic human downvote (real signal, preserved by design), as are the 2 remaining block downs on nyc and the 1/1/0 net-negative edges.
  • Side effect, intended: spared upvotes that surviving −1 rows had been eating now show through — covered corridors read slightly warmer, at their true spared-signal level.
server · counter_lyft.py

3 · Cancel mode is the new default — flips demoted to --flip

Symptom

Any future counter pass in flip mode would recreate the block-level negatives the sweep just removed: the NetGate keeps edge tallies ≥ 0, but every flip still registers its device “against” at block level.

Root cause

  • Flip semantics conflate two operations: removing the device's own credit (correct) and adding opposition (unwanted). Only removal is needed — and removal is a primitive the vote API already has: direction=0, block-scoped clear of the device's own votes.

What changed

  • counter_lyft.py now casts direction=0 on the covered edges by default: the device's own votes on the covered blocks are removed. A removal can only subtract what the device itself cast, so no (vote_type, edge) tally can go negative and no device is ever counted “against” — structurally, without a gate.
  • The tally-gate query (load_net_counts, a full-map aggregate) is skipped in cancel mode; the legacy behavior stays available behind --flip with the NetGate guard unchanged. All 15 unit tests pass (NetGate tests still cover the flip path).
  • Idempotency preserved: a re-run finds no remaining votes on the covered blocks and plans no-ops.
