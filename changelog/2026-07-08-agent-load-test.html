Agent load test: the vote pipeline saturates at ~9 votes/s

2026-07-08 · map agent-test-1 (NYC · streets · Bikes list) · local dev stack (host Flask app.py, Werkzeug threaded · OSRM :5005 · Redis :6379 · Postgres in Docker)

TL;DR. Simulated voter agents (WebSocket + one graph-votes fetch + route→vote cycles) were run in tiers of 5 → 160 against a fresh map. The app never hard-crashed, but the vote path saturated at ~8–9 votes/s from Tier 3 (20 agents) onward — every additional agent just deepened the queue. At Tier 6 (160 agents) the app functionally locked up: 13% of votes exceeded a 45 s client timeout (p95 = 45.6 s), 11 of 160 graph-votes responses were truncated mid-body, and Flask RSS doubled to 7.1 GB. Root cause: all votes serialize through one process-wide lock, and each vote performs ~300–550 sequential Redis round trips plus a synchronous Postgres write inside it (~90–100 ms of serialized work per vote). The health endpoint stayed at 1–2 ms throughout — monitoring would not have noticed.

Method

A fresh map agent test 1 was created via POST /api/maps. Each simulated agent behaves like a real client joining the map: it opens /ws?map=agent-test-1 and counts pushed deltas, fetches /api/graph-votes once (what the client does on load), then runs six cycles of POST /api/routes (random Manhattan-core origin/destination) followed by POST /api/vote on the returned edge set (typically ~100–200 edges, i.e. a real multi-block route vote with clear-then-cast semantics). A sidecar probe hit /health every second and sampled Flask CPU/RSS. Harness: loadtest.py (asyncio/aiohttp), 45 s request timeout, unique voter_id per agent.

Caveat: local dev serves via Werkzeug thread-per-connection; prod is gunicorn + gevent (1 worker). The bottleneck measured here is inside the request handler (lock + Redis/DB round trips), so it applies to both — but the failure shape differs: prod's single gevent worker would show head-of-line blocking on all endpoints sooner, whereas Werkzeug kept cheap endpoints fast while votes queued.

What breaks, in order

1 · One process-wide lock serializes every voteCritical — the lockup

cast_vote takes _proposal_vote_lock (a single threading.Lock, server/app.py:315) around the whole clear-then-cast transaction (server/app.py:1104). It serializes all voters on all maps within the instance — the per-voter Redis voter_lock would already be enough for the read-modify-write correctness it protects. With ~90–100 ms of work inside, the instance has a hard ceiling near 10 votes/s; queue latency is depth × 100 ms, which is exactly the measured linear p50 series (0.29 → 0.72 → 1.76 → 3.79 → 8.37 → 16.6 s). At 160 agents the queue exceeds any client timeout: functional lockup.

2 · ~300–550 sequential Redis round trips per vote inside the lockCritical — why the lock is slow

The critical section is dominated by per-edge chatter for a ~145-edge route vote: apply_directional (server/vote_store.py:203) builds and executes a 2-command pipeline once per edge (~145 round trips), and apply_block_delta (server/block_votes.py:56) issues 1–3 unpipelined HINCRBY/HDELs per edge (~150–400 more). Add the synchronous Postgres read + delete + 145-row insert (server/app.py:1158) and the post-write count read-back. At ~0.2 ms per local round trip this is the measured ~100 ms. (Contrast: read_edge_vt_counts at vote_store.py:260 already does it right — one pipeline for all edges.)

3 · graph-votes: 33.7 MB per join, cache defeated by votingHigh — the join storm

Each joining client fetches /api/graph-votes: ~33.7 MB uncompressed JSON, 1.3 s to build idle, 3–4 s p50 under load. The LRU vote cache (server/app.py:299) is keyed by revision — and every vote bumps the revision — so under sustained voting every fetch at a new rev is a full rebuild, and each response buffers the full body per request. At Tier 6 this drove RSS from 3.7 to 7.1 GB and truncated 11 of 160 responses mid-body (ClientPayloadError) — clients would see the stale-cache mismatch path.

4 · WS fan-out is O(votes × clients), one thread + one Redis connection per clientHigh

Every vote publishes one delta (per-edge counts for ~145 edges + block counts) and each of the N connected clients receives it — 132,808 messages at Tier 6 for 831 votes. Each WS handler (server/app.py:885) is a dedicated thread polling its own Redis pubsub connection at 10 Hz. 160 clients ≈ 160 polling threads fighting the GIL with the vote work — this is why routes p95 rose from 30 ms to 2.1 s (OSRM itself was never the bottleneck) and CPU exceeded one core only via socket/JSON C code.

5 · No backpressure or load-sheddingMedium

Werkzeug accepts unbounded connections and queues them into the lock; a vote waits 45 s and then dies at the client while the server still burns through it (write amplification after abandonment). Nothing sheds load, nothing bounds the queue, and /health — p50 1–2 ms through the entire meltdown — is blind to vote-path saturation, so prod monitoring keyed on health would miss this exact failure.

6 · Memory headroomMedium

Baseline RSS is ~3.5 GB (NYC graph) and peaked at 7.1 GB. Each horizontal replica pays the full graph again, and a join storm adds gigabytes of transient response buffers — on a small Cloud Run instance this profile is an OOM, which is the mobile-crash pattern seen before, now on the server side.

Mitigation plan

Ordered by impact; M1+M2 remove the lockup, M3+M4 remove the join storm, the rest harden.

M1 · Batch all Redis writes into ≤3 pipelines per vote (fixes #2 · est. 100 ms → ~10 ms)

  1. In cast_vote, replace the per-edge _apply loop with a whole-plan batch: accumulate every HINCRBY for clears + casts into one pipeline and execute once (same commands, same keys — pure transport change).
  2. apply_block_delta needs HINCRBY return values (the 0↔1 presence boundary), so make a vectorized apply_block_deltas two-phase: pipeline all bd: HINCRBYs → read results → pipeline the boundary-crossing bagg: adjustments and HDELs. Two round trips regardless of edge count.
  3. Optional endgame: move clear-then-cast into a Lua script/Redis Function — one round trip and cross-instance atomicity, which would also let the Redis voter_lock shrink.
  4. Verify with the existing vote semantics tests plus a new test asserting command-count per vote (pipeline call count) so the chatter can't regress.

M2 · Narrow the global lock to per-voter (fixes #1 · unlocks concurrency)

  1. Audit what _proposal_vote_lock actually protects: the voter's DB read-modify-write (per-voter by definition) and Redis counter updates (atomic HINCRBYs, and single-pipeline after M1). Nothing in the section is cross-voter except the counters, which don't need mutual exclusion.
  2. Replace it with a striped in-process lock keyed by (slug, device_id) — e.g. 64 threading.Locks indexed by hash — matching the scope of the existing cross-instance Redis voter_lock. Same correctness story, stated in one place.
  3. Postgres: give delete_edge_votes/record_edge_votes a connection pool + executemany/COPY; one transaction per vote. The synchronous write is fine once it only blocks that voter.
  4. Load-test again with the harness: expect votes/s to scale to Postgres/Redis limits (target ≥ 100/s single instance) and p95 flat vs. agent count.

M3 · Serve graph-votes as cached compressed bytes with debounced rebuild (fixes #3 and most of #6)

  1. Cache the gzipped bytes (not the JSON string) per (map, mode, rev); serve with Content-Encoding: gzip directly. 160 joiners then share one build + one compression, and per-request buffering drops ~10×. (Mind the existing curl/Accept-Encoding trap — keep an identity path.)
  2. Debounce invalidation under sustained voting: rebuild at most every 2–3 s, serving the last complete snapshot with its rev stamped. Clients already reconcile forward via WS deltas (SET semantics), so a slightly-stale snapshot + newer deltas is exactly the designed path; keep the topology-dimension stamp so the mismatch detector still works.
  3. Single-flight the rebuild (extend the existing build lock) so N concurrent joiners trigger one build.
  4. Longer term: emit the vote array in the typed-array binary format like graph-topology, or sparse (nonzero entries only) — a fresh map's 33.7 MB is almost all zeros.

M4 · Coalesce WS broadcasts; one pubsub listener per process (fixes #4)

  1. Batch deltas per map: aggregate published deltas and flush to clients at ≤ 5–10 Hz. Because clients SET authoritative counts, last-write-wins merging per (edge, vt) is lossless — N votes/s to M clients becomes ~10 msgs/s per client regardless of vote rate.
  2. Replace per-client pubsub connections + 10 Hz poll threads with one Redis pubsub listener per process fanning out to in-memory client queues; each WS then blocks on its queue instead of polling. Kills 160 threads and 160 Redis connections at Tier-6 scale.
  3. Verify: rerun Tier 5–6; expect routes p95 back to ~50 ms (contention gone) and WS message count ≈ clients × flush ticks, not clients × votes.

M5 · Backpressure, load-shedding, and a saturation signal (fixes #5)

  1. Bound the vote queue: if lock wait exceeds ~2 s (or striped-lock queue depth exceeds a threshold), return 503 + Retry-After immediately — the client already has optimistic-rollback UX. Better a visible retry than a 45 s hang that dies anyway.
  2. Expose vote-path saturation where monitoring can see it: lock-wait p95, votes/s, and rebuild time in /api/admin/stats, and fail /health (or a separate readiness probe) when lock-wait p95 exceeds a limit — the current health check stayed green through the whole event.
  3. Prod serving: with M1–M4 the handler becomes IO-light; keep gevent but run ≥ 2 workers × 2 instances (the June Redis vote lock + mode-scoped invalidation were built for exactly this) and set explicit gunicorn timeouts.

M6 · Memory (fixes #6, mostly falls out of M3)

  1. M3's shared compressed cache removes the join-storm buffers (the 3.5 → 7.1 GB spike).
  2. Baseline: the ~3.5 GB NYC graph per replica is the known rustworkx/typed-array workstream — worth doing before adding replicas, since each pays it again.
  3. Add RSS to the admin stats sample so growth is visible per deploy.

Verification checklist (after M1+M2)

  • Rerun loadtest.py --agents 40: vote p50 should be < 0.3 s (was 3.8 s) and votes/s > 50 (was 8.6).
  • Rerun --agents 160: zero timeouts, zero ClientPayloadError, RSS peak < 4.5 GB.
  • Vote-semantics tests green; one-direction-per-block invariant spot-checked via two agents voting opposite directions on overlapping routes.
  • Redis command count per 145-edge vote ≤ ~10 (was ~300–550) — assert via MONITOR sample or pipeline-call counter.
