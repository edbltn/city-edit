BASEMAP

The map knew where you were, but wouldn't say

Symptom

At neighborhood zoom the map was anonymous grey blocks. A proposal card could read "Rockaway Parkway & Linden Boulevard" while the map underneath named neither street — you could not tell Canarsie from Corona.

Root cause

  • The basemap has always been CARTO's dark_nolabels / light_nolabels tiles. That was a deliberate choice — the vote heat is the product and unlabelled tiles never compete with it — but it costs every scrap of orientation
  • Simply switching to a labelled basemap would not work: the block heat is drawn ON TOP of the base raster, so every street name would end up buried under a translucent hot block

What changed

  • CARTO ships the same cartography split in two, so the text half is re-added as a separate transparent raster layer drawn last — above the heat and the selection wash. The split is the whole trick; it is what lets a street name stay readable over a hot block
  • Labels sit at full opacity on the dark styles and 0.75 on the light ones. Dialling the dark ones back sounded tasteful and was wrong: a raster overlay has no halo knob, so opacity is the only contrast control, and on a saturated map (Williamsburg on nyc-bikes) anything under 1.0 washed the street names out entirely
  • The no-WebGL Leaflet fallback gets the same overlay, gated on the same !maplibreActive so a WebGL browser never stacks two label sets

DATA

Business names had to come from somewhere else

Symptom

CARTO's label tiles carry streets, neighborhoods and water — and no businesses or civic landmarks at any zoom. Verified against their own z13–z18 tiles over Times Square: not one theatre, shop or restaurant.

Root cause

  • Positron's label layer is designed as basemap furniture, not as a POI directory. What it does label beyond streets is green space, in green caps
  • Everything needed to build the missing half was already on disk: each city ships source.osm.pbf, the server already parses it with pyosmium, already encodes MVT, already writes PMTiles, and /api/tiles/<city>/*.pmtiles already serves and caches them

What changed

  • build_place_labels.py: one pyosmium pass produces places.pmtiles per city — 1.6 MB for NYC, under 0.5 MB elsewhere, ~100s to build
  • The client adds a MapLibre symbol layer above the CARTO label raster, filtered by each POI's reveal zoom and sorted so important labels win collisions
  • cities.py advertises a placesVersion exactly like blocksVersion: it doubles as the "does this city have labels?" flag and as the ?v= cache-buster, so a city built before the artifact existed adds no layer rather than requesting an archive that 404s on every pan

CARTOGRAPHY

Four ways the labels wanted to feel broken

Symptom

Every intermediate version was legible and wrong: a directory dump at city zoom, subway stops that read as street labels, and park names printed twice in two different fonts.

Root cause

  • The raw data is mostly noise. The five most common named POI tags in the NYC extract are subway platforms (15,688 — one per track), restaurants, named rail segments (10,675), places of worship, and abandoned track (4,950). Four of those five are not places
  • Density does not tune by hand. Any fixed per-kind zoom that looks right in Midtown is empty in Canarsie, and vice versa
  • Subway stops share Grand Central's tag. Both are railway=station, but NYC has 470-odd stops and most are named after the street above them
  • Two cartographies can't collide-avoid each other. The CARTO labels are baked pixels; ours are live symbols. Anything both layers label gets printed twice

What changed

  • An explicit allowlist cuts 210,003 named features to 34,349. Anything not named in it is dropped, so a new junk tag can never leak in
  • Grid thinning decides the zoom each label appears at: at every zoom the map is divided into cells and only the highest-ranked unplaced POI in a cell earns that zoom, with already-placed labels re-claiming their cell first. The density cap is geometric, so it holds everywhere without per-neighborhood tuning. Quarter-tile cells gave ~50 labels on the city view; full-tile cells give ~18
  • Subway stops get their own entry so 496 street-named labels stay off the city-scale view, and it deliberately skips the wikidata notability bonus — nearly every stop carries one and would otherwise land straight back among the mainline terminals. Getting the weight of that entry right then took a second correction in the opposite direction; see The subway stops that disappeared
  • Green space belongs to the basemap. Parks, gardens and squares are dropped from the allowlist entirely; this layer owns buildings and businesses. Verified the division is clean: CARTO labels no stadium, hospital or university
  • The thinning runs to zoom 21 (CONFIG.maxZoom), not 19. Every POI the grid never places falls back to the last zoom, and a ceiling of 19 dumped 20k labels — 60% of the set — into one ungoverned band

ASSETS

Drawing text meant owning the font

Symptom

The MapLibre style's glyphs URL pointed at demotiles.maplibre.org — harmless while nothing on the map drew text, and load-bearing the moment something did.

Root cause

  • MapLibre cannot render a text-field from a webfont; it needs signed-distance-field glyphs served as protobuf ranges
  • Red Hat Mono — the UI's own face — has no CJK coverage, and NYC has plenty of Chinese shop names in the extract

What changed

  • scripts/build_glyphs.js bakes the Latin ranges from Red Hat Mono into public/fonts/: 144 KB total, served as static assets by Vite in dev and nginx in prod
  • Using the UI's mono face is also a legibility decision: our labels read as visibly ours, distinct from the basemap's sans street names, which makes the two-cartography stack legible as a hierarchy rather than an inconsistency
  • CJK is handled by MapLibre's localIdeographFontFamily, which draws those ranges from a system font at runtime — without it every Chinatown shop name would render as nothing at all

REGRESSION

The subway stops that disappeared

Symptom

Six subway stations ring the East Village. At z16 the map showed one, and none appeared anywhere until z17–19.

Root cause

  • 496 of the 561 stations in the NYC bbox are station=subway, sharing Grand Central's railway=station tag. They were given their own entry to keep 496 street-named labels off the city-scale view — but that entry set rank and floor together, and rank 64 is near the BOTTOM of everything eligible at z15
  • So every grid cell went to a museum, hospital or university first. The stops were in the tileset the whole time; they just never won a cell
  • Worse, the shared grid is the wrong budget for them in principle. One museum per cell is plenty — museums are individually optional. Stations are read as a set, and showing one of six is not a sixth as useful, it is close to useless

What changed

  • Split the two concerns the single rank was carrying: prominence goes back up (rank 86 — a stop should win its cell whenever it is eligible) and the zoom holds them back instead (floor 14, never city scale)
  • Transit thins on its own grid, one level finer than everything else. The grid zoom is part of the cell key, so stations now compete only against other stations and never against a nearby deli
  • All six East Village stops now show at z16, and the city-wide z14 band grew from 157 labels to 420 as the stations surface
  • Two tests pin the regression from both directions: a stop must outrank every kind that once buried it, and it must not be displaced by a co-located museum — while two stops on one corner must still compete

ICONS

27 little marks, and why they let the ranking go back up

Symptom

A column of names in four colors still reads as a list. And the original reason for demoting the subway stops was real: a blue "5th Avenue" sitting beside the basemap's own "5th Avenue" street label reads as a rendering bug.

Root cause

  • Color alone carries about two bits. It can say which family a label belongs to, but not what the place is, and it cannot distinguish a station from a street name that happens to share its text
  • MapLibre draws icons from a sprite sheet, which would mean a second asset pipeline to keep in sync with the palette in mapStyles.ts

What changed

  • 27 glyphs on a 16px grid at 1.5 stroke — the vote-type icons' thin-line language (32-grid, 1.2 stroke) scaled so the strokes hold together at 13 CSS px
  • Rasterised at mount and registered with map.addImage instead of shipped as a sprite, so each glyph is baked in its category's color for the ACTIVE basemap and there is no sprite to regenerate when a palette changes
  • text-optional makes the layer degrade well: where a block is too busy for both, MapLibre keeps the mark and drops the name, so a dense strip thins into icons rather than into nothing
  • The set is deliberately coarser than the OSM tags feeding it — a pub and a bar share a glass, a college and a university a mortarboard. At 13px a set of 40 near-identical marks is harder to read than one of 20 distinct ones
  • Three glyphs were redrawn after seeing them at size: two concentric ellipses read as an eye rather than a stadium, a compact capsule as no entry rather than a pharmacy, and stage curtains as a Greek letter rather than a theatre

LEGEND

Four colors, one palette per basemap

Symptom

An undifferentiated wall of names is only marginally better than no names — you cannot scan it for the thing you actually want (the nearest station, the school on the corner).

Root cause

  • Colour coding only pays off if it is learnable, and re-hueing categories per map style would mean re-learning them on every one of the eight styles
  • The heat ramp already owns each style's accent hue, so a loud label palette competes with the product

What changed

  • Four categories — transit, civic, culture, retail — in one palette per basemap (dark / light), not per style
  • Retail is deliberately the most neutral of the four: it is by far the largest category, and tinting every deli and bank would turn the deep zooms into confetti
  • Green is absent by design — parks are labelled by the CARTO raster underneath, in its own green, which makes five readable classes on screen from four of our own
  • Halos are painted in the basemap's own paper/ink token, which is the contrast control the raster overlay above it does not get to have

BUILD

Built where the PBFs still exist

Symptom

The label build reads source.osm.pbf. The prod image deletes every one of them.

Root cause

  • The Dockerfile's graph stage ends with rm -f osm_data/*/source.osm.pbf to keep the image small, and build_pmtiles.py runs in a LATER layer — it only needs the walk graph, so it never noticed

What changed

  • build_place_labels.py --all runs inside that same RUN, immediately before the rm -f
  • The Makefile tiles target and the docker-compose osm-refresh sidecar (first-run and the weekly refresh loop) build the labels alongside the graph tiles, so dev and prod stay on the same artifacts
  • Freshness is mtime-based against the PBF, like the graph tiles: repeated builds skip, --force rebuilds

+// dashes that show up in business names ("Joe's" is often U+2019, not U+0027).

+  [256, 511],
+  [512, 767],

+async function main() {

+  } else {

+    if (!res.ok) throw new Error(`font download failed: ${res.status}`);
+    font = Buffer.from(await res.arrayBuffer());

+async function rasterize(svg: string, sizePx: number, ratio: number): Promise<ImageData> {
+  const px = Math.round(sizePx * ratio);
+  const url = `data:image/svg+xml;charset=utf-8,${encodeURIComponent(svg)}`;

+  if (!ctx) throw new Error("2d context unavailable");
+  ctx.drawImage(img, 0, 0, px, px);
