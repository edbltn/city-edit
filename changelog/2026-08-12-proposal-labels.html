Three fixes to Top Proposals: a pin now takes real support (>100 net votes, both point and route families); every modal badges the vote types that are CURRENT top proposals for what it shows (square = point, diamond = route fully inside the selection); and route corridors are now grown ROUTING-CONSISTENTLY — an extension either keeps the segment a shortest path or pins a ghost waypoint (max 3), and the whole waypoint chain lands in the URL, so a shared top-proposal link keeps routing into its corridor long after the proposal itself has churned away.

THE GAP

A pin cannot say what it wants

Symptom

Every top proposal on the map is a pin — a square for a point proposal, a diamond for a corridor. A pin says that something is wanted somewhere. What it is wanted FOR is only available by hovering or clicking, one proposal at a time. There is no way to look at a city and read what it is asking for.

Root cause

  • The map already has two text tiers, and both are deliberately quiet. CARTO's *_only_labels raster carries street, neighbourhood, water and park names as baked pixels. Our own places.pmtiles layer carries businesses, transit, civic and culture POIs, pulled 58% toward neutral grey by POI_MUTE
  • POI_MUTE exists for exactly one reason, stated in its own comment: to leave the top proposals room to be the loudest thing on the map. But the whole of that headroom was being spent on pin SHAPE and glow rings — the two channels least able to carry meaning
  • Adding text to the pin's divIcon would have been the short path, and it inherits the zoom scaling and fan-out for free. It also has no collision avoidance whatsoever: twenty pins on Manhattan would have produced twenty overlapping sentences, on top of the place labels, on top of the street names

What changed

  • The words are drawn as a MapLibre symbol layer, not as pin markup, so decluttering is not ours to write — MapLibre runs one global collision index across every symbol layer and crowded labels simply do not place
  • They are the ONE text tier allowed to be vivid: the map style's accent at full chroma, which is the same color the heat wears, so a label reads as belonging to the heat it names
  • The pins stay exactly where they are. They are interactive and MapLibre here is interactive: false, so this adds words beside the existing pins rather than reimplementing them

DECLUTTERING

Letting MapLibre place them, and teaching it where the pins are

Symptom

A GL symbol layer collides against other GL symbols. It has no idea the Leaflet pins exist — they are DOM nodes floating above the canvas — so it would happily place a deli's name straight through one.

Root cause

  • Placement in MapLibre runs from the TOPMOST symbol layer down (PauseablePlacement starts at order.length - 1 and decrements), so the last layer added is the first one placed and wins every contest it enters. Verified in the installed maplibre-gl source rather than assumed — the ordering decides the entire scheme
  • The proposal pin is a 34×42 divIcon whose tail tip — the anchor, the point sitting on the location — is at (17, 36). Relative to that anchor the pin occupies y ∈ [−36, +6]

What changed

  • proposal-labels is added AFTER place-labels, so proposals claim their space first and the POI names move aside
  • Each symbol carries a fully transparent 34×42 collision puck (a zeroed RGBA buffer — collision boxes come from an image's dimensions, never its contents), offset by [0, 6] so it coincides exactly with the pin drawn over it. A side effect worth naming: a business name can no longer land underneath a proposal pin, which it could before this layer existed
  • icon-allow-overlap: true with icon-ignore-placement left at its default false. The two are independent — insertCollisionBox is called for the icon regardless of allow-overlap, and only ignore-placement decides whether it lands in the real grid or the ignored one. So the puck is never itself suppressed (the Leaflet pin is drawn whatever MapLibre decides) while still blocking everything else
  • text-optional: true is load-bearing rather than decorative: without it a label that cannot place takes the puck down with it and the pin loses its reserved footprint. With it, a crowded pin keeps its space and simply goes quiet
  • A rank reveal schedule makes the coarse call that collision cannot: two headline proposals at z12, five by z13, ten by z14, everything from z15. Collision thins by geometry; rank thins by importance, and symbol-sort-key: ["get", "rank"] means the proposal with more votes behind it takes contested space

COLOR

The contrast floor found two accents the eye had not

Symptom

"Use the accent at full chroma" is the right instinct and quietly wrong for two of the eight map styles.

Root cause

  • Transit's #3B8EE0 manages only 5.7:1 against the near-black basemap — UNDER the muted place labels' own 7.0–7.9:1. The tier it was supposed to outrank was louder than it was
  • Trees' #5FA052 manages 5.0:1 on the light paper against a POI band of 4.8–5.5:1 — inside the noise
  • A one-directional knob ("deepen on light basemaps") cannot fix a dim accent on a dark one, and a fixed lift toward white would desaturate the accents that were already strong

What changed

  • The correction is a ratio over the place labels, not an absolute number, because what has to hold is the hierarchy: PROPOSAL_CONTRAST_OVER_POI = 1.15. Whatever the POI tier is painted at, a proposal clears it
  • The accent is mixed toward the theme's selection ink only as far as needed. That single rule runs in OPPOSITE directions per basemap for free, because selection is white on the dark themes and near-black on the light ones — it LIFTS transit to 9.6:1 and DEEPENS trees to 6.4:1
  • Accents that already clear the bar are left exactly as authored — the bike green at 11.1:1 and the harbor teal at 9.5:1 are untouched, asserted by a test so a future refactor cannot quietly desaturate every theme
  • PROPOSAL_CONTRAST_MAX_MIX = 0.55 caps the drag: past that a color stops being the map's accent and becomes a tint of the selection color. Better a slightly quiet label that still wears the theme than a legible one belonging to no map in particular

TYPOGRAPHY

Two lines, one symbol, and no bold to lean on

Symptom

The label has to read as a different KIND of thing from a nail salon's name, using a font family that ships in exactly one weight.

Root cause

  • npm run build:glyphs bakes a single SDF stack, Red Hat Mono Regular. There is no bold cut, so every step of the hierarchy has to be made of size, color, spacing and halo
  • It bakes only four Unicode ranges — 0–255, 256–511, 512–767 and General Punctuation 8192–8447. Arrows (↑), geometric shapes (▲ ◆) and even the proper minus sign U+2212 have NO GLYPHS and would render as nothing at all

What changed

  • Uppercase is the tier marker: both other text layers are mixed case, so caps read instantly as a different register without needing a weight. The label is never abbreviated — every one of these strings starts with a verb, and the verb is the entire difference between "Add bike lane" and "Improve bike lane"
  • Size steps clearly above the place labels (10.5–12.5px against their 8.6–10.5), asserted at every zoom by a test
  • The claim comes FIRST, nearest the pin, with the count under it. The other order was built and rejected in the browser: it put the smallest, faintest text in the tightest slot — the few pixels directly under the pin's tail — and made you read a number before knowing what it counted
  • Both lines are ONE format expression with a per-section text-color override, not two layers: a single symbol means a single collision box, so the count can never place without its claim or drift away from it
  • The count is signed because it is a differential (+412), and compacts to +1.6k past a thousand. A test asserts every string this can emit stays inside the four baked glyph ranges
  • Halo is 2.0 at 0.2 blur — heavier and HARDER than the place labels' 1.2/0.3. Measured on the NYC bike map, where the heat under a label is a dense field of saturated green and blue: at 1.2 the type dissolved into it, and a blurred halo only smeared the boundary

FAILS QUIETLY

Four ways this layer can vanish without saying anything

Symptom

Every one of these produces the same symptom — no labels at all, nothing in the console — which is why they are pinned by tests rather than left to review.

Root cause

  • Two zoom curves. MapLibre allows ONE zoom-driven interpolate/step per expression and rejects the whole layer for a second one, as a NON-FATAL style error. This is the same trap placeLabelStyle.ts was split out for; its exported countZoomCurves guard is reused here
  • The zoom-unit off-by-one. minz is a LEAFLET zoom and MapLibre's camera runs one level lower, so the filter must compare against ["+", ["zoom"], 1]. Get it wrong and every label appears one zoom level late — visible only if you are looking for it
  • Puck drift. GraphLayer eases the pins smaller at both zoom extremes via --indicator-scale. If the puck's own ramp drifts from that, the reserved footprint stops matching the pin drawn over it
  • Unbaked glyphs. A tempting ↑412 renders as nothing

What changed

  • proposalLabelStyle.ts holds every expression and formatter as a pure module, with proposalLabelStyle.test.ts asserting: one zoom curve per expression, the zoom + 1 filter shape verbatim, the puck ramp against a re-derivation of GraphLayer's own scale formula, the 34×42/[0,6] pin geometry, and that all emitted text stays in the baked ranges
  • Plus the design invariants that are easy to erode: proposal contrast clears the loudest place label on every style, strong accents stay untouched, the count stays subordinate but above 3:1, and the reveal schedule is monotonic
  • 32 tests in this area; 464 in the suite, all passing

NOT IN THIS COMMIT

The wiring is written and verified, and is still uncommitted

Symptom

This report covers the committed foundation. The layer that consumes it — addProposalLabels in MapLibreBackground and the broadcast effect in GraphLayer — is written, type-checked, and was driven in the browser, but is NOT in the commit.

Root cause

  • Another session has roughly 500 lines of uncommitted arrival-animation and vote-epoch work interleaved in those same two files, including arrivalAnimation.ts, which is still untracked
  • The changes are not separable at hunk granularity — the very first hunk of MapLibreBackground.tsx contains my proposalLabelColors import and their HeatNormalization / arrivalAnimation imports on adjacent lines
  • Staging the whole files would have committed their unfinished work under this message; line surgery across 24 hunks of someone else's in-flight edits is not a call to make unilaterally

What changed

  • The bridge is the existing cross-renderer pattern: GraphLayer dispatches PROPOSAL_LABELS_EVENT on window with the resolved label list, exactly as it already does for BLOCK_VOTES_EVENT and BLOCK_SELECT_EVENT; MapLibreBackground listens and setDatas a GeoJSON source
  • Positions are the pins' settled ones — edge midpoint for a square, rbtpDisplayPos for a diamond — deliberately NOT the transient fan-out overrides. A fan-out only happens where pins are stacked within 26px, which is precisely where all but the top-ranked label is suppressed anyway
  • Rank runs within each family, not across the merged list: a PBTP's count is the net on one hot edge while an RBTP's score sums net across a whole corridor, so ranking them together by magnitude would simply put every corridor above every point. They are interleaved after the fact, ties going to the corridor
  • Station networks are skipped — they turn every edge into a pseudo-winner sharing one label, which would be thousands of identical words; those maps name their stations through the place-label layer
  • One bug found and fixed during review: setData fires sourcedata for its own source, so the not-yet-loaded retry re-applied its own write in an unbroken loop. Guarded by tracking the applied payload identity

+/** Evaluate a plain ["interpolate",["linear"],["zoom"], z, v, …] at one zoom. */
+function rampAt(expr: unknown, zoom: number): number {
+  const e = expr as unknown[];
+  const stops: Array<[number, number]> = [];
+  for (let i = 3; i < e.length; i += 2) stops.push([e[i] as number, e[i + 1] as number]);
+  if (zoom <= stops[0][0]) return stops[0][1];
+  const last = stops[stops.length - 1];
+  if (zoom >= last[0]) return last[1];
+  for (let i = 0; i < stops.length - 1; i++) {
+    const [z0, v0] = stops[i], [z1, v1] = stops[i + 1];
+    if (zoom >= z0 && zoom <= z1) return v0 + ((v1 - v0) * (zoom - z0)) / (z1 - z0);
+  }
+  throw new Error("unreachable");
+}

+/** Parse the two color notations the styles use: "#rrggbb" and "rgb(r, g, b)".
+ *  (Scraping digits with a regex silently turns "#F4F5F0" into rgb(4, 5, 0) —
+ *  the light basemap's paper reads as black and every contrast check inverts.) */
+function parseColor(css: string): [number, number, number] {
+  const hex = css.match(/^#([0-9a-f]{6})$/i);
+  if (hex) {
+    const n = parseInt(hex[1], 16);
+    return [(n >> 16) & 0xff, (n >> 8) & 0xff, n & 0xff];
+  }
+  const rgb = css.match(/\d+/g)!.map(Number);
+  return [rgb[0], rgb[1], rgb[2]];
+}
+
+/** sRGB relative luminance, for the contrast checks below. */
+function luminance(css: string): number {
+  const [r, g, b] = parseColor(css).map((v) => {
+    const s = v / 255;
+    return s <= 0.03928 ? s / 12.92 : ((s + 0.055) / 1.055) ** 2.4;
+  });
+  return 0.2126 * r + 0.7152 * g + 0.0722 * b;
+}
+
+function contrast(a: string, b: string): number {
+  const [hi, lo] = [luminance(a), luminance(b)].sort((x, y) => y - x);
+  return (hi + 0.05) / (lo + 0.05);
+}

+/** sRGB relative luminance (WCAG), for the contrast floor below. */
+function luminance([r, g, b]: [number, number, number]): number {
+  const lin = (v: number) => {
+    const s = v / 255;
+    return s <= 0.03928 ? s / 12.92 : ((s + 0.055) / 1.055) ** 2.4;
+  };
+  return 0.2126 * lin(r) + 0.7152 * lin(g) + 0.0722 * lin(b);
+}
+
+/** WCAG contrast ratio between two colors. */
+function contrastRatio(a: [number, number, number], b: [number, number, number]): number {
+  const [hi, lo] = [luminance(a), luminance(b)].sort((x, y) => y - x);
+  return (hi + 0.05) / (lo + 0.05);
+}
