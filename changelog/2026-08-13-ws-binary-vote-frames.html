The WebSocket vote stream was JSON: a median 89-edge route cast shipped 3,316 bytes to say ~150 numbers, spelling every edge id twice and quoting every one as a decimal string. It is now a canonical binary frame at 508 bytes — 6.5× smaller — with ids sorted and delta-varint encoded, and the vote type hoisted out of every cell. The second half is new: a sync packet the client asks for on foreground and reconnect, carrying only the cells that moved while the tab was hidden. That repair used to be a full /api/graph-votes refetch — 1.78 MB on nyc-bikes, measured against prod today.

THE PACKET

One vote, 508 bytes instead of 3,316

Symptom

Every cast published a JSON delta whose size was dominated by punctuation and repetition, not by information. A median NYC route cast was 3.3 KB; the largest was 37 KB.

Root cause

  • Every edge id was sent twice. edges was always exactly the key set of vtCounts — the client never used it for anything the counts did not already carry
  • Every id was spelled in full, as a quoted decimal string. "3184007":[3,0], is 18 bytes. But a route's edge ids are near-consecutive: the median gap between successive ids in a real NYC cast is 6, and 65% of gaps fit in seven bits
  • The vote type rode as an id AND a label on a packet that only ever describes one vote type, and dir/reversed fed an increment path that has been unreachable since counts became authoritative SETs

What changed

  • Ids are sorted and delta-varint encoded, so a step of 6 costs one byte instead of eighteen. edges is not transmitted at all — the client rebuilds it from the cell ids
  • A frame is a header plus groups, and a group is one vote type's cells at one revision. The vote type, its label and the mode are paid for once per group, not once per cell
  • The decoder returns the same VoteDelta shape the JSON path produced, so applyDeltaToGraphData, the replay ring and gap detection are untouched. This is a transport swap, not a model change
  • Measured on real casts from the local prod-shaped DB: 1 edge 210→45 B, median route 3,316→508 B (6.5×), p90 9,074→1,274 B (7.1×), largest 37,147→4,979 B (7.5×)

BIT BUDGET

Every field, and what happens at its ceiling

Symptom

This codec's direct predecessor — the 53-bit Redis field layout — gave vote_type_id 16 bits. A bulk import pushed vote_types past 65535, the overflow landed on the direction bit at 52, and those votes recorded as DOWNVOTES. Silently.

Root cause

  • A fixed-width field that overflows does not fail; it bleeds into whatever field sits above it. Nothing in the system could see it happen
  • The field that overflowed was a global, monotonically growing SERIAL being carried at a width chosen from how big it was at the time

What changed

  • Growable fields are varints, not fixed widths. A varint is self-delimiting, so an oversized value cannot bleed into its neighbour at all — it is a structural fix for the class of bug, not a wider guess. vtId is a varint; its real max on this deployment is already 75,107, past the ceiling that caused the original bug
  • Growable fields appear once per GROUP at full width, never once per cell. The per-cell fields are the ones that must stay small, so the per-cell fields are the ones that carry no global ids
  • Every varint is bounded at 253−1 — Number.MAX_SAFE_INTEGER, the same ceiling voteKey.ts works to. Out of range raises at encode and at decode. There is no silent wrap anywhere in the codec
  • Fixed bytes are the four header bytes plus mode. magic mismatch, unknown version and unknown kind all raise, and the client answers by falling back to a full refetch — so a future layout change degrades to today's behaviour instead of corrupting counts. Unknown flags bits are ignored, which is what makes adding a flag backward compatible
  • Counts are varints, so 65,536 does not wrap the way 16 bits would. A count can go transiently NEGATIVE under a racing decrement, which an unsigned varint cannot carry — the encoder clamps to 0 (what the client's Math.max(0, …) already does) rather than raising on the vote path

THE SYNC PACKET

Repairing a backgrounded tab for a kilobyte instead of 1.78 MB

Symptom

A hidden tab keeps its WebSocket but misses deltas, and gap detection only fires when the NEXT delta arrives. A reconnect was worse: deltas published while the socket was down were never delivered, and nothing noticed until someone else voted.

Root cause

  • The only repair available was a full /api/graph-votes?format=sparse refetch. Measured against prod today that is 1,781,694 bytes gzipped for nyc-bikes and 184,420 for nyc-walkways — the whole city, to learn about maybe three votes
  • (For the record: the comparison ebook puts that body at ~57 KB. It is not — nyc-bikes has 237,270 voted edges. The 57 KB figure appears to be from a much lighter map)
  • The server kept no history, so there was nothing cheaper it could have sent

What changed

  • publish_delta now records each delta's encoded frame in a Redis sorted set scored by revision (deltalog:<slug>), written in the same call that publishes so the log can never drift from the stream it replays. Bounded both ways — 128 entries and a 900 s TTL, ~120 KB per map — because Memorystore is 1 GB with allkeys-lru and evicting the vote hashes is the failure that matters
  • The client sends {"type":"sync","since":<rev>} on visibilitychange, on pageshow and on every socket open. The reply is ONE coalesced SYNC frame: one group per vote type, counts merged last-write-wins — lossless, because the counts are absolute SETs, the same argument DeltaHub already makes for coalescing its flush window
  • The safety property. A sync may only claim to carry a client forward when the log can PROVE it covers the gap. Every delta claims exactly one revision, so full coverage means exactly head − since logged entries in range. Anything less means a revision moved with no delta behind it — a hydration, a resnap, a manual INCR vote_rev — and the frame is marked TRUNCATED, which the client answers with the full refetch it does today
  • So the packet is strictly an improvement: it repairs the common case cheaply and degrades to the old path, never to a wrong heatmap
  • Measured: after 1 / 3 / 10 / 30 missed votes on different corridors (the pessimistic case — real traffic repeats corridors and repeats coalesce away) the sync frame is 508 B / 2.2 KB / 8.1 KB / 23.7 KB. Against 1.78 MB that is a 219× reduction at ten missed votes

WHAT THE FUZZER FOUND

Three ways a corrupted frame decoded into a different, valid frame

Symptom

The round-trip fuzz test asserted more than round-tripping: that flipping one byte must either RAISE or decode to something that re-encodes to those exact bytes. It failed three times, and each failure was a real hole.

Root cause

  • LEB128 permits redundant encodings. 0x00 and 0x80 0x00 both mean 0, so one flipped continuation bit turned a valid frame into a different valid frame
  • A zero id-delta mid-run landed on the id already in the dict and silently collapsed two cells into one — a frame that decodes fine, with a cell missing
  • Lossy UTF-8 decoding (errors="replace") turned a corrupted label byte into a different label. The client appends unknown labels to its legend, so that would have materialized a phantom proposal type

What changed

  • Varints must be canonical: a multi-byte varint whose last group is zero is refused. That makes the encoding a bijection — one frame has exactly one byte string, so the bytes can be hashed or ETagged, and corruption is far likelier to be rejected than to decode into plausible-but-wrong counts
  • Cell ids must be strictly ascending: only the first cell may have a zero delta (that is id 0)
  • Labels decode strictly; invalid UTF-8 rejects the frame, and the client refetches
  • Plus: no trailing bytes after a frame (a length corrupted SHORT would decode a valid prefix and drop real cells), and length fields are checked against the remaining buffer before anything is allocated
  • All three rules are now first-class tests as well as fuzz invariants, on both implementations

THE GUARD

The 24-bit cliff is still live — and the block layer had no rail

Symptom

Auditing every path a vote_type_id travels for a lingering 16-bit assumption turned up something worse: no 16-bit assumption survives, but the SAME failure mode does, one field over, unguarded.

Root cause

  • vote_types.id is a Postgres int4 SERIAL — it can mint 2,147,483,647. Three packed layouts carry that id in 24 bits: the Redis vote field (vote_store.pack, vt at 51..28), the block aggregate field (block_votes.pack_block_field, vt at 47..24) and the client's store key (voteKey.ts). So the database can mint ids 128× larger than anything downstream can address
  • An id past 24 bits does not round or error — it lands on a direction bit. At vt = 2**24 the vote field's overflow hits DIR_BIT (52) and the block field's hits its direction bit (48). Widening from 16 to 24 in July moved the cliff; it did not remove it
  • vote_store.pack already raised. block_votes.pack_block_field did not — it shifted silently, so vt = 16,777,216 decoded as vote type 0 with the direction flipped. An upvote aggregated onto the block as a downvote. That is the July bug, exactly, still live on the block layer
  • And the failure was doubly quiet: get_or_create_vote_type_id catches everything and return 0s, and a 0 id reads as "untyped vote" downstream. The client then discarded the server's message entirely — throw new Error(`Vote failed: ${res.status}`) — rolled the optimistic apply back, and showed nothing

What changed

  • MAX_VOTE_TYPE_ID = 16,777,215, defined in vote_store.py next to the bit layout that sets it, with the full audit table in the comment. Enforced at the narrowest real limit, not at the widest field or at the DB column
  • The guard is at creation, in get_or_create_vote_type_id, and sits outside that function's try/except so the generic handler cannot turn a hard limit back into a silent return 0. Ordinary DB trouble still degrades to 0; only the ceiling raises
  • It raises a dedicated VoteTypeLimitError whose message names the limit AND the refused label: “Cannot create the vote type “X”: this map service supports at most 16,777,215 distinct vote types and that limit has been reached (id 16,777,216). Existing vote types still work…”. Both request paths — a cast with a free-text suggestion, and map creation with custom types — return it as 507 with vote_type_limit: true
  • pack_block_field now bounds-checks like pack does, so the silent-wrap path is closed as a last line of defence behind the creation guard
  • The client stops swallowing it. castVote.ts reads the server's own message on a failed cast and dispatches vote-rejected; App.tsx feeds it to the existing ErrorToast — the same event-driven route PasscodeGate already uses to reach out of the map subtree
  • For scale: the largest id in the registry today is 75,607, 0.45% of the ceiling. This is a backstop, not a near-term constraint — but so was 65,535, right up until a bulk import walked past it

COMPATIBILITY

Both encodings, one flush, no per-client cost

Symptom

A long-lived tab can hold JS older than the server it is talking to, and the DeltaHub's whole point is that a flush costs one encode per map, not one per client.

Root cause

  • Transcoding per subscriber would have put the cost back exactly where delta_hub.py removed it (finding #4 of the July 8 load test)
  • A hello message sent after connect loses the race with the first flush — the inbound pump only drains once per queue timeout, so which encoding a client got would have depended on timing

What changed

  • The hub builds BOTH payloads once per flush window, and only builds the binary twin if some subscriber can read it. Each subscriber takes the one it can read, so the O(1)-encodes-per-flush property holds
  • Binary capability rides in the handshake (?bin=1), the same way map and token already do — known before the first byte is sent, so it cannot race anything. init echoes back what the server decided
  • A delta that cannot be encoded (no vtCounts) falls the whole flush back to JSON rather than failing it, so one malformed delta can't take down every binary client on the map
  • A client that never announced binary support and asks for a sync is answered with {"type":"resync"} — do the full refetch — rather than being sent bytes it cannot read

Verification

What was run

  • Cross-language parity is test-enforced. The Python encoder writes golden vectors to client-react/src/utils/__fixtures__/wireFrames.json; the TS suite decodes them AND re-encodes them to Python's exact bytes. If either side's layout drifts, one of the two suites fails — the same guard test_vote_codec.py ↔ voteKey.test.ts already puts on the 53-bit vote key.
  • Fuzz, both sides. 2,000 random frames round-trip byte-identically; 2,000 single-bit corruptions either raise or re-encode to the corrupted bytes exactly; 2,000 random byte strings never hang and never throw anything but a WireFormatError. Deterministic seeds — a flaky codec test is worse than none.
  • Server suite: 180 unit tests pass (45 new codec tests, 21 new sync tests). Client: 546 tests pass, 36 of them new, and npx tsc -b is clean — Vite dev never type-checks, and that has broken a client build unseen before.
  • End to end against a live Flask on :5055 with real Redis and Postgres, driving the real WS handler: (1) a binary client gets a 50-byte binary DELTA frame from a live POST /api/vote; (2) a client that missed one cast is repaired by a 44-byte SYNC frame carrying ONLY the two cells that changed; (3) after a bare INCR vote_rev — the hydration/resnap case — the sync comes back TRUNCATED rather than silently short; (4) a client that never announced binary support gets resync and never receives a binary frame.
  • Sizes are measured, not estimated. server/tools/measure_ws_payload.py pulls real edge ids from real casts in the local prod-shaped Postgres and real block ids from the city's edge→block mapping, so the id gaps — the thing delta-varint encoding lives or dies on — are the real ones. The refetch baseline is a live curl against cityedit.org.
  • The guard fires end to end, on a live server. The local dev sequence was pushed with setval('vote_types_id_seq', 16777215) so the next id would be 16,777,216; a cast with a brand-new label came back HTTP 507 carrying the full message, left no vote_types row and no edge_votes row, and a normal cast on an existing type returned 200 immediately after. Sequence restored and the junk row deleted.
  • The boundary is pinned by test, not by comment. test_vote_type_limit.py (15 tests) asserts MAX_VOTE_TYPE_ID equals the narrowest packed field, that the max id still round-trips through all three layouts inside 2^53, and — computing the packed value WITHOUT the bounds checks — that one past the limit decodes as vote type 0 with the direction flipped, on BOTH the vote field and the block field. It also pins that the WS varint is NOT the narrowest link, so the codec in this same change cannot quietly become the limit.
  • Lint is unchanged. GraphLayer.tsx reports the same 14 pre-existing problems before and after; WebSocketContext.tsx the same 2.
  • A concurrent session's work was kept out. server/app.py also carried an unrelated sticker-binding hunk from another session; the diff and the commit were split hunk-by-hunk so only the two WS hunks are mine.
For you

  • Background one of those tabs for a minute while voting in the other, then foreground it: the heat should correct itself with no /api/graph-votes request in the Network tab, and the console should log [ws] sync rev N→M.
  • Kill and restart Flask while a tab is open. On reconnect the tab should log a sync (or a truncated one followed by one refetch) — before this change it would have stayed stale until the next vote.
  • redis-cli incr vote_rev:nyc-walkways, then foreground a tab: expect sync truncated … full refetch in the console. That is the safety path working, not a bug.
  • redis-cli zcard deltalog:nyc-walkways should stay ≤ 128 no matter how much you vote, and redis-cli ttl deltalog:nyc-walkways should be ≤ 900.
  • The vote-type guard, if you want to see it: psql the LOCAL db, select setval('vote_types_id_seq', 16777215), then vote with a label nobody has used. +// Byte-for-byte mirror of server/wire_codec.py — the parity is test-enforced
+// (wireCodec.test.ts decodes golden vectors this repo's Python encoder wrote,
+// the same arrangement voteKey.test.ts ↔ test_vote_codec.py already uses).
+// Read the Python module for the full rationale; the short version:
+//
+//   * A JSON delta spelled every edge id twice (once in `edges`, once as a
+//     quoted key of `vtCounts`) and every id in full. A route's edge ids are
+//     near-consecutive, so ids are sorted and delta-varint encoded here.
+//   * `vote_type_id` is a VARINT and lives once per group, never once per
+//     cell. The 16-bit `vt` field in the Redis codec overflowed into the
+//     direction bit at 52 and silently recorded upvotes as downvotes; a
+//     varint is self-delimiting, so an oversized value cannot bleed into the
+//     neighbouring field at all.
+//   * Every varint is bounded at 2^53-1 (Number.MAX_SAFE_INTEGER), the same
+//     ceiling voteKey.ts works to. Anything larger throws instead of wrapping.

+"""Binary wire codec for the WebSocket vote stream (frame version 1).
+
+Why this exists
+---------------
+The vote stream used to be JSON. A single 89-edge route cast published
+
+    {"type":"delta","rev":41,"edges":[...89 ints...],"m":"bikepaths","vt":15,
+     "dir":1,"reversed":false,"vtLabel":"Protected bike lane",
+     "vtCounts":{"2079":[3,0], ...89 entries...},
+     "blockCounts":{"1841":[3,0], ...~60 entries...}}
+
+which is ~4 KB for ~150 numbers that carry maybe 300 bytes of information. The
+edge ids are transmitted TWICE (once in `edges`, once as the keys of
+`vtCounts`), every id is spelled out in full even though a route's edge ids run
+consecutively, every key is a quoted decimal string, and `vt` is repeated once
+per frame while `vtLabel` is repeated in full.
+
+This codec keeps exactly the same semantics — authoritative post-write
+[up, down] per (edge|block, vote type), applied as an idempotent SET — and
+spends bytes only on what changed.
+
+Two frame kinds share one layout:
+
+  DELTA  the live per-vote packet. One group per source delta, so the client
+         sees the same per-revision stream (and the same gap detection) it
+         always did.
+  SYNC   the catch-up packet requested on foreground / reconnect. Coalesced:
+         one group per vote type, counts already merged last-write-wins, which
+         is lossless because counts are absolute SETs. Repairs a backgrounded
+         tab for ~1 KB instead of a ~57 KB /api/graph-votes refetch.
+
+Layout (all multi-byte integers are LEB128 unsigned varints, little-endian
+groups of 7 bits, high bit = continue):
+
+    FRAME
+      byte 0   magic    u8   0xCE                  (constant)
+      byte 1   version  u8   0x01                  (this layout)
+      byte 2   kind     u8   1 = DELTA, 2 = SYNC
+      byte 3   flags    u8   bit0 = TRUNCATED (sync could not cover `since`)
+      ...      rev      var  head revision this frame describes
+      ...      baseRev  var  revisions (baseRev, rev] are covered
+      ...      nGroups  var  number of groups that follow
+
+    GROUP  (repeated nGroups times)
+      ...      rev      var  this group's revision
+      byte     mode     u8   MODE_IDS value (0..15 today)
+      ...      vtId     var  GLOBAL vote_type_id, full width
+      ...      labelLen var  UTF-8 byte length of the vote-type label
+      ...      label    labelLen bytes
+      ...      nEdge    var  edge cells that follow
+      ...      cells    nEdge x CELL   (edge ids, strictly ascending)
+      ...      nBlock   var  block cells that follow
+      ...      cells    nBlock x CELL  (block ids, strictly ascending)
+
+    CELL
+      ...      idDelta  var  id - previousId; previousId starts at 0
+      ...      up       var  authoritative up count
+      ...      down     var  authoritative down count
+
+Bit budget, and what happens at each ceiling
+--------------------------------------------
+The predecessor of this codec is the 53-bit Redis field layout in
+vote_store.py, where `vote_type_id` was given 16 bits, a bulk import pushed
+vote_types past 65535, and the overflow landed on the direction bit at 52 —
+silently recording upvotes as downvotes. The structural lesson, applied here:
+
+  * A field that can grow is a VARINT, not a fixed width. Varints are
+    self-delimiting, so an oversized value can never bleed into the next
+    field the way a fixed-width overflow does. `vtId` is a varint (its real
+    max on this deployment is already 75107, i.e. past the 16-bit ceiling
+    that caused the original bug).
+  * A field that can grow appears ONCE PER GROUP at full width, never once
+    per cell at a guessed width. The per-cell fields are the ones that must
+    stay small, so the per-cell fields are the ones that carry no global ids.
+  * Every varint is checked against MAX_VARINT (2^53 - 1, JS
+    Number.MAX_SAFE_INTEGER — the same ceiling the existing vote codec
+    respects). Encoding a larger value raises; decoding one raises. There is
+    no silent wrap anywhere in this file.

+  magic      u8, constant. A byte that isn't 0xCE raises WireFormatError; the
+             client treats that as "not our frame" and ignores it.
+  version    u8, 1..255. A version the reader doesn't implement raises, and
+             the client falls back to a full /api/graph-votes refetch — the

+             readers, so adding a flag is backward compatible.

+             outside 0..255 raises rather than truncating.

+             that is never reset; at the observed rate (~15k casts total on
+             the busiest map) 2^53 is unreachable. Above the ceiling the
+             encoder raises, and the client's existing gap detection would
+             force a refetch rather than mis-apply.

+    """Return (value, next_pos).

+    way (0x00 and 0x80 0x00 both mean 0), so a single flipped continuation bit
+    turns a valid frame into a DIFFERENT valid frame — the fuzzer found exactly
+    that. A redundant trailing group is refused here, which makes the encoding
+    a bijection: one frame has exactly one byte string, so these bytes can be
+    hashed or ETagged, and a corrupted frame is far likelier to be rejected
+    than to decode into plausible-but-wrong vote counts."""
+    value = 0
+    shift = 0
+    start = pos
+    while True:
+        if pos >= len(buf):
+            raise WireFormatError("varint runs past end of buffer")
+        byte = buf[pos]
+        pos += 1
+        value |= (byte & 0x7F) << shift
+        if not (byte & 0x80):

+            # information — it is a longer spelling of a shorter number.
+            if byte == 0 and pos - start > 1:
+                raise WireFormatError("non-canonical varint (redundant trailing zero)")
+            break

+        if shift > 56:
