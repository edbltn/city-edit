City Edit · Change log

API latency fixes — kill the per-request DB tax, unblock the gevent hub

2026-07-07 · branch fix/unify-voting
1 2 3 VerificationChecklistFull diff

The per-endpoint latency dashboard exposed a shared floor under every API call: a full-table vote-count aggregate over 1.8M rows ran on the f1-micro Postgres for each request via resolve_map's map lookup — 320 ms medians on endpoints whose real work is sub-millisecond. This lands the fix set: the map query split so single lookups use an indexed count (or none), a 30 s TTL cache that takes Postgres out of the hot path entirely, psycogreen + a real connection pool so one slow query no longer freezes the whole gevent worker, a per-instance maps-list cache, and graph-votes 304s that answer straight from Redis without loading a graph. Verified locally (sub-ms warm endpoints, tests green, 32-greenlet concurrency harness clean); prod deploy pending.

Flask API · resolve_map

1 · The shared floor: a full-table vote count under every request

Symptom

Per-endpoint P99s (new log-based metric, 7-day baseline) showed a ~100–300 ms floor under endpoints whose own work is sub-millisecond: reverse-geocode p50 320 ms (a KD-tree query + ≤5-hop BFS!), and /api/maps tailing to 3.6 s at p95.

Root cause

  • resolve_map() — the first line of every API endpoint — called get_map(slug), and _MAP_SELECT LEFT JOINs (SELECT map_slug, COUNT(*) FROM edge_votes GROUP BY map_slug): a full-table aggregate over ~1.8M vote rows, on the db-f1-micro, per request. The result (voteCount) isn't even read by resolve_map.

What changed

  • _MAP_SELECT split three ways (same column list, so the row shape and _map_row_to_dict are untouched): list keeps the full-table aggregate (list_maps ranks by count), one uses a correlated (SELECT COUNT(*) … WHERE map_slug = m.slug) that walks idx_edge_votes_map for just that map, and light selects 0 AS vote_count for callers that never read it.
  • get_map(slug, with_vote_count=False) → light; the /api/maps/<slug> and by-subdomain config endpoints keep accurate counts via the indexed variant.
  • On top of that, resolve_map's lookup is now behind a 30 s in-process TTL cache (misses included — bots probe random slugs; bounded at 512 entries), so steady-state resolve_map costs no DB round-trip at all. Map-mutating endpoints (create, set-subdomain, promote-vote-types) invalidate their slug; cross-instance staleness is bounded by the TTL.

Flask API · gevent

2 · One slow query froze the whole instance

Symptom

P99s across unrelated endpoints moved together: whenever the 3.6 s maps aggregate (or any slow query) ran, every other in-flight request on the instance stalled behind it.

Root cause

  • Prod runs one gunicorn gevent worker, but psycopg2 is a C extension: without a wait callback it blocks the entire event-loop hub for the duration of every query. Concurrency existed in name only wherever Postgres was touched.
  • The DB layer used a single shared connection — which was only safe because the hub blocked. Making psycopg2 yield without fixing that would let two greenlets interleave on one connection ("another command is already in progress").

What changed

  • psycogreen installs psycopg2's gevent wait callback — guarded by monkey.is_module_patched("socket") so plain python app.py local dev is untouched.
  • The shared connection became a ThreadedConnectionPool(1, 5) (5 × 4 max instances stays under the f1-micro's ~25-connection ceiling), with a brief wait-and-retry when the pool is drained and drop-on-OperationalError so a dead connection isn't returned to the pool.
  • Proved under a monkey-patched runtime: 32 greenlets — indexed reads, full-table aggregates, pg_sleep writers — completed interleaved in 0.63 s with zero errors and the wait callback verified active.

Flask API · endpoints

3 · Endpoint-level: shared maps-list cache, 304s that skip the graph load

Symptom

/api/maps re-ran the ranking aggregate for every distinct visitor (HTTP max-age=60 only helps repeat visitors), and /api/graph-votes p95 hit 15 s: it called ensure_loaded() before the ETag check, so on a cold instance even a would-be-304 paid a 10 s+ graph load.

Root cause

  • Browser caching is per-visitor; the server recomputed the same ranked list for each one.
  • The graph-votes revision (its ETag input) lives in Redis — the graph itself is only needed to build a response body, never to conclude the client's copy is current.

What changed

  • /api/maps keeps one enriched list per instance for 60 s (same horizon as its Cache-Control), invalidated by map creation via invalidate_map_cache.
  • /api/graph-votes computes rev + ETag from Redis first and answers 304 before touching the graph; ensure_loaded() moved after the conditional so only actual body builds load it.
