Click-to-explode works for route-based top proposals — one cluster engine for both pin kinds

2026-07-14 · branch fix/unify-voting
1 2 VerificationChecklist

Clicking a crowded stack of proposal pins is supposed to fan it out into a pickable grid before any side effect — but the entire fan-out machinery lived inside the point-pin (indicatorMarkers) memo, which early-returns when a map has no point-based winners. On all-route maps (chicago-bikes: 20 diamonds, 0 squares) the exploder was therefore never installed: diamond clicks selected the top-of-stack corridor blind, and bare-map taps over a stack dropped a start pin. The fix extracts the machinery into a clusterEngine memo owned by neither pin kind, which assigns the exploder refs unconditionally (also killing a stale-closure hazard after mode switches empty the winners list). Both marker memos now consume the same engine; the diamond markers and MapView are untouched. Verified live: diamond-only stacks explode, fanned picks select, bare-map taps near stacks no longer place starts, and mixed square+diamond stacks still fan out together.

Diagnosis · why the two pin kinds diverged

1 · The exploder lived inside the point-pin memo

Symptom

Clicking a crowded stack of proposal pins fans it out into a pickable grid (“click to explode”) — but only when a point-based top proposal (PBTP square) existed. On a map whose top proposals are all route-based (RBTP diamonds — e.g. chicago-bikes, whose 714 K imported votes are all route-kind), clicking a stack of overlapping diamonds selected whichever sat on top, blind.

Root cause

  • The cluster machinery — the clusterables list, clusterAround(), spreadCluster(), and the explodeClusterAt() gate — was born with the PBTP squares and lived inside the indicatorMarkers memo. When RBTPs were added, they were wired in parasitically: the PBTP memo pushed the diamonds into its clusterables, and published the gate on two refs (internalExploderRef for the diamond markers' own clicks, clusterExploderRef for the host's path taps and drag-hover).
  • But the host memo early-returns before those refs are assigned: if (source.length === 0) return null — no point-based winners, no markers to render, so also no exploder for anyone. Diamond clicks fell through their internalExploderRef.current?.() guard (still null) straight to corridor selection, and bare-map taps over a stack placed a start pin instead.
  • Worse than never-installed: stale. When winners transiently empty (a theme/mode switch resets them; votes reload), the refs kept the previous closure — an exploder frozen over the OLD clusterables at their OLD positions — so explode behavior after a mode switch depended on what the last non-empty render happened to see.
  • So the observed rule “explode only works when a point pin is around” was exactly the code structure: the shared gesture was owned by one of the two marker kinds.
Fix · GraphLayer.tsx

2 · One clusterEngine memo, owned by neither pin kind

Symptom

The fan-out machinery needed a home that exists whenever either pin kind exists.

Root cause

  • Extraction, not rewrite: the cluster functions were already kind-agnostic (spread keys carry the kind: e<edgeIdx> vs r<id>); only their placement gated them on squares.

What changed

  • New clusterEngine useMemo, hoisted above both marker memos. It computes placed (each square/station resolved to its edge midpoint) and clusterables (squares and diamonds at their settled display positions), and defines clusterAround / spreadCluster / explodeClusterAt — all moved verbatim.
  • The exploder refs are assigned unconditionally on every engine run — with zero clusterables the gate still exists and simply returns false — so they can never be null-on-a-diamond-map or stale-after-a-mode-switch again.
  • indicatorMarkers (the PBTP memo) now consumes { placed, clusterAround, spreadCluster } from the engine and keeps only rendering: heat ranking (now computed from placed), icons, role tinting, its handleClick — whose cluster-detection body is unchanged.
  • The diamond markers and the host (MapView) are untouched: they already called the gate through the refs; the refs just finally always point at a live one. Dependency arrays tightened accordingly (winners/routeProposals/applySpread/stationLabel moved to the engine; the marker memo keys off clusterEngine).

  • tsc --noEmit clean.
  • Driven in the running dev app (Vite + host Flask + Redis, Chrome). Repro map chicago-bikes: 20 RBTP diamonds, 0 PBTP squares — the exact state where the exploder was previously never installed.
  • Diamond-stack click → the stack fanned out (container got votes-spreading; 3 markers lifted into the 500000+ fanned z-band in a 38 px grid) and the click was consumed — no blind corridor selection. Console: [proposals] diamond click 2fb8434d override=false.
  • Picking a fanned diamond → selected that corridor: URL gained the forced-corridor token (…,f2fb8434d;…), Start/End populated, the “TOP ROUTE PROPOSAL · Improve bike lane · Selects 236 blocks” card opened.
  • Bare-map tap just off a diamond-only stack (the clusterExploderRef path through MapView) → exploded 4 diamonds, and did NOT place a start pin.
  • Transient snap-back intact: unhovered spread collapsed after ~2.2 s (SPREAD_DURATION_MS), votes-spreading cleared, 0 fanned markers.
  • Regression, mixed cluster on nyc-bikes (8 squares + 20 diamonds): clicking an overlapping square+diamond stack fanned out 3 icons — 1 diamond + 2 squares — together in one grid.
For you

Manual checklist

  • Open http://localhost:3000/m/chicago-bikes (all-route map): click any overlapping pair of diamond pins — they should fan out into a grid instead of opening a corridor.
  • Click one of the fanned diamonds — the corridor should select (start/end pins at its anchors, route-proposal card open).
  • With no route active, click the map just beside (not on) a diamond stack — it should still fan out rather than drop a start pin.
  • On http://localhost:3000/m/nyc-bikes, click a stack where a square and a diamond overlap — both kinds should fan out together in one grid (no regression).
  • Switch modes on a multi-mode map and immediately click a stack — it should explode at the current positions (the stale-exploder case).
