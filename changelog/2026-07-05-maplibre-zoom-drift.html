MapLibre ↔ Leaflet position drift — zoom off-by-one + riding the zoom animation

2026-07-05 · branch fix/unify-voting
1 2 3 VerificationChecklist

The “position drift” after the icons + heatmap zoom-rescale work was two separate camera bugs between the two renderers that now share the screen: MapLibre (base map + block heat) ran at 2× Leaflet's scale because the two libraries define zoom against different tile sizes, and during zoom animations the GL map froze while the Leaflet layers glided — Leaflet suppresses move events mid-animation. Both fixed in MapLibreBackground; measured to sub-pixel in the live app.

Client · camera sync

1 · The drift itself: same zoom number, 2× the scale

Symptom

Everything Leaflet draws — top-proposal pins, route lines, hover highlights — sat off its street on the MapLibre base map. The offset was zero at the screen center and grew linearly toward the edges, and it changed as you panned or zoomed: classic “position drift”. Measured in the live app: a point 0.01° from center projected 117 px away in Leaflet but 233 px away in MapLibre — exactly 2×.

Root cause

  • Leaflet and MapLibre define zoom against different world-tile sizes: Leaflet's world at zoom z is 256·2^z px, MapLibre's is 512·2^z px. The same numeric zoom therefore renders MapLibre at exactly twice Leaflet's scale.
  • syncCamera passed leafletMap.getZoom() straight into ml.jumpTo(...), and the constructor did the same with CONFIG.initialView.zoom. Centers matched, scales didn't — so the two renderers agreed only at the screen center.
  • This only became visible now: until commit a1fc806 the opaque Leaflet raster fallback painted OVER the MapLibre canvas in local dev, so the visible base map was Leaflet's own tiles (self-consistent by construction) and the mismatch was hidden.

What changed

  • New module constant LEAFLET_TO_MAPLIBRE_ZOOM = 1 with the why, subtracted in both places that drive the MapLibre camera: the map constructor and syncCamera's jumpTo.
  • Verified live: leaflet 14 / maplibre 13, and the projection residual for off-center probe points dropped from hundreds of px to < 1 px (float rounding), before and after pan/zoom.

Client · zoom animation

2 · Mid-zoom drift: the GL map froze while Leaflet glided

Symptom

During a wheel/button zoom, the icons and heat canvas rescale smoothly (last workstream) but the MapLibre base map + block heat stayed FROZEN for the 250 ms animation, then snapped to the target view — the layers visibly drifted apart mid-zoom on every single zoom step.

Root cause

  • During its animated zoom Leaflet suppresses move events: _animateZoom calls _move(center, zoom, undefined, supressEvent=true) at animation start, and the only real move fires 250 ms later in _onZoomTransitionEnd.
  • syncCamera only listens to move, so the GL camera held the OLD view for the whole transition while every .leaflet-zoom-animated element rode a CSS transform transition to the new one.
  • (Pinch zoom was never affected: Leaflet's TouchZoom fires per-frame move events, which keep jumpTo live.)

What changed

  • New zoomanim handler rides the animation the same way the heat canvas does: it maps every current container point p to its target-frame position q + p·scale (where q = project(nw, z') − project(center', z') + size/2 and scale = 2^Δz) and sets that as a CSS transform on the GL container with Leaflet's exact transition — transform 0.25s cubic-bezier(0, 0, 0.25, 1) — so base map, block heat, heat canvas and icons all tween on the identical curve.
  • On zoomend the transform is cleared in the same tick as the final move's jumpTo: MapLibre re-renders in its own rAF (before paint), so the crisp final frame and the cleared transform land in the same compositor frame — no flash.
  • Guarded by Leaflet's _animatingZoom flag so pinch-zoom and flyTo (which sync per-frame via move) never fight the transition.
  • transformOrigin: "0 0" added to the container so the scale is about the viewport's top-left corner, matching the transform math.

Client · deep zoom

3 · Follow-on: don't lose the base map at deep zoom

Symptom

With the camera now offset by −1, the old maxzoom: 19 on the raster LAYER would have blanked the base map at Leaflet zooms ≥ 20 (the app allows 21) — a MapLibre layer-maxzoom HIDES the layer once the camera passes it.

Root cause

  • CartoDB serves tiles up to z19. The cap belongs on the SOURCE, where it means “overzoom (stretch) z19 tiles beyond this” — the GL equivalent of Leaflet's maxNativeZoom — not on the layer, where it means “hide me”.

What changed

  • Moved maxzoom: 19 from the carto-tiles layer onto the carto-base source (and dropped the layer's redundant minzoom: 0).

Verification

What was run

  • Quantified the bug before fixing: injected probe points via the browser console — dx/dy between lm.latLngToContainerPoint and ml.project was 0 at center, 116/-154 px at +0.01°, -350/-461 px at ±0.03° (exactly 2× slope). After the fix: < 1 px everywhere.
  • Exercised zoom in the live app (zoom control + reloads): cameras stay locked (leaflet z / maplibre z−1) and the projection residual stays sub-pixel after every zoom.
