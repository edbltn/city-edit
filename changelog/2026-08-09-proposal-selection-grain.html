The pin and the card now agree on what you selected

2026-08-09 · branch main
The card and the pin asked different questions Widening the ring must not widen click-through A corridor you traced most of read as untraced VerificationChecklistFull diff

Two surfaces described the same selection and disagreed about it. Run a route through a point-based top proposal and the card listed it, badged it and counted its votes — while its pin stayed dark, because the card asks at block grain and the pin asked whether the winner’s own edge was on the routed path. A junction block holds dozens of stubs and a route crosses two, so the pin’s test missed nearly every intersection proposal a route ran through. The ring now comes from the same block union the card badges; the narrow test survives for one job only — deciding click-through, which is safe only where a polyline really lies underneath. The corridor diamonds had the same disagreement one family over: they demanded full block coverage, which looks symmetric with the point rule but is not — a point has one block, so any overlap is already full coverage for it. Coverage is now a threshold behind one shared predicate, so the pin, the card header and the row badge cannot drift apart again.

THE BUG

The card and the pin asked different questions

Symptom

Run a route through a point-based top proposal and the route card lists it, badges it as a top proposal, and folds its votes into the row counts — while the pin sitting right there on the map stays dark. Reported for route-based proposals running through point ones; it is really every selection.

Root cause

  • The card asks at block grain: topKindsFor materializes the path into whole blocks and badges any winner whose edge is in that union
  • The pin asked a much narrower question: is the winner's own edge on the routed path (direction twins forgiven)?
  • A junction block is not one segment — it holds every stub radiating from the intersection, and a route crosses exactly two of them. On nyc-proposals the block under “Fix dangerous intersection” holds 38 edges / 19 distinct segments; the odds of the route traversing the one the vote landed on are about 2 in 19
  • So the narrow test missed nearly every intersection proposal a route plainly ran through — exactly the proposals a point-kind vote type produces

What changed

  • The ring now comes from onSelectedBlockSet: winners sitting on any block the selection touches — the same union the card badges
  • Both sets are built in one pass over winners, so the pin and the badge can only ever be computed from the same inputs
  • Reproduced and then re-checked in the running app: the card badged the row and 0 of 21 icons carried is-selected; after the change, exactly 1 does, and it is the badged type

THE CATCH

Widening the ring must not widen click-through

Symptom

The obvious fix — point onPath at the block union — would have broken the pointer, quietly. That flag does two jobs at once.

Root cause

  • onPath also drives passthrough: an on-path pin is pointer-events: none so the route polyline underneath it owns the gesture (drag → ghost mid, tap → restart from here)
  • That is only safe where a polyline really is underneath. A proposal on a crossed junction block sits beside the route, not on it — made click-through, it would have become simply dead to the pointer

What changed

  • Two sets, two jobs, documented as such at the declaration: onPathEdgeSet (exact, twin-forgiving) keeps click-through and the exploded-icon mid-drag; onSelectedBlockSet (block grain) drives the ring and nothing else
  • onSelectedBlock is deliberately !onPath && … — the two are disjoint, so reading the code you can see which pins stay interactive
  • A proposal the selection covers but does not run over therefore reads selected and stays clickable, which is the behaviour you want: it is the thing you would click next

THE SIBLING

A corridor you traced most of read as untraced

Symptom

Run a selection along part of a corridor without covering all of it: the point pins along the way light up, and the corridor's own diamond stays dark. Flagged in the original report as “possibly related” — it is the same disagreement, one family over.

Root cause

  • isRouteCovered demanded every block of the corridor hold a selected edge
  • That looks symmetric with the point rule and is not: a point proposal has one block, so any overlap is already full coverage for it. Only corridors were ever held to the strict bar
  • And full coverage barely survives the ends — a route along a corridor starts and stops mid-corridor, or OSRM clips a junction block at a turn

What changed

  • Coverage becomes a ratio with a threshold: ROUTE_SELECTED_MIN_COVERAGE = 0.6. Ran along most of it → selected; merely brushed it → not
  • One predicate is shared by all three surfaces that answer “what does this selection stand for” — the diamond's ring, the route card's header, and the card's route badge — so they cannot drift apart the way the pin and the card just did
  • The header now takes the best-covered corridor rather than the first in rank order, because with a threshold several can qualify at once
  • isRouteCovered keeps a minRatio parameter, so a caller that genuinely wants all-of-it can still ask for it
