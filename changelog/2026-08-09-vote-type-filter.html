The vote-type dropdown becomes the map's legend

The map drew 17 vote types at once and offered no way to name them, weigh them, or look at one without the others — the only per-type list in the app was a cast-target picker that hid half of them and vanished until you had a selection. So the dropdown becomes the legend: every type on the map, with its icon, its name, its live net support, a checkbox to show or hide it, and a hover only to isolate it. Toggling reaches all four things that draw vote signal — block heat, the canvas heatmap, the square point pins and the diamond corridors — and is applied before selection, so hiding sixteen of seventeen types promotes the survivor’s runners-up rather than emptying the map. Casting always un-hides the type you voted for, because a filter plus a vote button is otherwise a trap.

THE PROBLEM

The map had icons but no key

Symptom

Every top-proposal pin on the map carries a vote-type icon, and every block's heat is the differential of some vote type — but nothing on screen said which types existed, how much support each had, or let you look at one without the others. On nyc-proposals that is 17 types stacked into one indivisible picture.

Root cause

  • The only per-type list in the app was the vote-type dropdown — and it was a cast-target picker, opened to answer “what am I voting for”, not “what am I looking at”
  • It listed only the types castable in the current selection mode, so half the map's proposals were never named anywhere
  • The topbar legend named the tools (start · selection · end) and one aggregate Votes swatch — nothing about the vote types the swatch was actually made of
  • The two lists were the same list, drawn from the same icons, sitting 400px apart

What changed

  • The dropdown becomes the legend: one panel, every vote type on the map, with its icon, its name and its live net support
  • Each row carries the two things you can do with a legend entry — a checkbox (show/hide it on the map) and the row itself (make it what you're voting for)
  • A hover-revealed only on each row isolates that type; the header carries N/M and an All / None toggle
  • Rows whose kind doesn't match the current selection stay listed and toggleable under a divider — their proposals are on screen, so hiding them has to be possible

STATE

Hidden labels, not visible ones

Symptom

A filter needs to be readable from React (the panel) and from three hot paths that never re-render for it (the canvas heatmap, the PBTP scan, the RBTP job). And it has to survive vote types appearing while you look at the map.

Root cause

  • There is no global store in this client — map config is a module singleton read through a static context, and GraphLayer works through refs precisely to stay out of React's render path
  • Storing the visible set would make every newly-arriving vote type invisible by default: a custom suggestion someone casts while you watch would silently never appear

What changed

  • map/voteTypeFilter.ts holds the HIDDEN labels. Empty set = show everything, and a type nobody has seen yet is visible without anyone opting it in
  • Module-level singleton + subscribe(), so hot paths call isVoteTypeVisible() synchronously and the UI binds through useSyncExternalStore
  • map/voteTypeRegistry.ts answers the other half — which types exist and what each is worth — merging the map's authored types, every label with live votes, and every label cast this session
  • Scoped per map slug in sessionStorage: filtering is a gesture for this visit, not a durable preference that leaves someone staring at an empty map in a month

THE RENDER PATHS

Four places draw vote signal; all four had to agree

Symptom

“Only show these types” is not one switch. Block heat, the canvas edge heatmap, the square point pins and the diamond corridors are computed by four different pieces of code from three different arrays.

Root cause

  • Block heat is topProposalDiffs — the max differential across a block's types, indexed by the block legend
  • Canvas heat (no-block maps) reads edge_votes, a precomputed net across ALL types — there is no per-type array to filter
  • PBTP pins come from selectTopProposals, RBTP corridors from createRouteProposalJob — both already carrying a label predicate, for kind

What changed

  • topProposalDiffs takes an optional legend mask: rank only visible types, and go cold (0) when none of a block's types is on
  • The untyped fallback is suppressed while filtering — a legacy block's total can't be attributed to a type, so painting it would be heat nobody asked for
  • The canvas re-sums per-type nets into a filtered array, cached by (vote revision, filter version) and skipped entirely when nothing is hidden
  • Both proposal families take an isVisible predicate, applied before selection rather than to the finished list — so hiding 16 of 17 types promotes the survivor's runners-up into the freed slots instead of leaving the map near-empty
  • One subscription in GraphLayer fans a toggle out: heat repaints immediately (cheap re-derive), pins follow on an urgent recompute

THE GUARANTEE

You can never vote into a void

Symptom

A visibility filter plus a vote button is a trap: hide a type, vote for it, and the map does not move. The user has no way to tell that from the vote having failed.

Root cause

  • The filter is per-label and casting is per-label, but nothing connected them
  • Separately, a brand-new custom suggestion was invisible to the picker until the next map-config fetch — the server reports custom types back in searchVoteTypes, which the client holds as a snapshot taken at page load

What changed

  • castVotes now always ensureVoteTypeVisible(label) — casting is the strongest statement that a type matters to you, so it clears any toggle hiding it
  • It also registerVoteTypeLabel(label), putting a fresh custom type into the searchable list and the legend on the spot
  • Both run before the POST, so the UI reacts to the press, not to the round-trip
  • Committing a typed Suggest: “…” registers it too — an explicit act, unlike every string typed on the way there

PLACEMENT

A legend you can't open isn't a legend

Symptom

The vote-type control lived in .vote-switcher-group, which was hidden-reserve'd (invisible, no pointer events) until you had something to vote on. As a picker that was right. As the legend it is fatal — the map's key would be unreachable until you drew on the map.

Root cause

  • The gate encoded the control's old single meaning: no selection, nothing to cast, nothing to pick

What changed

  • The gate comes off; the group is always visible. Cast −/+ and Clear are untouched — they are still the things that need a selection
  • The prefix label goes Vote: → Proposals:, which names both jobs: the proposals on the map, and the proposal you're voting for
  • A filtered map reads exactly like an empty one, so the collapsed control carries an accent N/M badge even with the panel shut

REVISION

Two families, two headings, one column of eyes

Symptom

First pass headed the panel Shown on map · N/M · All / None and split it with a divider that renamed itself as you drew. One global count and one global All / None were the wrong grain, the divider read as an afterthought, and a checkbox is a form control — not what “is this drawn on the map” looks like.

Root cause

  • The split was on castable right now, so a corridor type changed house the moment you finished drawing a route — the heading moved under the reader
  • A single N/M spanning the whole panel could not say which half was turned down — “8 of 17” reads the same whether you hid the pins or the corridors
  • One global All / None is the wrong grain: the useful gesture is “all the corridors” or “all the pins”, not “everything”

What changed

  • Split by proposal FAMILY instead — Point proposals and Route proposals, headings that never move. The family you can cast into leads
  • Each heading carries its own show-all / hide-all eye, in the same left column as the rows' eyes, so the section control and its members read as one unit
  • From a mixed section that eye SHOWS everything — the recovering direction; a blank map is the outcome worth making people ask for twice
  • Every toggle is now the conventional eye / eye-with-slash. Deliberately NOT restyled into the app's square-capped house language: this control's job is instant recognition
  • An All proposals master row sits above the families — the same control at a wider scale — and is suppressed on single-family maps, where it would only shadow the one section's own eye
  • Each heading carries (n/N shown) for its own group, which is the grain that was missing: one global count said nothing actionable, while a per-family count tells you which half of the map you have turned down
  • The collapsed field keeps a struck-through eye rather than a number — it has room for one signal, and filtered is the one that matters there
  • New setVoteTypesVisible commits a whole section in ONE write, so a 12-type family costs one repaint and one recompute rather than twelve

For you

Manual checklist

  • Open http://localhost:3000/m/nyc-proposals and click Proposals: — expect a panel headed SHOWN ON MAP 17/17, one row per vote type with a checkbox, icon, name and support count.
  • Uncheck two or three types. The heat should change immediately; the pins and corridors follow a beat later (they need the full edge-table scan).
  • Hover a row and click only — the map should collapse to that one type, and the header should read 1/17 in the accent color.
  • Close the panel and confirm the collapsed control still shows the accent 1/17 badge — this is the thing that stops a filtered map looking like a broken one.
  • Press All and confirm the map comes back exactly as it was.
  • Now the guarantee: hide a type, select it as your vote target, place a point and press +. It should re-check itself and reappear.
  • Type a brand-new suggestion, cast it, then reopen the panel — it should be listed and searchable without a page reload.
  • Scroll to the divider (Corridor proposals · on the map, vote elsewhere) and confirm those rows still toggle but don't become your cast target.
  • Reload the page with a filter active — it should persist (sessionStorage, per map). Open the map in a new tab and confirm it starts unfiltered.
  • Judgement call worth your eye: None hides everything and blanks the map. It is reversible and the badge reads 0/17, but tell me if you'd rather it wasn't offered.

+    if (!label || seen.has(label)) return;

+  for (const vt of cfg?.searchVoteTypes ?? []) if (nets.has(vt.label)) push(vt.label);

+  for (const label of sessionLabels) push(label);
