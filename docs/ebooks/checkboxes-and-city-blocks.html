Checkboxes and City Blocks

One Million Checkboxes served 650 million toggles from eight droplets for about $800. City Edit serves a few thousand people a week from Cloud Run and still takes seconds to paint. The two systems are not competitors — they are opposite shapes, and reading the shape is what tells you which of City Edit's remaining levers are real.

Chapter 01

The two shapes

Both systems are "a shared mutable thing, live, in a browser." That similarity is why the comparison is worth making and also why it misleads if you stop there. The load characteristics come almost entirely from one number: how big is the thing a client must hold before it can render anything at all?

For OMCB that number is a megabit. One million booleans is 125 KB dense, and Hamy didn't even send it dense — clients got [[CHECKED], [UNCHECKED]], two lists of indices, which on a half-checked board is worse than the bitset but still trivially small. Everything after that is delta.

For City Edit that number is the NYC walk graph: roughly 1.3M nodes and 3.3M edges, shipped as the GTB2 binary blob — 50 MB raw, 15.5 MB brotli. The mutable part, the votes, is smaller than OMCB's entire state: about 57 KB in the format=sparse body. City Edit's problem has never been the shared mutable thing. It's the immutable substrate the shared mutable thing is indexed against.

Hold that asymmetry through the rest of this. It reverses almost every instinct you would import from the OMCB write-up: broadcast fan-out is not City Edit's problem, a Go rewrite would buy almost nothing, and the single most valuable thing in Hamy's post — the last paragraph, about scoping updates to the viewport — is the one City Edit has already done for two of its three payloads and not yet for the one that matters.

Chapter 02

OMCB, faithfully

The write-up is short and the architecture is smaller than the traffic suggests. Reconstructed:

The two failure modes he names are worth quoting in effect. First, the fan-out arithmetic: "one update leads to n fanout." With enough concurrent clients this saturates before anything else does, and the mitigations he observed in production were both lossy — cap the bandwidth (drop updates) and periodically re-push full state to resynchronise the clients that fell behind.

Second, and this is the sentence to actually take away: the boxes a client renders were already viewport-scoped by react-window, but the boxes it receives never were. His estimate for scoping the stream to the visible range plus a buffer: ~99% less update bandwidth. He also notes the HTMX polling variant was "highly cacheable, client can ask for just what it needs, no wasted bw sending data clients don't need" — at the cost of seconds of latency instead of real time.

The transferable claim

The expensive thing is not the update rate and not the language. It is sending each client bytes describing parts of the world it is not looking at, from a machine you pay egress on. Everything actionable in this book is a restatement of that against City Edit's numbers.

Chapter 03

City Edit as it stands

You built it, so this chapter is a ledger, not a tour. The point is to fix the numbers in one place so Chapter 7 can point at them.

Serving topology

One Cloud Run service, desire-path-mapper, runs nginx and gunicorn side by side under supervisord in the same container. OSRM is its own service so its 1.6 GB of MLD files don't sit on the app's budget. Redis is Memorystore, Postgres is Cloud SQL. There is no CDN and no load balancer — a google_cloud_run_domain_mapping points the domains straight at the service.

200 × 8 ≈ 1600 concurrent viewers before saturation, and the comment in main.tf:328 is right that the ceiling is viewers, not RPS — every WebSocket holds a concurrency slot for its lifetime.

The cold-load waterfall, before and after the July work

The changelog/2026-07-23-coldload-swr.html measurements are the best data in the repo. Three headless runs on a fresh profile against prod nyc-bikes: cold 8.5–9.9 s, warm ~950 ms. Three fat terms, fully serialised, and the fattest one — the ~6 s vote array build — could not even begin until the topology had finished downloading.

Where the client's work goes after the bytes land

Even with a warm IndexedDB topology, the client still does real work before it can hit-test. GraphLayer.tsx:1947–1975 builds the node adjacency, the block index, then the edge and node spatial indexes — the last two yielding to the main thread every 120,000 items:

client-react/src/components/GraphLayer/spatialLookup.ts:178

export const INDEX_YIELD_BATCH = 120_000;
// …
if (i > 0 && i % INDEX_YIELD_BATCH === 0) await yieldToMain();

On 3.3M edges that is ~28 yields for the edge index and ~11 for the nodes, all on the main thread, all after the download. It's correctly sliced so it doesn't jank the paint — but it is still serial with everything else the main thread wants to do.

Read the "Served by" column as the finding. Every byte in the first five rows leaves the same Cloud Run instance, in us-central1, over the same single gevent worker's nginx. The one row that comes off a CDN is the one you don't own.

And note the perverse ordering: the payload with the strongest immutability guarantee in the whole system — the topology blob, byte-identical for every visitor to a given graph version, already content-addressed by ?v= — is the one with no edge in front of it. The tiles, which do have a caching tier, are the ones already scoped to a viewport and therefore cheap.

Chapter 05

Convergent evolution

Four places where the two stacks arrived at the same answer from opposite directions. These are worth naming because they're the parts you should stop optimising — they're done, and OMCB's experience confirms the shape at a scale City Edit will not see.

1 · Batch to Redis, emit a delta, fan out from one listener

Hamy: "Change is batched to Redis. Redis emits a delta. Servers get delta and push it to attached clients." City Edit reached the identical inversion in server/delta_hub.py after finding #4 of the July 8 load test: before it, every WebSocket client held its own Redis pubsub connection and its own 10 Hz polling thread.

2 · Bit-packed keys instead of structured records

OMCB packs a board into index lists. City Edit packs a vote into a single 53-bit integer that fits Number.MAX_SAFE_INTEGER, so the Redis field key, the client's localStorage key and the wire codec are the same number:

server/vote_store.py:152–195 · mirrored in client-react/src/utils/voteKey.ts

#   bit  [52]      direction    (0 = up, 1 = down)
#   bits [51..28]  vote_type_id (24 bits)
#   bits [27..24]  mode         (4 bits)
#   bits [23..0]   edge_id      (24 bits)
def pack(edge_id, mode, vt_id):
    return (vt_id << 28) | (mode << 24) | edge_id

The failure mode is worth remembering as a general lesson about packed layouts: vt was 16 bits until July, vote_types is a global SERIAL, a bulk import pushed ids past 65535, and the overflow bit landed exactly on the direction bit — silently recording every such vote as a downvote.

3 · Snapshot + delta, with the client reconciling forward

Both systems serve a possibly-stale full state and let deltas carry the client forward. City Edit's version is more disciplined than OMCB's, because it has to be: the snapshot is debounced (2.0 s), and the ETag is computed from the served entry, never the live revision —

server/app.py:2223–2234

def _graph_votes_etag(slug, mode, entry, gzipped, sparse=False):
    """ETag derived from the SERVED entry (its rev + blocks stamp), never
    from the live revision — the etag must always describe the body it
    rides with (a live-rev etag over a debounced body is the
    304-pins-stale-body bug of the blocks re-bake incident)."""

Plus X-Vote-Rev / X-Vote-Rev-Current so a page load — which has no deltas to reconcile from — can notice it is behind and schedule exactly one refetch. That's the part OMCB solved by pushing full state to everyone periodically.

4 · Viewport rendering that isn't viewport fetching

react-window renders only visible checkboxes but receives all updates. City Edit's MapLibre layers render only the visible tiles — and for basemap, blocks and places, only fetch the visible tiles. For the topology, it fetches the whole city. Same gap, different payload. Hamy's ~99% estimate is the reason Lever 2 exists.

Chapter 06

Five real divergences

AxisOMCBCity EditConsequence
What's big Nothing. 125 KB total. An immutable 15.5 MB substrate per city. OMCB optimises the stream; City Edit must optimise the first transfer.
Fan-out direction Server → all, continuously. n clients × every update. Server → subscribers of one map, merged every 100 ms, ~145 edges per cast. Fan-out is a solved, small cost here. Do not spend effort on it.
Statefulness of a request Stateless app servers over a shared Redis. Any droplet serves any client. Instances hold multi-GB resident graphs and per-instance vote snapshot caches. Scale-out is expensive: each new instance pays a graph load and rebuilds its own snapshots.
Concurrency model ~8 processes across 8 boxes; Go goroutines after the rewrite. One gevent worker per instance, 8 instances max. Python, GIL-bound on every C-extension call that doesn't yield. A single non-yielding operation head-of-line-blocks an entire instance's 200 concurrency slots.
Edge DO egress, no CDN, and the author's regret is about the price of that egress. Cloud Run domain mapping, no CDN, and the cost is latency more than money. Same missing tier, different bill. Both authors should have put a CDN in front.

Row four deserves elaboration, because it's the one that quietly caps everything. Under one gevent worker, concurrency exists only where the code yields. That is why server/database.py needed psycogreen — without the wait callback, psycopg2 froze the whole hub for every query, and the July 7 report shows P99s across unrelated endpoints moving together whenever the 3.6 s maps aggregate ran.

The same hazard is live in two places today. The PMTiles reader re-parses root and leaf directories in pure Python on every tile — roughly 5 ms with no yields — which is why there's a hot-bytes LRU in front of it:

server/app.py:2019–2025

# Reader.get re-parses the root+leaf directories in pure Python
# (~5ms, no gevent yields) on EVERY call, so a cold-nginx-cache burst
# would otherwise head-of-line-block the worker.
with _tile_lock:
    body = _tile_gzip_lru.get(key)

And the vote array build calls np.add.at / np.maximum.at over the whole vote set inside one C call. It's fast — the vectorised rewrite in server/vote_store.py:318 replaced a 4.6M-iteration Python loop — but it does not yield, so those hundreds of milliseconds are hub-frozen. Which is exactly why the SWR rebuild was moved onto a real OS thread rather than a greenlet: the GIL hands off every few ms, so the hub keeps serving.

Chapter 07

The levers

Ranked by expected latency win per unit of risk, against the current ~2.5–3.5 s cold path and ~950 ms warm path. Every one is grounded in the ledger in Chapter 4.

LEVER 01

Put the immutable artifacts behind a CDN

Target
The 15.5 MB topology blob first; then graph.pmtiles, blocks.pmtiles, places.pmtiles, and /assets/.
Where
terraform/main.tf:524 (domain mapping today) · deploy/nginx-cloudrun.conf:136 · GraphLayer.tsx:1868, 1906
Win
Removes a trans-continental round trip and origin bandwidth from the dominant remaining term of every cold load. Also removes 15.5 MB × N from the single gevent worker's nginx.
Risk
Low. The blob is already version-addressed; there is no invalidation story to get wrong.

This is the one place where OMCB's lesson transfers verbatim, and it is currently City Edit's largest single unclaimed win. Today every cold visitor, wherever they are, pulls 15.5 MB from one instance in us-central1 through an nginx sharing a container with the app. There is no reason for those bytes to touch the app at all.

The mechanism is already halfway built. The client cache-busts by graph version because a stale topology paired with fresh votes crashes mobile Safari:

client-react/src/components/GraphLayer/GraphLayer.tsx:1868–1882

const withVersion = (url, v = version) =>
  v ? url + (url.includes("?") ? "&" : "?") + "v=" + encodeURIComponent(v) : url;

// "-bin2-<blocks>" mirrors the server ETag: format AND block mapping
// are versioned separately from topology content.
const binVersion = version
  ? `${version}-bin2${blocksVersion ? `-${blocksVersion}` : ""}`
  : null;

So the object key writes itself: gs://…/topology/<binVersion>.gtb2.br. Publish it at graph-build time (the same place topology_binary_br() already runs in server/graph_registry.py:392), front the bucket with an external HTTPS LB + Cloud CDN, and either 302 /api/graph-topology?format=bin to the object or have the client build the CDN URL directly. Keep the Flask route as the fallback so a missing object degrades to today's behaviour instead of a blank map.

Note the ordering advantage: standing up the LB for the blob gives you the tier for /assets/ and the PMTiles archives for free, and those are already immutable / week-long.

LEVER 02

Stop shipping the whole city's topology

Target
The GTB2 blob's size, not its delivery.
Where
server/graph_registry.py:170–190 (blob assembly) · client-react/src/components/GraphLayer/graphTopology.ts (decode + accessors)
Win
Potentially the same order Hamy estimated for OMCB — a first view covers a small fraction of a 5-borough graph.
Risk
High. This is a real architectural change, not a config one.

This is Hamy's ~99% observation applied to the payload that deserves it. A cold visitor to /m/nyc-walkways sees a few square kilometres and receives 3.3M edges. The blob is a flat concatenation — header, coords, ends, edge→block ids — with edge_id as an implicit array index, which is precisely what makes chunking hard: every id in the vote arrays, the block index and the URL waypoints is a global index into that array.

Two viable shapes, in increasing order of ambition:

  1. Bbox-scoped blob with a global id space. Serve ?format=bin&bbox=… returning a sparse GTB2 variant: an explicit edge_id column alongside coords and ends, covering only edges intersecting the view plus a ring. Client holds a holey topology — the same trick sparseVotes.ts already plays for votes — and fetches additional bboxes on pan. Every consumer already indexes by edge id, so ids stay global and nothing downstream renumbers.
  2. Topology as tiles. Reuse the machinery already serving /api/tile/<city>/blocks/<z>/<x>/<y>.mvt — including the nginx proxy_cache, the 204-for-empty convention, and the immutable ETags — for graph geometry. This makes Lever 1 and Lever 2 the same lever.
What breaks

Anything that needs the global graph rather than the visible one: buildNodeAdj, route-proposal corridor growth (ROUTE_CHECK_MAX_POPS 30000 A* runs), and topProposals spacing at TOP_PROPOSAL_MIN_SPACING_M 600. The honest answer is probably that proposal computation moves server-side or into a worker fed by a coarse city-wide summary, and the client keeps only the geometry it can see. That is a redesign, so cost it before starting — but the number it is chasing is the whole remaining cold path.

LEVER 03

Give the box more than one worker

Target
4 vCPU serving through 1 gevent worker.
Where
deploy/supervisord.conf · terraform/main.tf:329, 407
Win
Removes head-of-line blocking on every non-yielding operation: the PMTiles directory parse, the numpy vote build, brotli, any un-patched C call.
Risk
Memory. Each worker is a full copy of the resident graphs.

The comment at main.tf:404 is honest about this: "the single gevent worker plus nginx gzip are the concurrency ceiling per instance — extra cores keep topology/vote-snapshot compression off the request path's back." Three cores are doing compression and nothing else.

You can't naively set --workers 4: 1.35 Gi resident × 4 blows the 8 Gi limit. But the barrier is softer than it looks, because the correctness prerequisites are already met — the voter read-modify-write is serialised fleet-wide by vote_store.voter_lock, and each instance's vote cache is a bounded shared-nothing LRU with Redis holding truth. That is exactly the argument main.tf:432–440 makes for maxScale 8; it applies within an instance too.

Three routes, cheapest first:

  • Preload + fork. gunicorn --preload loads the graph arrays once in the arbiter; workers fork and share pages copy-on-write. walk_graph_arrays.npz decodes to numpy arrays that are never mutated at runtime, so CoW should hold — the refcount-touching problem that defeats this for Python objects largely doesn't apply to the array buffers themselves.
  • Two workers at 4 Gi each. Doubles the yield-free-operation tolerance for one config line, no sharing tricks. The measured 1.35 Gi is with every city warm; a two-worker instance would need per-worker LRU budgets trimmed from VOTE_CACHE_MAX_MB 512.
  • Split the workload. Serve the big static blobs from the CDN (Lever 1) and this pressure mostly evaporates, because the remaining Flask work is small JSON and tiles.

Verdict Do Lever 1 first and re-measure. If the worker still blocks, preload + 2 workers is the next step, not more instances — maxScale 8 already exists and each scale-out instance pays a fresh graph load and a fresh set of ~6 s snapshot builds.

LEVER 04

Make the vote snapshot cross-instance

Target
The ~6 s array build, currently rebuilt per instance × map × mode.
Where
server/app.py:328–332, 2376–2404 · server/vote_store.py:318
Win
Kills the last inline-build path and makes scale-out cheap.
Risk
Low–medium. Redis is 1 GB BASIC with allkeys-lru; a large snapshot value could evict vote data.

The cache today is an in-process OrderedDict bounded at 512 MB. It's correct and it's shared-nothing by design — but that means every instance the autoscaler adds starts cold, and the fork at app.py:2376 still builds inline when nothing is cached at all:

server/app.py:2390–2401

else:
    # Nothing cached at all (fresh instance past prewarm, LRU eviction,
    # a blocks re-bake) — there is nothing to serve stale, so this one
    # request builds inline behind the single-flight lock.
    with lock:
        rmap.graph.ensure_loaded()
        fresh_rev = int(redis_client.get(vote_store.revision_key(rmap.slug)) or 0)
        entry = (_vote_cache_get(cache_key, fresh_rev)
                 or _build_graph_votes_body_locked(rmap, mode, fresh_rev, cache_key))

The natural fix follows the shape you already chose for the topology: the sparse body is ~57 KB, small enough to live in Redis under votesnap:<slug>:<mode>:<rev> with a short TTL. A cold instance then serves a fresh visitor from Redis in milliseconds instead of building the arrays. The instance-local LRU stays as an L1 in front of it.

Watch the eviction interaction: Memorystore is 1 GB with allkeys-lru, and per the monitoring runbook, past 100% it starts evicting the vote hashes themselves — which are the serving source of truth. Snapshots are regenerable and vote hashes are not, so either give snapshots a TTL short enough that they're never the LRU-resident bulk, or bump memory_size_gb alongside.

LEVER 05

Move the client's index build off the main thread

Target
The post-download gap on warm loads — the ~950 ms that isn't network.
Where
GraphLayer.tsx:1947–1975 · spatialLookup.ts:178 · graphCache.ts
Win
Interaction-ready sooner on repeat visits, which is most visits.
Risk
Low, structurally — the payload is already transferable.

On a warm load the topology comes out of IndexedDB as an ArrayBuffer — deliberately, because structured-cloning millions of small arrays is itself a mobile memory spike. Then the main thread decodes it and builds four indexes in 120,000-item slices.

Everything about that pipeline is already worker-shaped: the input is a transferable ArrayBuffer, and the output — coords (Int32Array), ends (Uint32Array), edgeBlockId (Int32Array) — is entirely typed arrays. A worker could read IndexedDB directly, decode, build the spatial indexes, and post typed arrays back with zero-copy transfer. The yieldToMain slicing then becomes unnecessary rather than merely well-tuned.

The same argument applies to route-proposal recompute, which is already requestIdleCallback-scheduled with a 4 s timeout and sliced one vote type at a time. It runs A* with a 30,000-pop cap per corridor check and up to 16 recovery checks per corridor. That's a worker's job, not an idle callback's — the reason it's an idle callback is that it needs the topology, which lives on the main thread. Move the topology into the worker and both problems close together.

LEVER 06

Rewrite the hot path in Go — don't

OMCB's claim
Flask → Go, ~20× faster.
Applicability here
Low. Different bottleneck.

It is the most quotable number in Hamy's post and the one most likely to send you down a six-week detour. His 20× was against per-request Python doing per-connection work at high fan-out — request handling was the workload.

City Edit's hot loops already left Python. build_arrays is numpy scatter-adds; the tile path is a byte pass-through with an LRU; the topology blob is ndarray.tobytes() concatenation pre-compressed once per graph load; routing is OSRM, a C++ service. What's left in Python is the glue, and the glue is not the ~2.5 s.

The runtime lesson that does transfer is narrower and is Lever 3: the problem is not that Python is slow, it's that one gevent worker has no parallelism to fall back on when a C call doesn't yield. Go would fix that as a side effect of rewriting everything. Two gunicorn workers fix it for one line.

Chapter 08

What not to copy

Redis as the only store

OMCB has no database. City Edit's split — Postgres canonical, Redis serving — is load-bearing and should stay. The rebuild_redis_for_map path exists precisely because Memorystore is 1 GB with allkeys-lru and will evict under pressure. A checkbox board can be recreated from nothing; 1.8M vote rows with device identity and provenance cannot.

Capping bandwidth by dropping updates

OMCB's mitigation was to shed deltas and periodically re-push full state. City Edit's equivalent already exists in a strictly better form: an overflowing subscriber is closed (QUEUE_MAX 256) and its reconnect + gap-refetch resyncs only that client. Don't add a global cap; the per-client one is more precise and already handles the case.

Polling instead of WebSockets

Hamy's HTMX variant traded real-time for cacheability. That trade is wrong here: City Edit's WS traffic is a merged 100 ms flush of ~145-edge casts on a map with a handful of concurrent viewers — it is not the cost. The cacheable-payload half of his argument is right, and City Edit should take it — but for the topology, via a CDN, not by downgrading the vote stream.

Horizontal scale-out as the first answer

Eight cheap stateless droplets works because an OMCB app server holds nothing. A City Edit instance holds every city graph. maxScale 8 is correct as a safety valve and wrong as a performance strategy: each added instance pays a graph load, a set of ~6 s snapshot builds, and its own 512 MB LRU before it helps anyone.

Chapter 09

Measure first

The instrumentation for all of this already exists — the July 22 work built it. Use it as the gate on every lever above.

The one number that matters

cityedit_map_load_ms, a log-based distribution extracted from the [MAPLOAD] line at server/app.py:2260, labelled by map / cached / nav / src. The client beacons it from client-react/src/utils/loadTelemetry.ts when the full-screen loader first dismisses — base map ready and heatmap painted. Split every measurement by cached_topo: Lever 1 and 2 move the cold arm, Lever 5 moves the warm arm, and averaging them hides both.

Reproducing a cold load

# TTFB for the term Lever 4 targets — first call vs second on one instance
curl -o /dev/null -s -w '%{time_starttransfer}\n' \
  'https://cityedit.org/api/graph-votes?map=nyc-bikes&mode=bikepaths&format=sparse'

# The bytes Lever 1 targets (br negotiated)
curl -o /dev/null -s -H 'Accept-Encoding: br' \
  -w 'size=%{size_download} ttfb=%{time_starttransfer} total=%{time_total}\n' \
  'https://cityedit.org/api/graph-topology?format=bin&map=nyc-bikes'

For the end-to-end number, headless Chrome on a fresh profile is what produced the 8.5–9.9 s figures — a warm browser profile measures the wrong arm. And per the debugging notes: a hidden or occluded Chrome window freezes rAF, so MapLibre never fires load and the beacon never sends. Bring the window forward or you'll measure nothing.

The alerts that will tell you a lever went wrong

  • App memory > 90% of 8 Gi — the first thing Lever 3 (more workers) will trip. Steady state is ~70–75%.
  • Redis memory > 85% — the first thing Lever 4 (snapshots in Redis) will trip. Past 100%, allkeys-lru evicts vote data and the heatmap silently loses votes.
  • Sustained 5xx — a gunicorn worker timeout on a graph load, or an OOM restart loop.
